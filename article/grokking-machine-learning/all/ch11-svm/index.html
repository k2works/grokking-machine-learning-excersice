    第 11 章 サポートベクターマシンとカーネル法 - 3 言語比較¶

    原著第 11 章の SVM とカーネル法を、Python・Kotlin・F# で実装した結果を比較します。各言語の詳細は Python 版・Kotlin 版・F# 版 を参照してください。

    本章が明かすこと¶

    第 5 章のパーセプトロンには、正解率では見えない欠陥がありました。

    モデル 正解率 マージン幅（Python） （Kotlin） （F#）
    パーセプトロン（第 5 章） 1.0 0.0 0.0 0.0
    SVM（正則化 0.01） 1.0 0.648 0.564 0.577

    3 言語すべてでパーセプトロンのマージンが 0 になりました。 第 5 章では 3 言語が別々の境界線に到達しましたが、どの解も「点が境界線の上にちょうど乗っている」 という同じ弱点を持っていたのです。

    第 5 章で score >= 0 を正のクラスとする約束にしたおかげで正解率は 1.0 ですが、その点が少しでも動けば誤分類になります。「分離できた時点で止まる」というアルゴリズムの性質が、そのまま危うさになりました。

    第 7 章では「正解率はクラスが偏ると壊れる」と学びました。本章では別の形で、正解率が見せてくれないもの が現れています。

    前章のモデルを測り直す¶

    3 言語とも、第 5 章のパーセプトロンを SVM の型として解釈し直して測っています。

        perceptron, _ = perceptron_algorithm(POINTS, PERCEPTRON_LABELS)
    as_svm = SupportVectorMachine(tuple(perceptron.weights), perceptron.bias)

        val (perceptron, _) = perceptronAlgorithm(points, perceptronLabels)
    val asSvm = SupportVectorMachine(perceptron.weights, perceptron.bias)

        let perceptron, _ = GrokkingMl.Ch05Perceptron.perceptronAlgorithm 0.01 1000 0 points perceptronLabels

    let asSvm =
        { Weights = perceptron.Weights
          Bias = perceptron.Bias }

    両者の内部表現（重みとバイアス）が同一だからできることです。 第 10 章では第 6 章の実装を呼んで比較しましたが、本章では 型を移し替えて同じ指標で測っています。

    3 言語とも「構造が同じでも別の型」として扱い、明示的に変換しています。暗黙の変換がないおかげで、「これは SVM として測っている」という意図が読み取れます。

    ヒンジ損失¶

        return max(0.0, 1.0 - label * model.score(point))

        max(0.0, 1.0 - label * model.score(point))

        max 0.0 (1.0 - float label * score model point)

    label * score は「正しい側にどれだけ離れているか」です。ラベルを +1 / -1 で表すのはこのためです（第 5・6 章の 0/1 では、この積が意味を持ちません）。

    状況 label × score ヒンジ損失
    正解かつ余裕がある 2.0 0.0
    正解だがぎりぎり 0.5 0.5
    境界線上 0.0 1.0
    誤分類 -1.0 2.0

    「正解しているのに損失が残る」 のが第 5 章との決定的な違いです。

    型変換は第 5・6 章と同じ構図です。Python は動的、Kotlin は演算子オーバーロードで Int * Double を昇格、F# は float label の明示が必須。章をまたいで同じ差が繰り返し現れます。

    損失関数の系譜¶

    第 5 章から本章まで、損失関数が 3 つ登場しました。

    章 損失 正解した点の扱い 特徴
    第 5 章 パーセプトロン誤差 完全に無視 退化状態を 0 と誤認する
    第 6 章 対数損失 確率が 1 に近づくまで押す 確信度を測れる
    第 11 章 ヒンジ損失 マージンの外に出るまで押す 余白を稼ぐ

    第 6 章と第 11 章はどちらも「正解した点も動かす」のですが、止まる条件が違います。対数損失は永遠に押し続け（確率は 1 に到達しない）、ヒンジ損失はマージンの外に出た時点で 0 になります。

    この違いが「SVM は境界近くの点（サポートベクター）だけで決まる」という性質を生みます。

    正則化の意味が変わる¶

        penalty = regularization * sum(w * w for w in model.weights)

    第 4 章の L2 正則化とまったく同じ式です。しかし目的が違います。

    章 正則化の目的 効果
    第 4 章 過学習を防ぐ 重みを縮めてモデルを単純化
    第 11 章 マージンを広げる マージン幅は 2 / \|\|w\|\| に比例

    同じ式が別の意味を持つ例です。 第 4 章では「モデルの複雑さへの罰」でしたが、ここでは「余白を稼ぐ動機」になります。

    そして 3 言語とも、直感に反する結果をテストで固定しました。

    def test_weaker_regularization_widens_the_margin():
    loose, _ = train_svm(POINTS, LABELS, epochs=20000, regularization=0.01)
    tight, _ = train_svm(POINTS, LABELS, epochs=20000, regularization=0.1)
    assert loose.margin(POINTS, LABELS) > tight.margin(POINTS, LABELS)
    正則化 Python のマージン Kotlin F#
    0.01 0.648 0.564 0.577
    0.10 0.385 0.206 0.278

    「正則化を強くすればマージンが広がる」は誤りでした。 3 言語とも同じ方向の結果です。正則化が強すぎると重みが 0 方向へ潰れ、||w|| が小さくなる以上に 境界線からの距離そのものが縮みます。

    第 4 章の AUC のテストと同じく、思い込みで期待値を書いていたら失敗していた 種類の性質です。実測してから書きました。

    カーネルをどう表すか¶

    Kernel = Callable[[Point, Point], float]


def linear_kernel(a: Point, b: Point) -> float:
    return dot(a, b)


def polynomial_kernel(degree: int = 2, constant: float = 1.0) -> Kernel:
    def kernel(a: Point, b: Point) -> float:
        return (dot(a, b) + constant) ** degree

    return kernel

    typealias Kernel = (Point, Point) -> Double

val linearKernel: Kernel = { a, b -> dot(a, b) }

fun polynomialKernel(degree: Int = 2, constant: Double = 1.0): Kernel =
    { a, b -> (dot(a, b) + constant).pow(degree) }

    type Kernel = Point -> Point -> float

let linearKernel: Kernel = dot

let polynomialKernel (degree: int) (constant: float) : Kernel =
    fun a b -> (dot a b + constant) ** float degree

    F# の let linearKernel: Kernel = dot が際立ちます。 既存の dot 関数がそのままカーネルの型に適合するため、ラッパーが要りません。

    言語 カーネル型 既存関数の再利用
    Python Callable[[Point, Point], float] 関数で包み直す
    Kotlin (Point, Point) -> Double ラムダで包み直す
    F# Point -> Point -> float（カリー化） そのまま代入

    F# の関数型が カリー化されている（1 引数ずつ受け取る）ため、dot の型がそのまま Kernel になります。Python と Kotlin の関数型は「2 引数のタプルを受け取る」形なので、dot(a, b) を呼び直す層が挟まります。

    設定が要るカーネル（多項式、RBF）は 3 言語とも「カーネルを返す関数」です。第 9 章の Impurity、第 4 章の Regularization と同じ、戦略を型で表す という一貫した設計です。

    カーネル分類器がモデルの形を変える¶

    これまでのモデルは、学習が終われば訓練データを捨てられました。

    章 モデルが保持するもの 訓練データ
    3〜6・10 章 重みベクトル 捨てられる
    8 章 単語ごとの確率表 捨てられる
    9 章 木 捨てられる
    11 章（カーネル） 重み + 訓練点そのもの 捨てられない

    写した先の空間の座標が計算できない以上、「その空間での重みベクトル」も持てません。代わりに「どの訓練点とどれだけ似ているか」の重み付き和で予測します。

    重みが 0 の点は無視できる ので、実際には「重みが正の点」だけが効きます。それが サポートベクター です。

    この設計変更は、言語ごとの副作用も生みました。

    data class KernelClassifier(
    ...
    val kernel: Kernel,
)

    Kotlin では data class に関数を持たせると equals が期待どおり働きません。 関数は値としての等価性を持たないためです。第 9 章では木の等価比較をテストに使えましたが、本章ではできません。

    そのため 3 言語とも、本章のテストは等価性ではなく 振る舞い（正解率、重みの符号）を検証しています。型に関数を持たせると、自動生成される機能の意味が変わる という設計上の注意点です。

    XOR を 3 種類のカーネルで解く¶

    カーネル Python Kotlin F#
    線形 0.50 0.75 0.50
    多項式（2 次） 1.00 1.00 1.00
    RBF 1.00 1.00 1.00

    線形カーネルはどの言語でも 1.0 に届きません。 内積しか使わないので、実質的に第 5 章のパーセプトロンと変わらないためです。値が 0.50 と 0.75 に分かれるのは乱数列の違い（どの点を先に見るか）によるもので、「解けない」という結論は 3 言語で共通 です。

    多項式カーネルと RBF カーネルは 3 言語とも 1.0 に達しました。アルゴリズムは一切変えず、カーネル関数を差し替えただけです。

    XOR を解く 2 つの道¶

    第 10 章と本章は、同じ問題をまったく違う方法で解きました。

    第 10 章（ニューラルネット） 第 11 章（カーネル法）
    解き方 隠れ層で特徴を 学習する カーネルで特徴を 設計する
    必要な設計判断 層の数、幅 カーネルの種類、そのパラメータ
    モデルのサイズ 重み行列（データ量と無関係） 訓練点の数に比例
    説明可能性 低い（隠れ層の意味は不明） カーネル次第（RBF は「近い点に似せる」）
    学習の計算量 逆伝播（層の数に比例） カーネル計算（点の数の 2 乗）

    前者は柔軟だが不透明、後者は明快だが選択が難しい というトレードオフです。第 9 章の決定木が「説明可能性」で優れていたのと同じく、手法ごとに得意な軸が違います。

    この章のまとめ¶

    観点 Python Kotlin F#
    強み 連鎖比較（0 < a < b < 1）が 1 行、クロージャで工場関数が素直 if が式なので条件付きの勾配項をそのまま書ける 既存関数をそのままカーネル型に代入できる、{ model with } で部分更新
    注意点 型エイリアスは実行時に守られない 連鎖比較がない、data class + 関数で equals が壊れる 数値変換の明示が必要

    第 9 章では F# の判別共用体、第 10 章では不変リストの :: が噛み合いました。本章で噛み合ったのは カリー化された関数型 です。Kernel = Point -> Point -> float という型に既存の dot がそのまま適合するのは、関数を第一級の値として設計してきた言語ならではです。
