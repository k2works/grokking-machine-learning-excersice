    第 13 章 エンドツーエンドの実例（Kotlin 版）¶

    原著第 13 章「Putting it all in practice」を Kotlin で実装します。これまでの章で作った部品を組み合わせて、生データから評価までを 1 本のパイプラインに通します。

    新しいアルゴリズムは登場しません。本章の主題は 「実務のほとんどは前処理と評価である」 ということです。

    サンプル実装は apps/grokking-ml-kotlin/src/main/kotlin/ch13/EndToEnd.kt です。

    Kotlin Notebook で試す: この章の実験は ch13.ipynb にまとめてあります。実装本体を読み込んで動かすので、値を変えてその場で試せます。

    この章で作るもの¶

    • 欠損値の補完・正規化・One-Hot エンコーディング
    • 生データから特徴量ベクトルへの変換
    • 3 つのモデル（第 6・9・12 章）の学習と比較
    • 第 7 章の指標による評価

    部品を組み合わせるだけ¶

    インポートを見れば、本章の性格が分かります。

    import ch06.LogisticClassifier
import ch06.logisticRegression
import ch07.auc
import ch07.confusionMatrix
import ch07.f1Score
import ch07.precision
import ch07.recall
import ch09.Tree
import ch09.buildTree
import ch12.AdaBoost
import ch12.trainAdaBoost
import ch07.accuracy as matrixAccuracy

    4 つの章から部品を集めています。 どれも書き換えていません。

    import ch07.accuracy as matrixAccuracy というインポート別名が要点です。本シリーズでは accuracy という名前が第 5・6・9・11・12 章に登場します。同じ概念に同じ名前を付けてきた結果、統合の段階で衝突しました。 Kotlin のインポート別名がそれを解決します。

    第 4 章の分割は使えなかった¶

    Python 版では第 4 章の train_test_split をそのまま流用できましたが、Kotlin では型が合いません。

    // 第 4 章のシグネチャ
fun trainTestSplit(features: List<Double>, labels: List<Double>, ...): Split

    第 4 章の特徴量は 1 次元（List<Double>）でした。本章の特徴量は多次元（List<List<Double>>）です。中身の処理はインデックスの並べ替えだけなので、論理的には同じものが使えるはずですが、型が拒否します。

    そこで本章で書き直しました。

    /** 訓練用とテスト用に分割する。第 4 章と同じ手順を多次元の点に対して行う。 */
fun splitDataset(dataset: Dataset, testRatio: Double = 0.3, seed: Int = 0): DataSplit {
    val indices = dataset.points.indices.shuffled(kotlin.random.Random(seed))
    val testSize = (dataset.points.size * testRatio).toInt()
    val testIndices = indices.take(testSize)
    val trainIndices = indices.drop(testSize)
    return DataSplit(
        trainPoints = trainIndices.map { dataset.points[it] },
        trainLabels = trainIndices.map { dataset.labels[it] },
        testPoints = testIndices.map { dataset.points[it] },
        testLabels = testIndices.map { dataset.labels[it] },
    )
}

    ジェネリクス（fun <T> split(items: List<T>, ...)）で共通化する選択もありました。 本シリーズでは教材として各章を独立して読めることを優先し、第 4 章の実装は 1 次元のまま残しています。実務なら第 4 章の時点でジェネリックにしておくのが正解です。

    「後で再利用するとき、型がどこまで一般的だったか」が問われる という、静的型付け言語ならではの教訓です。

    前処理¶

    欠損値¶

    /** 数値に見えない値は既定値に落とす。欠損への最初の砦。 */
fun parseNumber(text: String, default: Double = 0.0): Double = text.toDoubleOrNull() ?: default

/** 欠損を中央値で埋める。平均より外れ値に強い。 */
fun imputeMissing(column: List<Double?>): List<Double> {
    val filler = median(column.filterNotNull())
    return column.map { it ?: filler }
}

    toDoubleOrNull() が Kotlin らしい点です。例外ではなく null で失敗を返す ため、?: default の 1 行で処理できます。Python 版では try/except のブロックが必要でした。

    List<Double?> という型で「値がないかもしれない列」を表します。filterNotNull() で既知の値だけを取り出し、it ?: filler で埋める。null 安全性が前処理の記述に直結しています。

    平均ではなく中央値を使います。 外れ値に引きずられないためです。

    @Test
fun `imputeMissing は外れ値に強い`() {
    // 平均なら 1000 に引きずられるが、中央値なら影響を受けない
    val filled = imputeMissing(listOf(1.0, 2.0, 3.0, 1000.0, null))
    assertEquals(2.5, filled.last(), 1e-9)
}

    正規化¶

    fun normalize(column: List<Double>): List<Double> {
    val low = column.min()
    val high = column.max()
    if (high == low) return column.map { 0.0 }
    return column.map { (it - low) / (high - low) }
}

    年齢は 18〜70、収入は 200〜900。このまま第 6 章のロジスティック回帰に渡すと、収入だけが効いてしまいます。 重みの更新量は特徴量に比例する（第 3 章の二乗トリック以来ずっとそうです）ので、値の大きい特徴量が支配的になります。

    high == low のときに 0 除算しないことも仕様として固定しました。

    カテゴリ変数¶

    fun oneHot(column: List<String>): Pair<List<List<Double>>, List<String>> {
    val categories = column.distinct().sorted()
    return column.map { value -> categories.map { if (value == it) 1.0 else 0.0 } } to categories
}

    「東京・大阪・京都」を 0・1・2 と番号で表すと、「京都は東京の 2 倍」という存在しない大小関係が生まれます。 代わりに 3 本の 0/1 列へ展開します。

    distinct().sorted() でカテゴリの順序を固定しています。列の順番が実行のたびに変わると、モデルの解釈が破綻します。

    生データから特徴量へ¶

    fun buildDataset(rows: List<Row>, labelColumn: String): Dataset {
    val labels = rows.map { if (it[labelColumn] == "yes") 1 else 0 }
    ...
    numericColumns.forEach { name ->
        val raw = rows.map { row -> row[name]?.takeIf { it.isNotEmpty() }?.let { parseNumber(it) } }
        columns += normalize(imputeMissing(raw))
        names += name
    }
    ...
}

    row[name]?.takeIf { it.isNotEmpty() }?.let { parseNumber(it) } という 1 行に注目してください。「キーがない」「空文字」「数値でない」という 3 段階の欠損を、null 安全演算子の連鎖で扱っています。

    • row[name] → キーがなければ null
    • ?.takeIf { it.isNotEmpty() } → 空文字なら null
    • ?.let { parseNumber(it) } → 値があれば数値化

    結果は Double? になり、そのまま imputeMissing へ渡せます。Python 版では None if row[name] == "" else parse_number(row[name]) と三項演算子で書いた箇所です。 Kotlin のほうが段階が明示されます。

    3 つのモデルを同じ土俵で比較する¶

    fun evaluate(
    name: String,
    predict: (Point) -> Int,
    probability: (Point) -> Double,
    points: List<Point>,
    labels: List<Int>,
): Evaluation {
    val matrix = confusionMatrix(labels, points.map(predict))
    return Evaluation(
        name = name,
        accuracy = matrixAccuracy(matrix),
        precision = precision(matrix),
        recall = recall(matrix),
        f1 = f1Score(matrix),
        auc = auc(labels, points.map(probability)),
    )
}

    モデルの型ではなく「予測関数」と「確率関数」を受け取ります。 これにより、共通のインターフェースを後付けせずに 3 つのモデルを同じ関数で評価できます。

    3 つのモデルは出力の形がばらばらです。

    モデル 予測 「確率」に相当するもの
    ロジスティック回帰（第 6 章） 0 / 1 予測確率（0〜1）
    決定木（第 9 章） 0 / 1 なし（0/1 をそのまま使う）
    AdaBoost（第 12 章） +1 / -1 重み付き投票のスコア（範囲は不定） 
    fun evaluateAdaBoost(model: AdaBoost, points: List<Point>, labels: List<Int>): Evaluation =
    evaluate(
        "adaboost",
        { if (model.predict(it) == 1) 1 else 0 },
        { model.score(it) },
        points,
        labels,
    )

    AdaBoost だけラベルの表現が違う ため、変換が必要でした。第 11 章で +1/-1 を導入した判断が、ここで統合コストとして表れています。

    points.map(predict) のように 関数参照をそのまま map へ渡せる のも、この設計が成立する理由です。

    実行結果¶

    「40 歳未満かつ収入 400 超なら購入」という規則に従う擬似データ 40 件（うち 9 件に 1 件は年齢が欠損）で試します。

    モデル 正解率 適合率 再現率 F1 AUC
    ロジスティック回帰 0.750 1.000 0.250 0.400 1.000
    決定木 0.833 1.000 0.500 0.667 0.750
    AdaBoost 0.917 1.000 0.750 0.857 1.000

    AdaBoost が勝ちました。 第 12 章で見たとおり、切り株を積み重ねることで「40 歳未満」「収入 400 超」という 2 つの条件を順に取り込めるためです。

    注目すべきは ロジスティック回帰の AUC が 1.000 なのに F1 が 0.400 という点です。

    • AUC 1.000 = 順位付けは完璧（買う人ほど高いスコアを付けている）
    • F1 0.400 = 閾値 0.5 での判定は不十分（再現率 0.250）

    第 7 章で「AUC は閾値に依存しない」「F1 は閾値に依存する」と学びました。この 2 つの指標が正反対の評価を下す例が、実データで現れました。 ロジスティック回帰は閾値を下げれば大きく改善します。モデルが悪いのではなく、閾値の選び方が悪い のです。

    これらの値は Python 版・F# 版とは異なります。擬似データの生成に使う乱数と、訓練／テスト分割の乱数が言語ごとに違う ためです。同じ規則のデータでも、40 件のうちどの 12 件がテストに回るかで数字は動きます。

    assertEquals(runPipeline(rows), runPipeline(rows))

    パイプライン全体が決定的である ことをテストで固定しました。data class の equals により、評価結果のリストごと比較できます。

    まとめ¶

    • 本章に新しいアルゴリズムはありません。10 章分の部品を組み合わせただけです。
    • インポート別名により、章をまたいで同名の関数（accuracy）を共存させられます。
    • 第 4 章の分割関数は型が 1 次元に固定されていたため再利用できませんでした。再利用を見越すならジェネリックにしておくべきでした。
    • toDoubleOrNull() と null 安全演算子の連鎖により、多段階の欠損処理が 1 行で書けます。
    • モデルの型ではなく関数を受け取れば、共通インターフェースなしに比較できます。
    • AUC 1.000 と F1 0.400 が同居しうることが、実データで確認できました。
