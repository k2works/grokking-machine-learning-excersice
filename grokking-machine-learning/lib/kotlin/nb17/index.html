    #17 SVM 用のデータセットを作る（Kotlin）¶

    原著ノートブック: Chapter_11_Support_Vector_Machines/Building_the_datasets.ipynb

    第 11 章（SVM）で使う 3 つのデータセットを 乱数で作る 回です。

    原著は乱数の種を固定していないので、生成そのものは再現できません。 代わりに「配布されている CSV が本当にその規則で作られたのか」を検算しました。 考え方は Python 版 に書いています。ここでは Kotlin 側の話をします。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-kotlin-lib/src/main/kotlin/lib/Nb17BuildingDatasets.kt
    テスト apps/grokking-ml-kotlin-lib/src/test/kotlin/lib/Nb17BuildingDatasetsTest.kt
    実行 ./gradlew test --tests "lib.Nb17*"

    規則をデータに持たせる¶

    原著は 3 つのデータセットを コピペで 3 回書いて います。 違うのはループ回数と z = ... の 1 行だけです。

    Kotlin では、その違いだけをデータにまとめました。

        /** 1 つのデータセットの作り方 */
    data class Spec(
        val name: String,
        /** 規則どおりに作る点の数 */
        val points: Int,
        /** ラベルを乱数にする点（ノイズ）の数 */
        val noise: Int,
        /** ラベルを決める規則 */
        val rule: (Double, Double) -> Int,
    ) {
        val total: Int get() = points + noise
    }

        val LINEAR = Spec("linear", 50, 10, ::linearRule)
    val ONE_CIRCLE = Spec("one_circle", 100, 10, ::oneCircleRule)
    val TWO_CIRCLES = Spec("two_circles", 200, 20, ::twoCirclesRule)

    関数をデータクラスのフィールドに入れられる ので、 生成器も検算も 1 つで済みます。原著の 3 つのセルが 1 つの generate に畳まれます。

        fun generate(spec: Spec, seed: Int): List<Point> {
        val random = Random(seed)
        fun coordinate() = COORD_SCALE * random.nextDouble() + COORD_OFFSET

        val points = List(spec.points) {
            val x = coordinate()
            val y = coordinate()
            Point(x, y, spec.rule(x, y))
        }
        val noise = List(spec.noise) {
            val x = coordinate()
            val y = coordinate()
            Point(x, y, random.nextInt(0, 2))
        }
        return points + noise
    }

    ローカル関数 coordinate() が random を閉じ込めるので、 6 * random.nextDouble() - 3 を 4 回書かずに済みます。

    検算の結果は Python 版と完全に一致する¶

        @Test
    fun `違反はすべてノイズ部分にあり約半数`() {
        // ノイズはラベルを 0 か 1 で振り直すので、規則と食い違うのは約半分
        val expected = mapOf("linear" to 5, "one_circle" to 7, "two_circles" to 12)

        SPECS.forEach { spec ->
            val violations = ruleViolations(spec, load(spec))
            assertEquals(expected.getValue(spec.name), violations.size, spec.name)
            assertTrue(violations.all { it >= spec.points }, spec.name)
            assertTrue(violations.size.toDouble() / spec.noise in 0.2..0.8, spec.name)
        }
    }
    データセット ノイズの数 規則に違反した数
    linear 10 5
    one_circle 10 7
    two_circles 20 12

    3 言語すべてで同じ数 になりました。 規則は四則演算と比較だけなので、浮動小数点の差が出る余地がありません。 #16 のように格子上で数えると言語差が出ますが、 与えられた点をそのまま判定するだけなら差は出ません。

    種を揃えても Python とは違う点が出る¶

    これは記録しておく価値があります。

        @Test
    fun `同じ種でもPythonとは違う点が出る`() {
        // Kotlin の Random と Python の random は別のアルゴリズム（Python は
        // メルセンヌツイスタ）。種を揃えても一致しない。
        // 原著が種を固定していれば、ここで手が止まっていた
        // Python 版の同じ種での 1 点目は 2.0665311091502883
        assertTrue(generate(LINEAR, seed = 0)[0].x1 != 2.0665311091502883)
    }

    Python の random はメルセンヌツイスタ、Kotlin の kotlin.random.Random は XorWow 系の別アルゴリズムです。種を揃えても同じ数列は出ません。

    つまり、もし原著が種を固定していたとしても、移植では再現できませんでした。 このノートブックが再現不能なのは原著の不備というより、 乱数列そのものを言語をまたいで一致させることが原理的に難しい ためです。

    #13 以降で「学習ログは再現できない」と繰り返し書いてきましたが、 その根っこにあるのはこれと同じ事情です。

    逆に言うと¶

    だからこそ、#02 の特異値や #06 の語彙添字のように 乱数を使わない部分が桁まで一致する ことに意味があります。 乱数の絡まない計算は、言語が違っても同じ答えに行き着きます。

    まとめ¶

    項目 原著と一致するか
    3 つのデータセットの規則 完全一致
    配布 CSV の行数（60 / 110 / 220） 完全一致
    先頭部分に規則違反が無いこと 検証済み
    ノイズ部分の違反数（5 / 7 / 12） Python 版・F# 版と完全一致
    生成される座標そのもの 再現できない（種の未固定に加え、乱数器が別物）
