    #11 大学院入学審査の決定木（Kotlin）¶

    原著ノートブック: Chapter_09_Decision_Trees/University_Admissions.ipynb

    入学審査データ 400 件から合否を決定木で当て、木の大きさを変えて過学習を見ます。

    #10 では「Smile の深さ = scikit-learn の深さ + 1」で対応が付きました。 このデータでは対応しません。 実測してみると、深さの効き方が予想と違いました。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-kotlin-lib/src/main/kotlin/lib/Nb11UniversityAdmissions.kt
    テスト apps/grokking-ml-kotlin-lib/src/test/kotlin/lib/Nb11UniversityAdmissionsTest.kt
    実行 ./gradlew test --tests Nb11UniversityAdmissionsTest

    制限が 1 つ足りない¶

    原著は 3 つの制限を同時に掛けます。

    scikit-learn 意味 Smile
    max_depth=3 木の深さ maxDepth
    min_samples_leaf=10 葉に残る件数の下限 nodeSize
    min_samples_split=10 分割してよい節の件数の下限 無い

    min_samples_split にあたるものが Smile にありません。 制限が 1 つ少ない状態で学習することになります。

    深さが飛び飛びに効く¶

    maxDepth を 1 から 6 まで変えて節の数を測りました。

    @Test
fun `Smile の深さは飛び飛びに効く`() {
    // #10 の 12 点では「Smile の深さ = scikit-learn + 1」で対応したが、
    // このデータでは対応しない。2 から 4 まで結果が変わらず、5 で跳ぶ
    val nodes = (1..6).map { nodeCount(fit(data, FEATURE_NAMES, maxDepth = it, minLeafSize = 10)) }

    assertEquals(listOf(1, 3, 3, 3, 15, 15), nodes)
}
    Smile の maxDepth 節の数 正解率
    1 1 0.550
    2 3 0.880
    3 3 0.880
    4 3 0.880
    5 15 0.890
    6 以上 15 0.890

    深さ 2 から 4 まで結果が変わらず、5 で急に跳びます。 単純な深さの上限なら 2→3→4 で節が 3→7→15 と増えるはずです。

    maxNodes を 2 から 10000 まで変えても結果は変わらなかったので、 葉の数の上限が効いているわけでもありません。 深さの制限とは別の停止条件が働いています。

    原因は特定できませんでした。分かったのは 「#10 で見つけた +1 の対応則は、このデータでは成り立たない」 という事実です。1 つの例で確かめた対応則を一般化してはいけません。

    どちらを合わせるか選ぶ¶

    原著の小さい木は 15 節・正解率 0.885 です。Smile では次の 2 択になりました。

    Smile の設定 節の数 正解率 原著の 2 人の予測
    maxDepth = 4 3 0.880 再現できる（True / False）
    maxDepth = 5 15 0.890 再現できない（False / False）

    「節の数」と「予測の中身」のどちらを合わせるかを選ぶことになりました。

    原著のこの節の主眼は「CGPA だけで判定が反転する」ことなので、 予測を再現するほうを既定にしました。

    /**
 * 原著が「過学習しない小さい木」として作る設定。
 *
 * 原著は `max_depth=3` / `min_samples_leaf=10` / `min_samples_split=10` の
 * 3 つを掛けて **15 節・正解率 0.885** の木を得た。Smile には
 * `min_samples_split` にあたるものが無く、深さの対応も付かない。
 *
 * ここでは **原著の 2 つの予測を再現できる設定** を選んだ（`maxDepth = 4`）。
 * 節は 3 つ（分割 1 つ）と原著より小さく、正解率は 0.88 になる。
 * 節の数を原著に合わせたい場合は [fitSameSizeAsOriginal] を使う。
 */
fun fitSmaller(data: Admissions): DecisionTree =
    fit(data, FEATURE_NAMES, maxDepth = 4, minLeafSize = 10)

    もう一方も残し、何が違うのかをテストで明示 しました。

    @Test
fun `節の数を原著に合わせると予測が変わる`() {
    // maxDepth=5 なら原著と同じ 15 節・正解率 0.89 になるが、木の中身は違う。
    // 原著が例に挙げた CGPA 8.9 の出願者を不合格と判定してしまう
    val sameSize = fitSameSizeAsOriginal(data)

    assertEquals(15, nodeCount(sameSize))
    assertEquals(0.89, accuracy(sameSize, data), 1e-12)
    assertTrue(!predictApplicant(sameSize, listOf(320.0, 110.0, 3.0, 4.0, 3.5, 8.9, 0.0)))
}

    選ばなかった選択肢もコードに残す のは、再現の限界を記録するためです。 「0.88 になった」とだけ書くと、0.89 の選択肢があったことが失われます。

    2 特徴量なら完全に一致する¶

    7 特徴量では合いませんでしたが、GRE と TOEFL だけに絞ると scikit-learn と同じ分割・同じ正解率 になりました。

    @Test
fun `2特徴量の浅い木は scikit-learn と同じ正解率になる`() {
    // scikit-learn の max_depth=1 が 0.8525、max_depth=2 が 0.8625。
    // Smile では深さが 1 つずれて同じ値になる
    assertEquals(0.8525, accuracy(fitExams(data, 2), data, EXAM_FEATURES), 1e-12)
    assertEquals(0.8625, accuracy(fitExams(data, 3), data, EXAM_FEATURES), 1e-12)
}

    ここでは +1 の対応則が成り立ちます。 特徴量が 2 つで木が浅いうちは、 #10 と同じ関係が保たれるようです。

    根の分割も一致します。

    @Test
fun `2特徴量の木は scikit-learn と同じ分割から始まる`() {
    // GRE Score <= 319.5。TOEFL より GRE のほうが効く
    for (depth in listOf(2, 3, 20)) {
        val root = splitConditions(fitExams(data, depth)).first()

        assertEquals("GRE Score", root.feature)
        assertEquals(319.5, root.threshold, 1e-9)
    }
}

    列名に空白が入る¶

    DOT からの抽出で 1 つ引っかかりました。この章の列名は "GRE Score" のように 空白を含みます。#10 の正規表現では拾えません。

    /** DOT 文字列から、分割に使われた条件を根から順に取り出す */
fun splitConditions(model: DecisionTree): List<Split> =
    SPLIT_LABEL.findAll(model.dot())
        .map { Split(it.groupValues[1].trim(), it.groupValues[2].toDouble()) }
        .toList()

// 列名に空白が入る（"GRE Score" など）ので、パターンにも空白を含める
private val SPLIT_LABEL = Regex("""label=<([A-Za-z_0-9 ]+) &le; ([0-9.]+)<br/>""")

    空白を許すと &le; の前の空白まで拾ってしまうので、trim() が要ります。 構造化されたデータを文字列に落として正規表現で読み戻す ことの脆さが出た箇所です。 Smile が木のノードを API で返してくれれば、こんな心配は要りません。

    この章で Kotlin が効いた場面・効かなかった場面¶

    場面 評価
    2 特徴量の木 効いた — scikit-learn と同じ分割・同じ正解率
    選択肢を残す設計 効いた — 2 つの fit を並べて限界を記録できる
    min_samples_split 効かなかった — Smile に無く制限が 1 つ足りない
    深さの対応 効かなかった — #10 の対応則が通じず、飛び飛びに効く
    DOT の解析 効かなかった — 列名の空白で正規表現が壊れかける

    #09・#10 に続いて、決定木は Smile のいちばん弱い領域でした。 木の構造を API で返さない ことが、すべての手間の根にあります。
