    #02 ハイデラバードの住宅価格を予測する（Kotlin）¶

    原著ノートブック: Chapter_03_Linear_Regression/House_price_predictions.ipynb

    実データ 2518 件から住宅価格を予測します。面積 1 列だけを使う単回帰と、 全 40 列を前処理してから使う重回帰の 2 本立てです。

    Kotlin でこの章を書くと pandas がいかに多くを肩代わりしていたか がはっきりします。 pd.get_dummies の 1 行に相当するものが Kotlin DataFrame には無いので、自分で書くことになります。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-kotlin-lib/src/main/kotlin/lib/Nb02HousePrices.kt
    テスト apps/grokking-ml-kotlin-lib/src/test/kotlin/lib/Nb02HousePricesTest.kt
    実行 ./gradlew test --tests Nb02HousePricesTest

    データセットの読み込み¶

    /** ハイデラバードの住宅データを読み込む。2518 行 × 40 列 */
fun loadData(): DataFrame<*> = DataFrame.readCSV(Datasets.path("Hyderabad.csv").toFile())

    readCSV は readCsv ではありません。Kotlin の命名規約からすると後者が自然に見えますが、 Kotlin DataFrame 0.15 の API は readCSV です。ここは一度引っかかりました。

    列の取り出しはヘルパーにまとめました。Kotlin DataFrame は列の型を実行時に推論するので、 Int として読まれた列を Double として扱うには変換が要ります。

    private fun DataFrame<*>.doubleColumn(name: String): DoubleArray =
    getColumn(name).convertTo<Double>().toList().toDoubleArray()

private fun DataFrame<*>.stringColumn(name: String): List<String> =
    getColumn(name).toList().map { it.toString() }

    面積だけの単回帰¶

    fun fitAreaOnly(data: DataFrame<*>): Nb01LinearRegression.Line {
    val area = data.doubleColumn("Area")
    val price = data.doubleColumn("Price")
    val df = smile.data.DataFrame.of(
        DoubleVector.of("Area", area),
        DoubleVector.of("Price", price),
    )
    val model = OLS.fit(Formula.lhs("Price"), df)
    return Nb01LinearRegression.Line(model.coefficients()[0], model.intercept())
}

    Kotlin DataFrame と Smile の DataFrame は別物 です。前者で CSV を読み、 後者に詰め替えて学習させます。pandas と scikit-learn なら同じ DataFrame を そのまま渡せたところが、2 段になります。

    戻り値には #01 で定義した Line を再利用しました。傾きと切片という同じ意味を持つので、 別の型を作る理由がありません。

    数値は原著と一致します。

    @Test
fun `単回帰の係数は原著と同じ数値になる`() {
    // 原著 scikit-learn の出力
    //   y-intercept: -6222669.083283698
    //   slope (coefficient of Area): 9753.940608184039
    val line = fitAreaOnly(data)

    assertEquals(-6222669.083283698, line.basePrice, 1e-6)
    assertEquals(9753.940608184039, line.pricePerRoom, 1e-9)
}

    前処理¶

    特徴量の持ち方¶

    pandas なら前処理後も DataFrame のままですが、Kotlin では 列名 → 値の配列 という LinkedHashMap に持ち替えました。

    /** 前処理を通したあとのデータ一式 */
data class Preprocessed(
    /** 列名 -> 値。列の順序を保つため LinkedHashMap を使う */
    val features: Map<String, DoubleArray>,
    val labels: DoubleArray,
    val standardizer: Standardizer,
) {
    val columnNames: List<String> get() = features.keys.toList()
    val rowCount: Int get() = labels.size
}

    LinkedHashMap を選んだのは 列の順序が意味を持つ からです。 予測時に組み立てる 1 行は、学習時とまったく同じ列順でなければなりません。 HashMap にすると順序が保証されず、実行のたびに違う結果になり得ます。

    標準偏差は自分で書く¶

    pandas の std() は既定で不偏分散（ddof=1）です。Kotlin の標準ライブラリに 標準偏差はないので、そこを合わせて書きます。

    /** 不偏分散（ddof = 1）の標準偏差。pandas の `std()` の既定に合わせる */
private fun DoubleArray.sampleStd(): Double {
    val mean = average()
    return sqrt(sumOf { (it - mean) * (it - mean) } / (size - 1))
}

    size - 1 を size にすると、3 言語で標準化後の値が食い違います。 テストで Python 版と同じ統計量になることを確認しています。

    @Test
fun `標準化の統計量は Python 版と同じ`() {
    val standardizer = prepared.standardizer

    assertEquals(1644.1516023007396, standardizer.areaMean, 1e-9)
    assertEquals(748.1348121200747, standardizer.areaStd, 1e-9)
    assertEquals(2.6261298274445357, standardizer.bedroomsMean, 1e-12)
    assertEquals(0.6850461155463963, standardizer.bedroomsStd, 1e-12)
}

    get_dummies を自分で書く¶

    pandas なら 1 行です。

    data_scaled_encoded = pd.get_dummies(data_scaled, columns=['Location'], prefix='Location', dtype=int)

    Kotlin では 3 行になります。

    // pandas の get_dummies に相当する処理。地域名を昇順に並べて列を作る
for (name in location.distinct().sorted()) {
    features["Location_$name"] =
        DoubleArray(VALID_ROWS) { if (location[it] == name) 1.0 else 0.0 }
}

    sorted() が要ります。distinct() は出現順を保つので、そのままだと Python 版と列順が変わってしまいます。get_dummies はカテゴリを昇順に並べるので、 それに合わせました。列順は係数の並びに直結するので、揃えておかないと読み比べができません。

    結果は原著と同じ 277 列です。

    @Test
fun `one-hot 符号化で277列になる`() {
    // 原著の出力: X_full.loc[0] ... Length: 277
    assertEquals(277, prepared.columnNames.size)

    val locationColumns = prepared.columnNames.filter { it.startsWith("Location_") }
    // 元の 40 列から Price と Location を除いた 38 列 + 地域の one-hot
    assertEquals(277 - 38, locationColumns.size)
}

    ランク落ちした行列を解く¶

    Python 版 で見たとおり、one-hot 符号化した地域列を 1 つも落としていないため、 設計行列は ちょうど 1 だけランクが足りません。

    Smile の OLS は既定で QR 分解を使い、正則性を仮定します。そのままでは解けないので、 擬似逆行列を求める SVD を明示的に選びます。

    /**
 * 前処理済みの全特徴量で重回帰を学習する。
 *
 * one-hot 符号化した地域の列は合計すると常に 1 になり、切片と線形従属になる。
 * 既定の QR 分解では正則性を仮定するので、擬似逆行列を求める SVD を明示的に選ぶ。
 */
fun fitAllFeatures(prepared: Preprocessed): smile.regression.LinearModel {
    val vectors = buildList {
        add(DoubleVector.of("Price", prepared.labels))
        prepared.features.forEach { (name, values) -> add(DoubleVector.of(name, values)) }
    }
    val df = smile.data.DataFrame.of(*vectors.toTypedArray())
    val properties = java.util.Properties().apply {
        setProperty("smile.ols.method", "svd")
    }
    return OLS.fit(Formula.lhs("Price"), df, properties)
}

    Smile はハイパーパラメータを java.util.Properties の文字列キーで受け取ります。 scikit-learn の名前付き引数に比べると型の助けが無く、キーを打ち間違えても 黙って既定値が使われます。ここは Smile の弱いところです。

    Python 版と数値が一致する¶

    驚いたのはここです。Smile の SVD 解が scikit-learn の解と 14 桁一致しました。

    実装 RMSE 新物件の予測
    Python（scikit-learn） 3981396.2916407348 6,004,735.314678079
    Kotlin（Smile SVD） 3981396.291640734 6,004,735.314678099

    切片だけは違います。

    実装 切片 Area の係数
    Python（scikit-learn） 8,947,283.554 7,023,504.9208845
    Kotlin（Smile SVD） 8,910,003.206 7,023,504.9208845

    切片が 3.7 万違うのに、予測値は 14 桁一致します。 切片の差は地域列の係数がちょうど打ち消しているからです。 ランク落ちした行列で「係数に意味が無い」とはこういうことです。

    テストは当てはまりの良さで検証しています。

    @Test
fun `全特徴量モデルの RMSE は原著とほぼ同じ`() {
    // 原著の出力: Root Mean Squared Error (RMSE) of the model: 3981401.4927888927
    // 係数は一意でないが、当てはまりの良さは解の取り方によらずほぼ同じになる
    val error = rmse(prepared.labels, predictAll(fullModel, prepared))

    assertEquals(3981401.4927888927, error, 3981401.4927888927 * 1e-4)
}

    新しい物件を予測する¶

    fun predictNewHouse(
    model: smile.regression.LinearModel,
    prepared: Preprocessed,
    area: Double,
    bedrooms: Int,
    location: String = "Gachibowli",
): Double {
    val names = prepared.columnNames
    val locationColumn = "Location_$location"
    require(locationColumn in names) { "学習データに無い地域です: $location" }

    val (scaledArea, scaledBedrooms) =
        prepared.standardizer.transform(area, bedrooms.toDouble())
    val row = DoubleArray(names.size)
    names.forEachIndexed { index, name ->
        row[index] = when (name) {
            "Area" -> scaledArea
            "No. of Bedrooms" -> scaledBedrooms
            locationColumn -> 1.0
            else -> 0.0
        }
    }
    return model.predict(row)
}

    Python 版は DataFrame を組み立てて列名で埋めましたが、Kotlin では DoubleArray を列順に埋めます。when の分岐でどの列に何が入るかが 1 か所に集まり、 Python 版より読みやすくなりました。

    require を使うと、失敗時に IllegalArgumentException が投げられます。 Python 版の raise ValueError に対応する Kotlin の作法です。

    この章で Kotlin が効いた場面・効かなかった場面¶

    場面 評価
    予測行の組み立て 効いた — when で列と値の対応が 1 か所にまとまる
    列順の保証 効いた — LinkedHashMap で意図を型に込められる
    CSV 読み込み 引き分け — readCSV の綴りに注意が要る
    one-hot 符号化 効かなかった — pandas の 1 行が自前実装になる
    標準偏差 効かなかった — 標準ライブラリに無く ddof を自分で合わせる
    Smile のハイパーパラメータ 効かなかった — 文字列キーで型の助けが無い

    データ前処理の語彙は、pandas の厚みが際立つ章でした。 一方で学習そのものは Smile が scikit-learn と同じ精度で解いており、差はありません。
