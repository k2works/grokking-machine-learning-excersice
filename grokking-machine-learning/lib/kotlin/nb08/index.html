    #08 ジニ不純度とエントロピーの計算（Kotlin）¶

    原著ノートブック: Chapter_09_Decision_Trees/Gini_entropy_calculations.ipynb

    決定木の章に入ります。木を作る前に、どこで分割すべきかを決める物差し — ジニ不純度とエントロピー — を手で計算します。

    原著は NumPy しか使わない小さな回です。Kotlin では 「初出順を保つ数え上げ」を 1 行で書けるか が焦点になりました。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-kotlin-lib/src/main/kotlin/lib/Nb08GiniEntropy.kt
    テスト apps/grokking-ml-kotlin-lib/src/test/kotlin/lib/Nb08GiniEntropyTest.kt
    実行 ./gradlew test --tests Nb08GiniEntropyTest

    groupingBy が初出順を保つ¶

    原著の counts は 6 行あります。

    def counts(elements):
    classes = {}
    for element in elements:
        if element in classes:
            classes[element] += 1
        else:
            classes[element] = 1
    return [classes[e] for e in classes]

    Kotlin では 1 行です。

    /**
 * 要素ごとの個数を、**初めて現れた順** に返す。
 *
 * 原著は辞書に数えてから取り出しており、Python 3.7 以降の辞書は挿入順を保つ。
 * Kotlin では [LinkedHashMap] が同じ性質を持つ。`groupingBy` の結果も
 * `LinkedHashMap` なので、そのまま初出順になる。
 */
fun counts(elements: List<String>): List<Int> =
    elements.groupingBy { it }.eachCount().values.toList()

    eachCount() が返すのは LinkedHashMap なので、 Python の辞書と同じく挿入順が保たれます。 ['A', 'A', 'A', 'C', 'B', 'C'] は [3, 2, 1]（A=3, C=2, B=1）になり、 辞書順の [3, 1, 2] にはなりません。

    groupBy { it }.mapValues { it.value.size } でも同じ結果ですが、 中間のリストを作らないぶん groupingBy のほうが素直です。

    @Test
fun `個数は初出順に並ぶ`() {
    // 原著の出力: [3, 2, 1]。A が 3、C が 2、B が 1 の順
    assertEquals(listOf(3, 2, 1), counts(ELEMENTS))
}

    順序が数学的な結果を変えるわけではありませんが、 浮動小数点の丸めまで原著と揃えるには必要 でした。

    整数除算に落ちないよう気をつける¶

    ジニ不純度の式には割り算が入ります。

    fun gini(elements: List<String>): Double {
    val classCounts = counts(elements)
    val n = classCounts.sum()
    return 1.0 - classCounts.sumOf { count ->
        count.toDouble() * count / (n.toDouble() * n)
    }
}

    count * count / (n * n) と書くと すべて Int なので整数除算 になり、 ほとんどの場合 0 になります。1.0 - 0 = 1.0 が返り、 「常に不純度 1」という壊れ方をします。

    Python 版は from __future__ import division を書いていた時代の名残で 原著にもその行がありますが、Python 3 では / が常に実数除算です。 Kotlin にはその保証がない ので、toDouble() を明示します。

    sumOf はラムダの戻り値型で多重定義が解決されるので、 count.toDouble() と書いた時点で Double を返す sumOf が選ばれます。

    Multik でベクトル演算を書く¶

    エントロピーは原著が np.log2 と np.dot を使う箇所です。 Multik（NumPy に相当）でその形を保ちました。

    fun entropy(elements: List<String>): Double {
    if (elements.isEmpty()) return 0.0

    val classCounts = counts(elements)
    val n = classCounts.sum()
    val proportions = mk.ndarray(classCounts.map { 1.0 / n * it })
    val logs = proportions.map { log2(it) }
    return -(logs * proportions).sum()
}

/** 2 を底とする対数。Multik には要素ごとの log2 が無いので自分で書く */
private fun log2(x: Double): Double = ln(x) / ln(2.0)

    Multik に要素ごとの log2 がありません。 NumPy の np.log2 に相当する 関数が無いので、map で 1 要素ずつ変換します。

    (logs * proportions).sum() が np.dot にあたります。 Multik の * は要素ごとの積なので、合計を取って内積にします。

    正直に言えば、この規模なら zip と sumOf で書くほうが短いです。

    // Multik を使わない書き方
classCounts.map { 1.0 / n * it }.sumOf { -log2(it) * it }

    それでも Multik を使ったのは、原著が「ベクトルへの一括演算」として 書いている形を保つため です。この連載はライブラリの対応を見るのが目的なので、 NumPy の役割を Multik が担うことを示すほうを優先しました。

    空のリストの扱いが 2 つで違う¶

    Python 版 と同じ発見です。

    @Test
fun `空のリストの扱いは2つで違う`() {
    // 原著はエントロピーだけ明示的に 0 を返す。ジニは 1 - 0 で 1 になる
    assertEquals(1.0, gini(emptyList()), 1e-15)
    assertEquals(0.0, entropy(emptyList()), 1e-15)
}

    Kotlin では gini(emptyList()) の中で n = 0 になりますが、 sumOf のラムダが 1 度も呼ばれないのでゼロ除算は起きません。 Python と同じ理由で、偶然うまくいっています。

    entropy のほうは if (elements.isEmpty()) return 0.0 を明示します。 これを外すと 1.0 / 0 が Infinity になり、log2(Infinity) から NaN が伝播します。 Python なら警告が出るところ、Kotlin は黙って NaN を返す ので、 明示的な早期リターンの重要度はむしろ高いです。

    関数参照で重み付けをまとめる¶

    ジニとエントロピーで同じ重み付けをするので、関数を引数に取る形にしました。

    /** 左右の不純度を、要素数で重み付けして平均する */
private fun weighted(
    impurity: (List<String>) -> Double,
    left: List<String>,
    right: List<String>,
    total: Int,
): Double = 1.0 / total * (impurity(left) * left.size + impurity(right) * right.size)

    呼び出し側は関数参照 ::gini / ::entropy を渡します。

    weightedGini = weighted(::gini, left, right, elements.size),
weightedEntropy = weighted(::entropy, left, right, elements.size),

    原著は同じ式を 2 回書いていました。 (List<String>) -> Double という型が「不純度を測る関数」を表している ので、 将来ほかの指標（誤分類率など）を足すときもここは変わりません。

    結果は原著と完全一致する¶

    @Test
fun `各分割の重み付き不純度は原著と同じ`() {
    // 原著のセル出力をそのまま期待値にしている
    val expected = listOf(
        Triple(0, 0.6111111111111112, 1.4591479170272446),
        Triple(1, 0.5333333333333333, 1.268273412406135),
        Triple(2, 0.41666666666666663, 1.0),
        Triple(3, 0.2222222222222222, 0.4591479170272448),
        Triple(4, 0.41666666666666663, 0.8741854163060886),
        Triple(5, 0.4666666666666667, 1.1424588287122237),
    )
    val splits = splitImpurities()

    for ((index, expectedGini, expectedEntropy) in expected) {
        assertEquals(expectedGini, splits[index].weightedGini, 1e-15, "gini at $index")
        assertEquals(expectedEntropy, splits[index].weightedEntropy, 1e-15, "entropy at $index")
    }
}

    Triple で 3 つ組を並べ、分解宣言で受けます。 失敗時にどの分割かが分かるよう、メッセージに添字を入れました。

    分割 0 のエントロピーが 1.4591479170272446 と、 entropy(ELEMENTS) の 1.4591479170272448 から最下位ビットだけずれるところも Kotlin で同じように再現されました。丸めの入り方が同じだからです。

    この章で Kotlin が効いた場面・効かなかった場面¶

    場面 評価
    数え上げ 効いた — groupingBy().eachCount() が 1 行で初出順を保つ
    重み付け 効いた — 関数型 (List<String>) -> Double で共通化できる
    テストの並べ方 効いた — Triple と分解宣言で表形式に書ける
    整数除算 効かなかった — toDouble() を忘れると静かに壊れる
    log2 効かなかった — Multik に要素ごとの log2 が無い
    NaN の扱い 効かなかった — 空のリストで警告が出ず黙って NaN が伝播する
