    #07 ナイーブベイズでスパム判定（Kotlin）¶

    原著ノートブック: Chapter_08_Naive_Bayes/Coding_naive_Bayes.ipynb

    メール 5728 通からスパム判定器を作ります。 この回だけ、原著が scikit-learn を使いません。 pandas と辞書だけで書かれています。

    ライブラリに依存しないぶん Kotlin への移植は素直で、 原著のすべての数値を 16 桁まで再現できました。 その代わり、Python では意識しなかった 2 つのこと — 文字列分割と多倍長整数 — が表に出ます。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-kotlin-lib/src/main/kotlin/lib/Nb07NaiveBayes.kt
    テスト apps/grokking-ml-kotlin-lib/src/test/kotlin/lib/Nb07NaiveBayesTest.kt
    実行 ./gradlew test --tests Nb07NaiveBayesTest

    split() の意味が Python と違う¶

    原著は text.lower().split() と書いています。Python の str.split() は 引数なしだと空白の連続をまとめて区切り、空文字列を返しません。

    Kotlin の String.split(" ") は違います。区切り文字が連続すると空文字列が残ります。

    "win   lottery".split(" ")   // ["win", "", "", "lottery"]

    メール本文には空白が 2 つ以上並ぶ箇所が普通にあるので、 そのまま移植すると 空文字列が語彙に入ります。

    /**
 * メール本文を、重複を除いた小文字の単語集合にする。
 *
 * 原著は `list(set(text.lower().split()))`。**同じ単語が何度出ても 1 回** と
 * 数えるのがこの実装の前提である。
 *
 * `split()` は Python では空白の連続をまとめて区切るが、Kotlin の
 * `String.split(" ")` は空文字列を残す。`Regex("\\s+")` で分けたうえで
 * 空文字列を落とす必要がある。
 */
fun processEmail(text: String): Set<String> =
    text.lowercase().split(WHITESPACE).filter { it.isNotEmpty() }.toSet()

private val WHITESPACE = Regex("""\s+""")

    Regex("\\s+") で分けても、先頭が空白なら空文字列が 1 つ残ります。 filter { it.isNotEmpty() } が要る理由です。テストで固定しました。

    @Test
fun `空白の連続はまとめて区切る`() {
    // Python の split() は空白の連続をまとめるが、Kotlin の split(" ") は
    // 空文字列を残す。Regex で分けて空文字列を落とす必要がある
    assertEquals(setOf("win", "lottery"), processEmail("win   lottery"))
}

    「同じ名前のメソッドが同じ意味とは限らない」典型例でした。 これを外すと語彙が変わり、lottery の出現数が原著と合わなくなります。

    戻り値を Set にする¶

    原著は list(set(...)) と、集合を作ってからリストに戻しています。 Kotlin では Set<String> のまま返しました。

    fun processEmail(text: String): Set<String>

    型で「重複がない」ことが表せます。 原著が list() に戻しているのは pandas の列に入れるためで、アルゴリズム上の意味はありません。 戻す理由が無いので戻していません。

    ラプラス平滑化を data class の既定値で表す¶

    /**
 * ある単語が、スパムとハムそれぞれ何通に現れたか。
 *
 * 原著は 1 から数え始める。ラプラス平滑化にあたり、
 * 「一度も見ていない側」の確率が 0 になるのを防ぐ。
 */
data class WordCounts(var spam: Int = 1, var ham: Int = 1)

    既定値を 1 にしておけば、WordCounts() と書くだけでラプラス平滑化が効きます。 原著の {'spam': 1, 'ham': 1} という辞書リテラルより、意図が型に載ります。

    数える側も 1 行です。

    val counts = words.getOrPut(word) { WordCounts() }
if (emails.spam[i] == 1) counts.spam += 1 else counts.ham += 1

    getOrPut が原著の「無ければ作って、必ず数える」をそのまま表します。 原著が if を 2 つ並べて実現していたところです。

    var を使っているのは、5728 通 × 数百語のループで copy() を呼び続けるのが無駄だからです。 WordCounts は学習中しか変わらないので、可変にしても外に漏れません。

    多倍長整数が必要になる¶

    ここが Kotlin でいちばん手が入った箇所です。

    原著の最終行はこうです。

    prod_spams = np.compat.long(np.prod(spams)*num_spam)
prod_hams = np.compat.long(np.prod(hams)*num_ham)
return prod_spams/(prod_spams + prod_hams)

    np.compat.long は Python 3 では int そのもので、小数点以下を切り捨てます。 そして Python の int は 多倍長 です。prod_spams は 10²⁰ を超えることがあり、 Long（最大約 9.2 × 10¹⁸）では溢れます。

    さらに Python は int / int を 多倍長のまま計算してから float にします。 先に Double へ落とすと桁が落ちます。

    // 原著の np.compat.long と同じ切り捨て。値は 10^20 を超えることがあるので
// Long では溢れる。Python の int は多倍長なので BigInteger で受ける
val truncatedSpams = BigDecimal(productSpams).toBigInteger()
val truncatedHams = BigDecimal(productHams).toBigInteger()

// Python は int / int を多倍長のまま計算してから float にする。
// ここで toDouble() してから割ると桁が落ちるので、BigDecimal で割る
return truncatedSpams.toBigDecimal()
    .divide((truncatedSpams + truncatedHams).toBigDecimal(), MathContext.DECIMAL128)
    .toDouble()

    MathContext.DECIMAL64（有効 16 桁）で試したところ、 lottery sale が 0.963814499204869 になり、原著の 0.9638144992048691 と 最後の 1 桁だけ 違いました。DECIMAL128（有効 34 桁）にして一致します。

    Python の int が黙ってやっていたことを、Kotlin では 3 行に分けて書く ことになります。 BigDecimal(double) で切り捨て、BigInteger で保持し、BigDecimal で割る。 それぞれに理由があるので、コメントを付けました。

    結果は原著と完全一致する¶

    @Test
fun `メール全体の予測は原著と同じ`() {
    if (!emailsAvailable()) return
    val model = train(loadEmails())

    // 原著のセル出力をそのまま期待値にしている
    val expected = listOf(
        "lottery sale" to 0.9638144992048691,
        "Hi mom how are you" to 0.12554358867164464,
        "meet me at the lobby of the hotel at nine am" to 6.964603508395961e-05,
        "enter the lottery to win three million dollars" to 0.9995234218677428,
        "buy cheap lottery easy money now" to 0.999973472265966,
        "Grokking Machine Learning by Luis Serrano" to 0.4197107645488719,
        "asdfgh" to 0.2388268156424581,
    )

    for ((email, value) in expected) {
        assertEquals(value, predictNaiveBayes(model, email), value * 1e-14, email)
    }
}

    assertEquals(expected, actual, delta, message) の第 4 引数にメールを渡しているので、 落ちたときにどの入力かがすぐ分かります。 許容誤差を value * 1e-14 と相対で書いているのは、 期待値が 6.96e-05 から 0.9999 まで 4 桁も違うためです。 絶対値で固定すると、小さい値のテストが甘くなります。

    単語ごとの出現数も一致します。

    assertEquals(WordCounts(spam = 9, ham = 1), model.words["lottery"])
assertEquals(WordCounts(spam = 39, ham = 42), model.words["sale"])

    data class なので構造的等価性でそのまま比べられます。 #04 では配列を持たせて equals を自前で書く羽目になりましたが、 こちらは Int を 2 つ持つだけなので何もしなくて済みます。

    この章で Kotlin が効いた場面・効かなかった場面¶

    場面 評価
    ラプラス平滑化 効いた — data class の既定値で意図が型に載る
    単語集合 効いた — 戻り値を Set にすれば重複がないことが型で分かる
    数え上げ 効いた — getOrPut が原著の 2 つの if を 1 行にする
    出現数の比較 効いた — data class の構造的等価性
    split() 効かなかった — Python と意味が違い、空文字列が混ざる
    多倍長整数 効かなかった — BigDecimal / BigInteger を経由する 3 行が要る

    ライブラリの差ではなく 言語の標準ライブラリの差 が出た回でした。 split() の挙動と整数の多倍長性は、移植のときに毎回確認すべき項目です。
