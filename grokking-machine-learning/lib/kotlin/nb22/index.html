    #22 タイタニックで通しの機械学習（Kotlin）¶

    原著ノートブック: Chapter_13_End_to_end_example/End_to_end_example.ipynb

    タイタニックの生存予測を、前処理からモデル選択まで通しでやる回です。 本の最終章で、これまでのアルゴリズムが一堂に会します。 シリーズ最終回 でもあります。

    この回で分かったのは、移植で難しいのは学習ではなく前処理と分割 だということでした。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-kotlin-lib/src/main/kotlin/lib/Nb22TitanicEndToEnd.kt
    テスト apps/grokking-ml-kotlin-lib/src/test/kotlin/lib/Nb22TitanicEndToEndTest.kt
    実行 ./gradlew test --tests "lib.Nb22*"

    欠損を型で表す¶

    pandas は欠損を NaN で表しますが、Kotlin では null 許容型 が使えます。

        data class Passenger(
        val survived: Int,
        val pclass: Int,
        val sex: String,
        val age: Double?,
        val sibSp: Int,
        val parch: Int,
        val fare: Double,
        val embarked: String?,
    )

    Double? と String? が「欠損しうる列」で、それ以外は欠損しません。 型を見れば、どの列を埋める必要があるかが分かります。

    埋めるほうも ?: 1 つで書けます。

        fun clean(raw: List<Passenger>): List<Passenger> {
        val median = medianAge(raw)
        return raw.map { it.copy(age = it.age ?: median, embarked = it.embarked ?: "U") }
    }

    そして 埋めた後の型も Double? のまま です。ここが少し歯がゆいところで、 featuresOf では passenger.age!! と書く必要があります。 「clean を通した後は非 null」を型で表すには、別の型を用意することになります。 今回は行数が増えるほうを避けました。

    Kotlin DataFrame の型推論に足をすくわれる¶

    最初、Embarked の欠損が 891 件（= 全件）と出ました。

    val embarked = frame.getColumn("Embarked").toList().map { it as? String }

    as? String がすべて失敗していたのです。 Kotlin DataFrame は 1 文字の値ばかりの列を Char などに推論することがあります。

            // Kotlin DataFrame は文字列列を Char 等に推論することがある。
        // 型で受けずに文字列化してから空を欠損とみなす
        val embarked = frame.getColumn("Embarked").toList().map { it?.toString()?.ifBlank { null } }

    as? は 失敗しても例外を投げず null を返す ので、 「全部欠損」という結果が静かに出ました。 as にしていれば ClassCastException で即座に気付けたはずです。

    null 安全のための構文が、かえって間違いを隠した 例です。 missingCounts を原著と突き合わせるテストを書いていたから見つかりました。

    分割の件数を合わせるには ceil が要る¶

    最初の実装では 535 / 178 / 178 になりました。原著は 534 / 178 / 179 です。

            // 原著は 6:4 に切り、その 4 をさらに半分ずつにする。
        // scikit-learn は `test_size` の側を **切り上げる**（ceil）ので、
        // 891 -> 534 / 357、357 -> 178 / 179 になる
        private val restSize = Math.ceil(prepared.size * 0.4).toInt()
        private val trainSize = prepared.size - restSize
        private val testSize = Math.ceil(restSize * 0.5).toInt()
        private val validationSize = restSize - testSize

    891 × 0.4 = 356.4 を 切り上げて 357。だから訓練は 534。 357 × 0.5 = 178.5 を 切り上げて 179。だから検証は 178。

    余りは必ずテスト側に行く という規則です。 「だいたい 6:2:2」で済ませていたら、この 1 件の差は永久に残りました。

        @Test
    fun `分割の件数は原著と一致する`() {
        // 原著の出力: 534 / 178 / 179。
        // scikit-learn は test_size の側を切り上げる
        assertEquals(534, split.train.second.size)
        assertEquals(178, split.validation.second.size)
        assertEquals(179, split.test.second.size)
    }

    ただし 中身は一致しません。

         * scikit-learn の `train_test_split(random_state=100)` は
     * **メルセンヌツイスタの並べ替え** を使うので、JVM では同じ分割を作れない。

    #17 で見たとおり、乱数列は言語をまたげません。 だからモデルの成績も一致しません。そこは最初から諦めて、 前処理と件数の再現に集中しました。

    Smile に GaussianNB が無い¶

    Smile の NaiveBayes は多項分布とベルヌーイ分布しか持ちません。 連続値を扱う scikit-learn の GaussianNB に当たるものがないので、自前で書きました。

    書いたら 正解率 0.38 でした。多数派を答える 0.67 より悪い値です。

    原因は分散の下駄でした。

            // scikit-learn の `var_smoothing`。**全特徴量の最大分散 × 1e-9** を足す。
        // one-hot の列は分散がごく小さいので、固定値 1e-9 を足すだけでは足りない。
        // それをやると正解率が 0.38 まで落ちた（多数派を答えるより悪い）
        val smoothing = 1e-9 * (0 until FEATURE_NAMES.size).maxOf { column -> ... }

    one-hot の列は 0 か 1 しか取らないので、片方のクラスに偏ると分散がほぼ 0 になります。 そこに固定値 1e-9 を足しても足りず、 -(x-μ)²/(2σ²) が巨大な負の値になって 1 つの列が全体を支配します。

    scikit-learn の var_smoothing は 全特徴量の最大分散に比例 させます。 Fare の分散が大きいので、下駄も相応に大きくなり、崩れません。

    これを直したら 0.71 になりました。 既定値の 1e-9 という数字ではなく、「何に比例させるか」が本質 でした。

    Smile は 7 つとも揃っている¶

            return linkedMapOf(
            "Logistic regression" to fromVector(smile.classification.LogisticRegression.binomial(trainX, trainY)),
            "Decision tree" to fromFrame(...),
            "Naive Bayes" to naiveBayesPredictor(trainX, trainY),
            "SVM" to svmPredictor(trainX, signed),
            "Random forest" to fromFrame(...),
            "Gradient boosting" to fromFrame(...),
            "AdaBoost" to fromFrame(...),
        )

    素朴ベイズ以外は Smile がそのまま持っています。 linkedMapOf にしているのは 順序を原著と同じに保つ ためです。

    ただしモデルによって入力の形が違います。

    モデル 入力
    ロジスティック回帰・SVM Array<DoubleArray>（生の行列）
    決定木・ランダムフォレスト・ブースティング DataFrame + Formula（列名が要る） 
            fun fromFrame(model: smile.classification.Classifier<smile.data.Tuple>):
            (Array<DoubleArray>) -> IntArray = { rows -> ... }

        fun fromVector(model: smile.classification.Classifier<DoubleArray>):
            (Array<DoubleArray>) -> IntArray = { rows -> ... }

    予測関数を返す形に揃える ことで、呼び出し側は違いを気にせずに済みます。 Kotlin の関数型が効く場面です。

    1 位は主張できない¶

        @Test
    fun `勾配ブースティングは上位に入る`() {
        // 原著は勾配ブースティングが単独 1 位。こちらは実行のたびに
        // ランダムフォレストと入れ替わる（[#20][Nb20EnsembleSpam] で見たとおり
        // Smile の RandomForest は種を固定しても結果が変わる）。
        // **1 位を主張できないので、上位 3 つに入ることを確かめる**
        val top3 = scores.entries.sortedByDescending { it.value }.take(3).map { it.key }

        assertTrue("Gradient boosting" in top3, "上位 3 つ: $top3")
    }

    最初は「勾配ブースティングが 1 位」と書いてテストが落ちました。 #20 で見つけた「Smile の RandomForest は種を固定しても変わる」が ここでも効いています。

    過去の回で見つけた性質が、最終回でテストを落とす。 シリーズを通しで書いていると、こういう繋がりが出てきます。

    まとめ¶

    項目 原著と一致するか
    891 行・342 人生存・欠損数 完全一致
    年齢の中央値 28.0 完全一致
    特徴量 20 列（Python の 21 列 − ラベル） 完全一致
    分割の件数（534 / 178 / 179） 完全一致
    分割の中身 一致しない（乱数列が言語をまたげない）
    モデルの成績 一致しない（分割が違うため）
    モデルの順位 ほぼ一致（勾配ブースティングが上位）
