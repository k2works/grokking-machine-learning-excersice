    #21 勾配ブースティングと XGBoost（Kotlin）¶

    原著ノートブック: Chapter_12_Ensemble_Methods/Gradient_boosting_and_XGBoost.ipynb

    8 人の年齢から「週に何日アプリを使うか」を当てる回帰の回です。

    そして このシリーズで Smile が scikit-learn と最もよく一致した回 でもあります。 勾配ブースティングの予測が 15 桁一致しました。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-kotlin-lib/src/main/kotlin/lib/Nb21GradientBoosting.kt
    テスト apps/grokking-ml-kotlin-lib/src/test/kotlin/lib/Nb21GradientBoostingTest.kt
    実行 ./gradlew test --tests "lib.Nb21*"

    勾配ブースティングが 15 桁一致する¶

        @Test
    fun `勾配ブースティングの予測は原著と15桁一致する`() {
        // 原著の出力
        //   array([6.87466667, 5.11466667, 6.71466667, 1.43466667, 1.43466667,
        //          1.43466667, 4.896     , 4.096     ])
        val expected = listOf(
            6.87466667, 5.11466667, 6.71466667, 1.43466667,
            1.43466667, 1.43466667, 4.896, 4.096,
        )

        predict(fitGradientBoosting()).forEachIndexed { index, value ->
            assertEquals(expected[index], value, 5e-9, "person $index")
        }
    }

    実測値は 6.874666666666666。原著の印刷 6.87466667 と、 印刷された桁すべてが一致します。

    #19 の SVM や #20 のランダムフォレストが これほど揃わなかったのに、なぜここは合うのか。

    乱数が入らないからです。

    • 勾配ブースティングは木を順番に育てる（並列化できない）
    • subsample = 1.0 なので部分標本を取らない
    • 回帰木の分割は、8 点しかなければ一意に決まる

    アルゴリズムが決定的なら、ライブラリが違っても同じ答えになります。 逆に言えば、これまで合わなかったのはすべて乱数か近似解法のせいでした。

    引数の並びを合わせるのに手間取る¶

            // loss, ntrees, maxDepth, maxNodes, nodeSize, shrinkage, subsample。
        // scikit-learn の既定は二乗誤差なので Loss.ls() を選ぶ
        return GradientTreeBoost.fit(
            formula, frame(), smile.base.cart.Loss.ls(),
            nEstimators, MAX_DEPTH + 1, 10000, 1, LEARNING_RATE, 1.0,
        )

    Smile の GradientTreeBoost.fit は 9 引数の版しか使えません。 最初 7 引数で呼んで、こう言われました。

    None of the following candidates is applicable:
static fun fit(p0: Formula!, p1: DataFrame!): GradientTreeBoost!
static fun fit(p0: Formula!, p1: DataFrame!, p2: Properties!): GradientTreeBoost!
static fun fit(p0: Formula!, p1: DataFrame!, p2: Loss!, p3: Int, ...): GradientTreeBoost!

    候補を並べてくれるので、何が足りないかがすぐ分かります。 Loss を渡し忘れていました。scikit-learn の既定は二乗誤差なので Loss.ls() です。

    Smile の API は「全部渡すか、何も渡さないか」の二択になりがちです。 #09・#11・#12 でも同じことをしています。 名前付き引数で書けない（Java の API なので） のがつらいところで、 10000, 1, 0.8, 1.0 という並びが何を意味するかはコメントに頼るしかありません。

    深さは #10 の対応どおり scikit-learn より 1 大きく 渡します。

    後半はライブラリを使わない¶

    XGBoost の類似度スコアの計算は、原著が自分で書いた関数です。 JVM に XGBoost4J はありますが、ここで必要なのは掛け算と割り算だけ です。

        fun similarityScore(values: DoubleArray, lambda: Double = 0.0): Double {
        if (values.isEmpty()) return 0.0
        val total = values.sum()
        return total * total / (values.size + lambda)
    }

    values.size + lambda で Int + Double の混在が自動で Double になります。 #12 で踏んだ整数除算の罠は、ここでは起きません （lambda が Double なので式全体が Double に持ち上がる）。

    もし lambda を Int にしていたら total * total / Int となり、 total が Double なので結局 Double 除算になります。 この式はたまたま安全でした。

    手計算が XGBoost の gain と一致する¶

        @Test
    fun `分割のスコアはXGBoostのgainと一致する`() {
        // 原著の木のダンプ: 0:[f0<35] ... gain=14.291667
        // 手で計算した最良スコアが、XGBoost が出す gain とぴたり合う
        assertEquals(14.291667, findBestSplit(xgboostResiduals(), 3.0).score, 1e-6)
    }

    原著が別々のセルに印刷している 2 つの数字（手計算の 14.291666666666666 と、 木のダンプの gain=14.291667）が同じものだと確かめました。 原著自身はこの一致に触れていません。

    原著の find_best_split にはバグがある¶

        @Test
    fun `原著が返す7という値は最後の切れ目のスコア`() {
        // 右の木 [-3,-2,-3,1,0] の最後の切れ目は [-3,-2,-3,1] / [0] で、
        // (-7)^2/(4+3) + 0^2/(1+3) = 7.0。これが原著の返り値 7.0 の正体
        val right = findBestSplit(xgboostResiduals(), 3.0).right
        val scores = splitScores(right, 3.0)

        assertEquals(7.0, scores.last(), 1e-15)
        assertTrue(scores.last() < scores.max())
    }

    原著は best_score ではなく new_score（最後の切れ目のスコア）を返しています。 詳しくは Python 版 に書きました。

    移植するときは 原著をそのまま写すか、直すか を選ぶことになります。 ここは「返り値が使われていない・本文の結論も正しい」ので直しました。 その判断を KDoc に残しています。

         * なお **原著の実装にはバグがある。** 返り値の 3 つ目に `best_score`
     * ではなく `new_score`（ループの最後の切れ目のスコア）を渡している。
     * ここでは最良のスコアを返す。詳しくは記事を参照。

    #05 の alternate_log_loss は「原著どおり写したうえで、 正しい式も並べて示す」ことにしました。 扱いが違うのは、あちらが本文の説明そのものに関わるからです。

    配列を持つ data class は equals を書く¶

        /** 分割の結果 */
    data class Split(val left: DoubleArray, val right: DoubleArray, val score: Double) {
        override fun equals(other: Any?): Boolean =
            other is Split &&
                left.contentEquals(other.left) &&
                right.contentEquals(other.right) &&
                score == other.score

        override fun hashCode(): Int =
            (left.contentHashCode() * 31 + right.contentHashCode()) * 31 + score.hashCode()
    }

    このシリーズで 4 度目です（#04・#05・#10・#21）。 data class に配列を入れると equals が参照比較になり、 テストが謎の失敗をします。

    もう反射的に書くようになりました。 F# のレコードは配列を入れても構造比較になるので、この手当ては要りません。

    まとめ¶

    項目 原著と一致するか
    勾配ブースティングの予測 15 桁一致
    類似度スコア・切れ目ごとのスコア 完全一致
    最良の分割（左右の木） 完全一致
    手計算のスコアと XGBoost の gain 一致（原著は触れていない）
    find_best_split の返すスコア 原著が間違っている
    XGBoost 本体 使わない（後半は四則演算だけ）
