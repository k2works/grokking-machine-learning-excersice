    #10 決定木の境界を図示する（Kotlin）¶

    原著ノートブック: Chapter_09_Decision_Trees/Graphical_example.ipynb

    2 次元の 12 点を決定木で分け、決定境界を見る回です。 原著はジニ・エントロピー・深さ 1 の 3 つのモデルを並べます。

    Smile の決定木は scikit-learn とまったく同じ 3 つの分割 を選びました。 一方で 深さの数え方が 1 つずれている ことが分かり、そこが今回の発見です。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-kotlin-lib/src/main/kotlin/lib/Nb10DecisionTreeBoundary.kt
    テスト apps/grokking-ml-kotlin-lib/src/test/kotlin/lib/Nb10DecisionTreeBoundaryTest.kt
    実行 ./gradlew test --tests Nb10DecisionTreeBoundaryTest

    分割の基準は SplitRule で選ぶ¶

    scikit-learn の criterion='gini' / 'entropy' にあたるものが、 Smile では列挙型 SplitRule です。

    /**
 * 決定木を学習する。原著は 3 通りの設定で呼び分けている。
 *
 * Smile は分割の基準を [SplitRule] で選ぶ。`GINI` と `ENTROPY` があり、
 * scikit-learn の `criterion='gini'` / `'entropy'` に対応する。
 */
fun fit(rule: SplitRule = SplitRule.GINI, maxDepth: Int = 20): DecisionTree =
    DecisionTree.fit(Formula.lhs("y"), frame(), rule, maxDepth, 100, 1)

    文字列ではなく列挙型 なので、綴りを間違えるとコンパイルエラーになります。 scikit-learn は criterion='ginni' と書いても実行時まで気づけません。 #03 で enum class が効いたのと同じ利点です。

    分割は scikit-learn と完全一致¶

    @Test
fun `木は scikit-learn と同じ3つの条件で分割する`() {
    // scikit-learn も x_0 <= 5.0 / x_1 <= 8.0 / x_1 <= 2.5 を選ぶ
    assertEquals(
        listOf(Split("x_0", 5.0), Split("x_1", 8.0), Split("x_1", 2.5)),
        splitConditions(fit()),
    )
}

    しきい値まで一致しました。 #09 では 2 段目の分割が違いましたが、あれは同点だったからです。 同点が無ければ、独立に実装されたライブラリでも同じ木に到達します。

    ジニとエントロピーが同じ木になる点も一致します。

    @Test
fun `ジニとエントロピーは同じ木になる`() {
    // 分割の候補に同点が無いので、どちらの指標でも同じ順序で選ばれる。
    // #09 では同点があって木の形が変わったのと対照的
    assertEquals(
        splitConditions(fit(SplitRule.GINI)),
        splitConditions(fit(SplitRule.ENTROPY)),
    )
}

    深さの数え方が 1 つずれている¶

    原著の DecisionTreeClassifier(max_depth=1) は「1 本の直線」を作ります。 同じつもりで Smile に maxDepth = 1 を渡すと、分割が 1 つも入りません。

    @Test
fun `Smile の深さは根を1と数える`() {
    // scikit-learn は根を深さ 0 と数えるので max_depth=1 で分割が 1 つ入る。
    // Smile は根を 1 と数えるため maxDepth=1 では分割が入らない
    assertEquals(emptyList(), splitConditions(fit(SplitRule.GINI, maxDepth = 1)))
    assertEquals(0.5, accuracy(fit(SplitRule.GINI, maxDepth = 1)), 1e-12)
}

    maxDepth を 1 から 4 まで変えて測るとはっきりします。

    Smile の maxDepth 分割の数 正解率 scikit-learn の相当値
    1 0 0.5 max_depth=0
    2 1 0.8333 max_depth=1
    3 3 1.0 max_depth=2
    4 3 1.0 max_depth=3（変化なし）

    scikit-learn は根を深さ 0、Smile は根を深さ 1 と数えます。

    これは静かに間違える種類の違いです。maxDepth = 1 は例外を投げず、 「木ができたが 1 つも分割していない」モデルを返します。 正解率が 0.5 なのを見るまで気づけません。

    変換する関数を用意して、意図を名前で示しました。

    /**
 * scikit-learn の `max_depth` と同じ意味で深さを制限する。
 *
 * **深さの数え方が 1 つずれている。** scikit-learn は根を深さ 0 と数えるので
 * `max_depth=1` で分割が 1 つ入るが、Smile は根を深さ 1 と数えるため
 * `maxDepth=1` では分割が 1 つも入らない（根だけの木になり正解率 0.5）。
 * 同じ木を得るには 1 を足す。
 */
fun fitWithSklearnDepth(depth: Int, rule: SplitRule = SplitRule.GINI): DecisionTree =
    fit(rule, depth + 1)

    これで原著と同じ 0.8333 が得られます。

    @Test
fun `深さ1の木は12点中10点しか当てられない`() {
    // 原著と同じ 0.8333。直線 1 本では 2 点を取り違える
    assertEquals(10.0 / 12.0, accuracy(fitWithSklearnDepth(1)), 1e-12)
}

    np.arange を自分で書く¶

    原著の格子は np.arange(min - 1, max + 1, 0.2) で作られます。 Kotlin に相当するものはありません。

    /** NumPy の `np.arange` と同じく、終端を含まない等差数列を作る */
fun arange(start: Double, stop: Double, step: Double): DoubleArray {
    val count = Math.ceil((stop - start) / step).toInt()
    return DoubleArray(count) { start + it * step }
}

    Kotlin の範囲式 0.0..10.0 step 0.2 は Double に使えません （step は整数の範囲にしか定義されていません）。 generateSequence(0.0) { it + 0.2 }.takeWhile { it < 10.0 } でも書けますが、 足し算を繰り返すと誤差が積もります。

    start + it * step と掛け算にすれば、誤差が積もりません。 np.arange も同じ計算をしています。だから 5.2 という値が Python と Kotlin で厳密に一致します。

    @Test
fun `arange は終端を含まない`() {
    // NumPy の np.arange と同じ挙動にする
    assertEquals(listOf(0.0, 0.5, 1.0, 1.5), arange(0.0, 2.0, 0.5).toList())
}

    格子と境界が一致する¶

    @Test
fun `格子は原著と同じ大きさになる`() {
    // x は 0 から 10 まで、y は 0 から 11 まで、刻みは 0.2。
    // 終端を含まないので 50 × 55 になる
    val grid = decisionGrid(fit())

    assertEquals(0.2, PLOT_STEP)
    assertEquals(0.0, grid.xValues[0], 1e-12)
    assertEquals(0.0, grid.yValues[0], 1e-12)
    assertEquals(55, grid.rowCount)
    assertEquals(50, grid.columnCount)
}

    @Test
fun `境界は軸に平行になる`() {
    // 決定木の境界は長方形の集まりなので、予測が変わる x 座標は
    // 分割しきい値の直後だけに限られる
    val changes = boundaryColumns(decisionGrid(fit()))

    assertEquals(1, changes.size)
    assertEquals(5.2, changes[0], 1e-9)
}

    Python と同じ 5.2 で境界が現れました。 格子の作り方・木の分割・ 予測のすべてが揃っていないと、この 1 行は通りません。

    配列を持つ data class の equals¶

    DecisionGrid は配列を 3 つ持ちます。#04 と同じく、 data class が生成する equals は配列を参照比較するので自前で書きました。

    override fun equals(other: Any?): Boolean =
    other is DecisionGrid &&
        xValues.contentEquals(other.xValues) &&
        yValues.contentEquals(other.yValues) &&
        predictions.contentDeepEquals(other.predictions)

    predictions は Array<IntArray> の 入れ子 なので、 contentEquals ではなく contentDeepEquals が要ります。 1 段目だけ比較しても、中身の IntArray は参照比較のままです。

    これで格子どうしを 1 行で比較できます。

    @Test
fun `Smile は同じ入力に対して同じ格子を作る`() {
    assertEquals(decisionGrid(fit()), decisionGrid(fit()))
}

    この章で Kotlin が効いた場面・効かなかった場面¶

    場面 評価
    分割の基準 効いた — SplitRule の列挙型で綴りミスが止まる
    木の再現性 効いた — 決定的で scikit-learn と同じ分割になる
    格子の比較 効いた — contentDeepEquals で入れ子配列を 1 行比較
    深さの数え方 効かなかった — 根を 1 と数え、静かに違う木ができる
    np.arange 効かなかった — Double の範囲式が無く自前実装
    data class + 配列 効かなかった — equals を自前で書く（3 度目）

    data class + 配列の問題は #04・#05 に続いて 3 度目です。 数値計算で Kotlin を使うなら、最初から equals を書く前提で設計する のが良さそうです。
