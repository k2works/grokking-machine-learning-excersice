    #08 ジニ不純度とエントロピーの計算（Python）¶

    原著ノートブック: Chapter_09_Decision_Trees/Gini_entropy_calculations.ipynb

    決定木の章に入ります。まずは木を作る前に、どこで分割すべきかを決める物差し — ジニ不純度とエントロピー — を手で計算します。

    NumPy しか使わない、6 要素だけの小さな回です。 そのぶん 2 つの指標の性格の違い がはっきり見えます。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-python-lib/src/grokking_ml_lib/nb08_gini_entropy.py
    テスト apps/grokking-ml-python-lib/tests/test_nb08_gini_entropy.py
    実行 uv run pytest tests/test_nb08_gini_entropy.py

    個数を数える順序が結果に効く¶

    #: 原著が使う 6 要素
ELEMENTS = ["A", "A", "A", "C", "B", "C"]


def counts(elements: list[str]) -> list[int]:
    """要素ごとの個数を、**初めて現れた順** に返す。

    原著は辞書に数えてから `[classes[e] for e in classes]` で取り出している。
    Python 3.7 以降の辞書は挿入順を保つので、結果は初出順になる。
    `['A', 'A', 'A', 'C', 'B', 'C']` なら A=3, C=2, B=1 で `[3, 2, 1]`。
    """
    classes: dict[str, int] = {}
    for element in elements:
        classes[element] = classes.get(element, 0) + 1
    return list(classes.values())

    原著の出力は [3, 2, 1] です。辞書順（A, B, C）なら [3, 1, 2] になるはずですが、 そうなりません。Python 3.7 以降の辞書が挿入順を保つためです。

    ジニ不純度もエントロピーも和なので、数学的には順序に依存しません。 それでも浮動小数点の丸めは順序で変わるので、原著の値と最下位ビットまで 突き合わせるならここを揃える必要があります。

    def test_個数は初出順に並ぶ() -> None:
    # 原著の出力: [3, 2, 1]。A が 3、C が 2、B が 1 の順
    assert counts(ELEMENTS) == [3, 2, 1]

    空のリストの扱いが 2 つで違う¶

    これがこの回のいちばんの発見でした。

    def gini(elements: list[str]) -> float:
    """ジニ不純度。1 から「同じクラスを 2 回続けて引く確率」を引いたもの。

    空のリストに対しては 1 を返す。原著は特別扱いしておらず、
    `1 - sum([])` がそのまま 1 になる。重み付けのときは要素数 0 が掛かるので
    結果に影響しない。
    """
    class_counts = counts(elements)
    n = sum(class_counts)
    return 1 - sum(count**2 / n**2 for count in class_counts)

    def entropy(elements: list[str]) -> float:
    """情報エントロピー。原著はこちらだけ空のリストを明示的に 0 にしている。

    `log2(0)` が発散するので、空を通すと NumPy の警告が出る。
    ジニ不純度が特別扱い不要だったのと対照的である。
    """
    if len(elements) == 0:
        return 0
    ...

    gini には if が無く、entropy にはあります。

    ジニ不純度は空のリストでも計算が破綻しません。 counts([]) は空のリストで、sum([]) は 0。n = 0 ですが 割り算が 1 度も実行されない ので ZeroDivisionError になりません。結果は 1 - 0 = 1 です。

    エントロピーは違います。np.log2 に空の配列を渡すこと自体は平気ですが、 比率を作る 1/n で n = 0 になり、警告が出ます。だから明示的に 0 を返します。

    def test_空のリストの扱いは2つで違う() -> None:
    # 原著はエントロピーだけ明示的に 0 を返す。ジニは 1 - sum([]) で 1 になる
    assert gini([]) == 1
    assert entropy([]) == 0

    空集合の「不純度」が 1 と 0 で食い違う のは、指標として見れば不整合です。 ただし重み付けのときに要素数 0 が掛かるので、結果には出てきません。 偶然うまくいっている箇所を、テストで明示しておきました。

    分割位置を 1 つずつずらす¶

    def split_impurities(elements: list[str] = ELEMENTS) -> list[SplitImpurity]:
    """先頭から順に分割位置をずらし、それぞれの重み付き不純度を求める。

    原著は 0 から `len(elements) - 1` まで回している。**右端では分割しない**
    ので、「左が全部・右が空」の場合は出てこない。
    """

    原著の出力を並べると、決定木が何を選ぶかが見えます。

    分割 左 | 右 重み付きジニ 重み付きエントロピー
    0 [] | AAACBC 0.6111111111111112 1.4591479170272446
    1 A | AACBC 0.5333333333333333 1.268273412406135
    2 AA | ACBC 0.41666666666666663 1.0
    3 AAA | CBC 0.2222222222222222 0.4591479170272448
    4 AAAC | BC 0.41666666666666663 0.8741854163060886
    5 AAACB | C 0.4666666666666667 1.1424588287122237

    分割 3 で両方の指標が最小になります。 A のかたまりをきれいに切り離す位置です。 決定木はこの探索を、全特徴量・全分割点について繰り返しているだけです。

    def test_最良の分割はAのかたまりを切り離す() -> None:
    # ['A', 'A', 'A'] | ['C', 'B', 'C'] で両方の指標が最小になる
    best = best_split()

    assert best.index == 3
    assert best.left == ["A", "A", "A"]
    assert best.right == ["C", "B", "C"]
    assert best.weighted_gini == pytest.approx(0.2222222222222222, rel=1e-15)

    2 つの指標が同じ分割を選ぶことも確かめました。 値のスケールは違いますが（ジニは 0〜1、エントロピーは 0〜log₂(クラス数)）、 この例では順位が同じ です。

    def test_ジニとエントロピーは同じ分割を選ぶ() -> None:
    splits = split_impurities()
    by_gini = min(splits, key=lambda split: split.weighted_gini)
    by_entropy = min(splits, key=lambda split: split.weighted_entropy)

    assert by_gini.index == by_entropy.index

    最下位ビットがずれる¶

    分割 0 は左が空なので、右がそのまま全体です。 重み付き不純度は全体の不純度と一致するはずですが、エントロピーだけ最後の桁が違います。

    値
    entropy(ELEMENTS) 1.4591479170272448
    分割 0 の重み付きエントロピー 1.4591479170272446

    原著の出力にもこの差がそのまま残っています。

    def test_分割しない場合の重み付き不純度は全体の不純度と一致する() -> None:
    # index 0 は左が空なので、右がそのまま全体になる。
    # ただしエントロピーは 1.4591479170272446 で、entropy(ELEMENTS) の
    # 1.4591479170272448 と最下位ビットだけ違う。重み付けの掛け算と割り算で
    # 丸めが 1 度多く入るため
    split = split_impurities()[0]

    assert split.weighted_gini == pytest.approx(gini(ELEMENTS), rel=1e-15)
    assert split.weighted_entropy != entropy(ELEMENTS)
    assert split.weighted_entropy == pytest.approx(entropy(ELEMENTS), rel=1e-15)

    原因は重み付けの式です。

    1 / total * (impurity(left) * len(left) + impurity(right) * len(right))

    左が空なので実質 1/6 * (entropy(全体) * 6) を計算しています。 数学的には元の値ですが、6 を掛けて 6 で割る間に丸めが 1 度余分に入ります。

    ジニ不純度のほうは一致しました。値が 0.611... と 2 の冪に近い位置にあり、 たまたま丸めが起きなかっただけです。

    「等しいはず」と「浮動小数点で等しい」は違う ということを、 != と approx の両方で書き分けました。

    まとめ¶

    項目 原著と一致するか
    個数の並び [3, 2, 1] 完全一致
    ジニ不純度・エントロピー 完全一致
    6 通りの分割の重み付き不純度 完全一致（最下位ビットのずれも含めて）

    #07 に続き、ライブラリを使わない回は完全に再現できます。 Kotlin 版・F# 版も同じで、差が出たのは 「初出順を保つ数え上げ」をどう書くか だけでした。
