    #21 勾配ブースティングと XGBoost（Python）¶

    原著ノートブック: Chapter_12_Ensemble_Methods/Gradient_boosting_and_XGBoost.ipynb

    8 人の年齢から「週に何日アプリを使うか」を当てる回帰の回です。

    • 前半は 勾配ブースティングを手で追う。弱学習器を 1 本ずつ取り出し、残差の縮み方を見る
    • 後半は XGBoost の類似度スコアを手で計算する

    このシリーズで最も数字が多く印刷される回 です。 そして、そこで 原著の実装のバグを 1 つ見つけました。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-python-lib/src/grokking_ml_lib/nb21_gradient_boosting.py
    テスト apps/grokking-ml-python-lib/tests/test_nb21_gradient_boosting.py
    実行 nix develop .#python-ml --command bash -c 'cd apps/grokking-ml-python-lib && uv run pytest tests/test_nb21_gradient_boosting.py'

    XGBoost は macOS で libomp が要るので、Nix シェル経由で実行します。

    残差の縮み方を段ごとに追う¶

    原著は学習済みモデルから弱学習器を 1 本ずつ取り出し、 「予測すべき残差 → その予測 → 新しい残差」を印刷します。

    def weak_learner_trace(model: GradientBoostingRegressor) -> list[dict]:
    """原著が段ごとに印刷する「残差 → 予測 → 新しい残差」を集める。

    原著は `predictions += preds * 0.8` と学習率を掛けて足し込み、
    `centered_labels - predictions` を次の残差にしている。
    """

    段ごとの残差がすべて一致しました。

    段 予測すべき残差
    1 [3, 1, 3, -3, -2, -3, 1, 0]
    2 [0.6, -0.6, 1.4, -0.867, 0.133, -0.867, 0.6, -0.4]
    3 [0.6, -0.6, 0.28, -0.44, 0.56, -0.44, 0.52, -0.48]
    4 [0.12, -0.12, 0.28, -0.44, 0.56, -0.44, 0.52, -0.48] 
    def test_残差は段を追うごとに小さくなる() -> None:
    # ブースティングの定義そのもの。二乗和で測る
    trace = weak_learner_trace(fit_gradient_boosting())
    magnitudes = [float(np.sum(stage["residuals"] ** 2)) for stage in trace]

    assert magnitudes == sorted(magnitudes, reverse=True)

    原著は数字を並べるだけですが、「単調に減る」は性質としてテストできます。 値が変わってもこのテストは生き残ります。

    3 段目の -7.4e-17 は「もう何も残っていない」の印¶

    原著の 3 段目の予測にこんな値が並びます。

    Predictions: [ 6.00000000e-01 -6.00000000e-01 -7.40148683e-17 -7.40148683e-17
 -7.40148683e-17 -7.40148683e-17 -7.40148683e-17 -7.40148683e-17]

    def test_3段目の予測はほとんど0になる() -> None:
    # 原著の出力に -7.40148683e-17 が並ぶ。
    # 「もう説明できるものが残っていない」を浮動小数点の誤差が示している
    trace = weak_learner_trace(fit_gradient_boosting())
    predictions = trace[2]["predictions"]

    assert predictions[0] == pytest.approx(0.6, rel=1e-12)
    assert predictions[1] == pytest.approx(-0.6, rel=1e-12)
    assert all(abs(value) < 1e-15 for value in predictions[2:])

    数学的には 0 です。 3 段目の木は 8 人のうち 2 人（最初の 2 人）にしか 意味のある値を出しておらず、残り 6 人には「何も足さない」と答えています。

    浮動小数点の誤差が残るので == 0 では書けません。 < 1e-15 としました。「0 に等しい」ではなく「0 とみなせる」 をテストしています。

    similarity_score は和の 2 乗¶

    後半は XGBoost の内部計算です。

    def similarity_score(values, lam: float = 0.0) -> float:
    """XGBoost の類似度スコア。原著の実装をそのまま写した。

    `sum(l)**2 / (len(l) + lam)`。**分子は和の 2 乗であって
    2 乗の和ではない。** だから符号がばらけるほど値が小さくなり、
    「似ている点が集まっているか」の尺度になる。
    """

    def test_類似度スコアは和の2乗を使う() -> None:
    # sum(l)**2 / (len(l) + lam)。2 乗の和ではない
    assert similarity_score([3.0], 3) == pytest.approx(2.25, rel=1e-15)
    assert similarity_score([3.0, 1.0], 3) == pytest.approx(3.2, rel=1e-15)
    # 符号が打ち消し合うと 0 になる
    assert similarity_score([3.0, -3.0], 3) == 0.0

    符号が打ち消し合うと 0 になる のがこの式の肝です。 「似ている残差が集まっている」ほど和が大きくなり、 ばらついていると打ち消し合って小さくなります。

    だから残差全体（総和 0）の類似度は 0 です。

    def test_全体の類似度は0になる() -> None:
    # 残差の総和が 0 なので、根の類似度スコアは 0。
    # 原著が「similarity_score(residuals, lam) -> 0.0」と出しているところ
    assert similarity_score(xgboost_residuals(), 3) == 0.0

    手計算が XGBoost の gain と一致する¶

    原著が手で探した最良の分割は [3, 1, 3] / [-3, -2, -3, 1, 0] で、 スコアは 14.291666666666666 でした。

    そして原著が別のセルで印刷している XGBoost の木のダンプがこれです。

    0:[f0<35] yes=1,no=2,missing=1,gain=14.291667,cover=8

    gain=14.291667。 手で計算した値と一致します。

    原著はこの一致に触れていませんが、 「手で計算したものが XGBoost の内部と同じ」を確かめられる、 この章でいちばん美しい点 だと思います。

    （この確認は Kotlin 版・F# 版にもテストとして入れました。）

    原著の find_best_split にはバグがある¶

    原著の実装の最終行です。

        return winning_left, winning_right, new_score, winning_split

    best_score ではなく new_score を返しています。 new_score はループの最後の反復で計算された値、 つまり 最後の切れ目のスコア です。最良のものではありません。

    原著の出力で確かめられます。

    find_best_split(right_tree, lam)
-> (array([-3., -2., -3.]), array([1., 0.]), 7.0, [...])

    左右の木は正しく [-3,-2,-3] / [1,0] が選ばれています。 そのスコアは (-8)²/(3+3) + 1²/(2+3) = 10.667 + 0.2 = 10.867 のはずです。 なのに 7.0 が返っています。

    7.0 は何か。最後の切れ目 [-3,-2,-3,1] / [0] のスコアです。

    (-7)² / (4+3) + 0² / (1+3) = 7.0 + 0.0 = 7.0

    def test_原著が返す7という値は最後の切れ目のスコア() -> None:
    # 原著のバグを再現して確かめる。右の木 [-3,-2,-3,1,0] の最後の切れ目は
    # [-3,-2,-3,1] / [0] で、(-7)^2/(4+3) + 0^2/(1+3) = 7.0 + 0.0 = 7.0。
    # これが原著の返り値 7.0 の正体である
    _, right, _ = find_best_split(xgboost_residuals(), 3)
    last_split_score = split_scores(right, 3)[-1]

    assert last_split_score == pytest.approx(7.0, rel=1e-15)
    # 最良（10.87）とは違う。原著は最良でないほうを返している
    assert last_split_score != max(split_scores(right, 3))

    なぜ気付かれなかったか¶

    左の木では バグが表に出ません。

    def test_左の部分木ではバグが表に出ない() -> None:
    # 左の木 [3,1,3] は最後の切れ目 [3,1] / [3] が最良と同点（5.45）なので、
    # new_score を返しても best_score を返しても同じ値になる。
    # **バグが隠れる条件が揃っていた**
    left, _, _ = find_best_split(xgboost_residuals(), 3)
    scores = split_scores(left, 3)

    assert scores[-1] == pytest.approx(max(scores), rel=1e-15)

    左の木 [3, 1, 3] は切れ目が 2 通りしかなく、 どちらも 同じ 5.45 になります。最後の切れ目 = 最良なので、 バグのある返り値も正しい値と一致してしまいます。

    原著は左の木の結果（5.45、正しく見える）を先に示し、 右の木の結果（7.0、実は間違い）を後に示しています。 先に正しく見える例が出ると、後の値も疑いません。

    なお 本文の結論は正しい ままです。原著が地の文で書いているのは 「左は [3,1] と [3]、右は [-3,-2,-3] と [1,0]」という 分割の中身 で、 そこはバグの影響を受けません。返り値の 3 つ目を誰も使っていないので、 実害がないまま残ったのだと思われます。

    これは #05 で見つけた alternate_log_loss と同じ構図です。 間違った値が、たまたま誰にも使われていない。

    XGBoost の葉の値まで一致する¶

    def test_XGBoostの葉の値は原著と一致する() -> None:
    # 原著の get_dump() の出力
    #   1 本目: leaf=0.816666603 / leaf=-0.933333337 / leaf=0.140000001
    #   2 本目: leaf=0.530833364 / leaf=-0.606666625 / leaf=0.100800037
    leaves = xgboost_leaf_values(fit_xgboost())

    assert leaves[0] == pytest.approx([0.816666603, -0.933333337, 0.140000001], abs=1e-9)

    原著が印刷した木のダンプの葉の値が、9 桁すべて一致します。

    そして原著の手計算も再現できます。

    def test_20歳の予測は葉の値の足し算になる() -> None:
    # 原著が手で確かめているところ
    #   4 + 0.816666603 + 0.530833364 + 0.345041722 = 5.6925416890000005
    model = fit_xgboost()
    leaves = xgboost_leaf_values(model)
    by_hand = INITIAL_PREDICTION + leaves[0][0] + leaves[1][0] + leaves[2][0]

    assert by_hand == pytest.approx(5.6925416890000005, rel=1e-12)
    # モデルの予測とも一致する（単精度なので 7 桁まで）
    assert float(model.predict(FEATURES)[1]) == pytest.approx(by_hand, rel=1e-7)

    ブースティングが「木の出力を足し算するだけ」であることが、数字で見えます。

    score だけは 8 桁目でずれる¶

    def test_XGBoostのスコアは8桁目でずれる() -> None:
    # 原著の出力は 0.8121875824035912。いまは 0.8121875524520874。
    # XGBoost は内部を単精度（float32）で計算するので、
    # 有効桁 7 桁を超えたところは版や環境で変わりうる
    score = fit_xgboost().score(FEATURES, LABELS)

    assert score == pytest.approx(0.8121875824035912, rel=1e-7)
    assert score != 0.8121875824035912

    原著 0.8121875824035912、いま 0.8121875524520874。 8 桁目から違います。

    XGBoost は内部を float32 で計算します（predict の戻り値の dtype がそれを示しています）。 単精度の有効桁は約 7 桁なので、それを超えた部分は版や環境で変わります。

    rel=1e-7 で「一致する」ことと、!= で「完全一致ではない」ことの 両方をテストに書きました。片方だけだと、後から読む人が誤解します。

    正則化パラメータの効果¶

    def test_gammaを上げると予測が平均に近づく() -> None:
    # 原著が「γ を上げるほど平均に近づく」と書いているところ。
    # γ = 100 では分割が 1 つも許されず、予測が平均 4.0 だけになる
    predictions = fit_xgboost(reg_lambda=0, min_split_loss=100).predict(FEATURES)

    assert predictions == pytest.approx([INITIAL_PREDICTION] * 8, rel=1e-6)

    原著は λ と γ を変えた図を 8 枚並べますが、数値は印刷しません。 「平均に近づく」を数値で確かめました。 γ = 100 では最良の分割スコア 14.29 でも足りず、木が 1 本も育ちません。 予測は base_score の 4.0 だけになります。

    λ のほうは、予測のばらつき（標準偏差）が単調に減ることで確かめました。

    まとめ¶

    項目 原著と一致するか
    段ごとの残差・予測（4 段ぶん） 完全一致
    勾配ブースティングの最終予測 完全一致
    類似度スコア・切れ目ごとのスコア 完全一致
    最良の分割（左右の木） 完全一致
    find_best_split の返すスコア 原著が間違っている（最後の切れ目の値を返している）
    XGBoost の葉の値 9 桁すべて一致
    XGBoost の score 8 桁目でずれる（単精度のため）
