    #22 タイタニックで通しの機械学習（Python）¶

    原著ノートブック: Chapter_13_End_to_end_example/End_to_end_example.ipynb

    タイタニックの生存予測を、前処理からモデル選択まで通しでやる回です。 本の最終章で、これまでのアルゴリズムが一堂に会します。

    シリーズ最終回 でもあります。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-python-lib/src/grokking_ml_lib/nb22_titanic_end_to_end.py
    テスト apps/grokking-ml-python-lib/tests/test_nb22_titanic_end_to_end.py
    実行 uv run pytest tests/test_nb22_titanic_end_to_end.py

    欠損の扱いを 3 通り使い分ける¶

    def clean(raw: pd.DataFrame) -> pd.DataFrame:
    """欠損を片付ける。

    - `Cabin` は 687 / 891 が欠損。**列ごと捨てる**
    - `Age` は中央値（28.0）で埋める
    - `Embarked` は `U`（Unknown）という新しい区分にする
    """

    同じ「欠損」でも扱いが 3 通りです。

    列 欠損数 割合 扱い 理由
    Cabin 687 77% 列ごと捨てる 埋めても情報がない
    Age 177 20% 中央値 28.0 数値なので代表値で埋まる
    Embarked 2 0.2% U という区分を作る カテゴリなので「不明」も 1 つの値

    「欠損を埋める」に唯一の正解はない ことが、この 3 行で見えます。 数値なら代表値、カテゴリなら新しい区分、多すぎるなら捨てる。

    def test_Cabinは8割近くが欠損(raw) -> None:
    # 687 / 891 = 0.771。原著が列ごと捨てる根拠
    assert missing_counts(raw)["Cabin"] / len(raw) > 0.75

    原著は「too many values to be useful」としか書きませんが、 判断の根拠を数値にすればテストできます。

    21 列になる¶

    def test_one_hot後の列は21になる(data) -> None:
    # Survived + SibSp + Parch + Fare + Sex 2 + Embarked 4 + Pclass 3 + 年齢 8
    assert len(data.columns) == 21
    assert "Sex_female" in data.columns
    assert "Embarked_U" in data.columns
    assert "Categorized_age_(70, 80]" in data.columns

    Age を 10 歳刻みに切って one-hot にするので、8 列に膨らみます。 連続値をわざと捨てて区分にする（ビニング）のがこの章の教材です。

    Embarked_U があることが、欠損の扱いが効いている証拠になります。

    分割の件数が原著と一致する¶

    def test_分割の件数は原著と一致する(split) -> None:
    # 原著の出力: 534 / 178 / 179
    assert len(split.train_x) == 534
    assert len(split.validation_x) == 178
    assert len(split.test_x) == 179

    原著は 2 段階で切ります。まず 6:4、その 4 を半分ずつ。 891 → 534 / 357、357 → 178 / 179。

    test_size の側が切り上げ られるので、余った 1 件はテストに行きます。 （この規則は Kotlin 版・F# 版で件数を合わせるときに調べ直しました。）

    7 つのうち 5 つが桁まで一致する¶

    @pytest.mark.parametrize(
    ("name", "expected"),
    [
        ("Logistic regression", 0.7696629213483146),
        ("Naive Bayes", 0.7471910112359551),
        ("SVM", 0.6797752808988764),
        ("Gradient boosting", 0.8089887640449438),
        ("AdaBoost", 0.7359550561797753),
    ],
)
def test_正解率が原著と一致する5つ(models, split, name, expected) -> None:
    # 原著の「Scores of the models」の出力
    assert accuracies(models, split)[name] == pytest.approx(expected, rel=1e-15)

    5 つが 16 桁一致 しました。random_state=100 が固定されているので、 分割が同じになり、決定的なモデルは同じ答えを出します。

    一致しなかったのは決定木とランダムフォレストです。

    def test_乱数を使うモデルは原著と一致しない(models, split, name, expected) -> None:
    # 原著はどちらも 0.7696629213483146。
    # 原著は random_state を渡していないので、そもそも実行のたびに変わる。
    # ここでは 0 を固定した値を記録する

    原著が種を渡していない のが原因です。 原著の 0.7697 という値も、著者がたまたま得たものにすぎません。 再現できないのではなく、そもそも固定されていない のです。

    AdaBoost が一致したのは意外でした。#20 では SAMME.R の削除で値が変わったのに、こちらは変わりません。 このデータでは離散版と実数版が同じ答えに落ち着いたということです。

    F1 スコアを持ち出す理由¶

    def test_SVMは正解率とF1の差が大きい(models, split) -> None:
    # 正解率 0.680 に対して F1 は 0.400。
    # 多数派（死亡）に寄せた予測をしているので、正解率だけでは見抜けない。
    # 原著が F1 を持ち出す理由がこの差である
    accuracy = accuracies(models, split)["SVM"]
    f1 = f1_scores(models, split)["SVM"]

    assert accuracy - f1 > 0.25

    SVM は正解率 0.680、F1 は 0.400。差が 0.28 あります。

    生存者は少数派（891 人中 342 人）なので、 「ほとんど死亡と答える」戦略でも正解率はそこそこ出ます。 F1 は生存者を当てられたかを見るので、そこで馬脚が現れます。

    原著が正解率のあとに F1 を出すのは、この差を見せるためでしょう。

    基準を補う¶

    def test_全員死亡と答える基準は0_607(split) -> None:
    # 原著は基準を出していない。SVM の 0.680 は基準を 0.07 上回るだけで、
    # AdaBoost の 0.736 でも 0.13 の改善にすぎない
    assert majority_baseline(split) == pytest.approx(0.6067415730337079, rel=1e-15)

    原著は基準を出していません。 検証データの 60.7% は死亡なので、「全員死亡」と答えるだけで 0.607 です。

    すると SVM の 0.680 は 0.07 の改善にすぎません。 0.68 という数字だけ見ると「7 割近く当たっている」と読めますが、 基準と比べると印象が変わります。

    #13（多数派を答える基準）・#14（平均を答える基準）と 同じ考え方を、最終章にも当てはめました。

    検証よりテストのほうが良い¶

    def test_検証よりテストのほうが成績が良い(models, split) -> None:
    # 検証 0.809、テスト 0.832。**過学習していれば逆になる**。
    # 原著は触れていないが、モデル選択が妥当だったことの傍証になる

    検証 0.809、テスト 0.832。テストのほうが高い のです。

    検証データを見ながらモデルを選ぶと、検証データに過剰に合わせてしまいます （モデル選択そのものが一種の学習になる）。 その場合はテストで成績が落ちます。落ちなかったということは、 7 つから 1 つ選ぶ程度では過学習しなかったということです。

    原著は触れていませんが、3 分割にした意味がここに出ます。

    グリッドサーチは GridSearchCV を使っていない¶

    def grid_search(split: Split, kernel: str = "rbf") -> dict[tuple[float, float], float]:
    """原著のグリッドサーチ。`C` と `gamma` の組み合わせを総当たりする。

    原著は `GridSearchCV` を import しているが、**実際には使わず
    手で 9 通り書き並べている**。ここは総当たりを 1 つのループにまとめた。
    """

    原著は from sklearn.model_selection import GridSearchCV と書いておきながら、 そのあと SVC(...) を 9 回コピペしています。

    教材としては手で並べるほうが分かりやすい という判断でしょう。 GridSearchCV は交差検証も一緒にやるので、 「検証データで比べる」という話の流れと合わなくなります。

    6 通りの印刷された値がすべて一致しました。

    def test_gammaは小さいほうが良い(split) -> None:
    # どの C でも gamma=0.1 が最良。データが 20 次元あるので、
    # gamma を上げると各点の影響範囲が狭くなりすぎる
    scores = grid_search(split)

    for c in (1, 10, 100):
        assert scores[(c, 0.1)] > scores[(c, 1)] > scores[(c, 10)]

    #19 の 2 次元データでは gamma を上げるほど正解率が上がりました。 ここでは逆です。20 次元あると、gamma が大きいと誰にも届かなくなります。

    def test_グリッドサーチの最良でも勾配ブースティングに届かない(models, split) -> None:
    # SVM は調整しても 0.725。勾配ブースティングの 0.809 には遠い。
    # 原著はグリッドサーチの結果を最終モデルに採用していない
    assert max(grid_search(split).values()) < accuracies(models, split)["Gradient boosting"]

    調整しても届きません。 原著もグリッドサーチの結果を採用せず、 勾配ブースティングをそのまま最終モデルにしています。 「ハイパーパラメータ調整より、モデルの選択のほうが効く」場面です。

    おまけ — 演習 13.1 のコードにもバグがある¶

    原著の演習 13.1（テストデータへの適用）にこんな行があります。

    test_categorized_age = pandas.cut(test_data['Age'], bins)
test_data['Categorized_age'] = categorized_age

    test_categorized_age を作っておきながら、代入しているのは categorized_age（訓練データのほう）です。

    訓練データは 891 行、テストデータは 418 行なので、 pandas が添字で揃えた結果、別人の年齢区分が入ります。

    すぐ上の行にも食い違いがあります。

    # Another small catch, the test data has no missing 'Embarked' fields. Therefore, the processed test data will not
# have an 'Embarked_Q' column. We need to artificially add one filled with zeros.
test_data['Embarked_U'] = pandas.DataFrame([0 for i in range(len(test_data))])

    コメントは Embarked_Q と言っていますが、足しているのは Embarked_U です。 足している列のほうが正しく（欠損が無いので U の列ができない）、 コメントが間違っています。

    #21 の find_best_split と合わせて、 このシリーズで見つけた原著のバグは 3 つ になりました。

    まとめ¶

    項目 原著と一致するか
    891 行・342 人生存・欠損数 完全一致
    前処理後の 21 列 完全一致
    分割の件数（534 / 178 / 179） 完全一致
    7 モデルのうち 5 つの正解率 16 桁一致
    決定木・ランダムフォレスト 一致しない（原著が種を固定していない）
    F1 スコア 5 つ 16 桁一致
    テストデータでの成績 16 桁一致
    グリッドサーチ 6 通り 16 桁一致

    シリーズを終えて¶

    22 本のノートブックを 3 言語で書き切りました。 一致したもの・しなかったものを振り返ると、境目ははっきりしています。

    一致するのは、乱数と近似解法が絡まないところです。 線形代数（#02）、語彙の数え上げ（#06）、 確率の計算（#07）、カーネルの値（#18）、 決定木の分割（#20）、ブースティングの残差（#21）。 これらは言語もライブラリも関係なく同じ答えに行き着きました。

    一致しないのは、乱数か近似解法か、ライブラリの設計判断が入るところです。 ニューラルネットワークの学習ログ、SVM の反復解法、 並列に育てるランダムフォレスト、削除されたアルゴリズム。

    そして 「一致した」と書く前に何度か走らせる ことの大切さも学びました。 #19・#20 では、1 回だけ実行していたら 「たまたま合った値」を成果として書いてしまうところでした。
