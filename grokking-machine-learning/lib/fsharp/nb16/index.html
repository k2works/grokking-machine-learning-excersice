    ノートブック #16 ネットワークの境界を描く（F# 版）¶

    原著ノートブック: Chapter_10_Neural_Networks/Plotting_Boundaries.ipynb

    学習をしない回 です。重みを手で決めたネットワークを 2 つ作り、 その境界を描いて「1 層目は直線、2 層目は曲がる」ことを見せます。

    原著の出力は図が 5 枚だけで、数字が 1 つも出ません。 Python 版 と同じく 境界を数値に直して 検証しました。

    ライブラリを一切使わない回なので、言語そのものの差がいちばん見える回 でもあります。 3 言語のうち F# の実装がもっとも原著に近い形になりました。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-fsharp-lib/src/GrokkingMlLib/Nb16PlottingBoundaries.fs
    テスト apps/grokking-ml-fsharp-lib/tests/GrokkingMlLib.Tests/Nb16PlottingBoundariesTests.fs
    実行 dotnet test --filter "FullyQualifiedName~Nb16"

    関数がそのまま値になる¶

    原著の plot_function(line_1) に対応するのは、そのまま predictions line1 です。

    /// 8 点それぞれの予測
let predictions (f: float -> float -> float) =
    alienDataset |> List.map (fun alien -> classify f (float alien.Aack) (float alien.Beep))

        Assert.Equal<int list>([ 0; 0; 0; 1; 1; 1; 1; 1 ], predictions line1)

    Kotlin は関数参照の :: を付ける必要がありますが、F# は要りません。 関数名がそのまま値 です。原著の Python と同じ見た目になります。

    使わない引数はワイルドカードで書ける¶

    /// 常に 1 を返すニューロン。入力を一切見ない
let bias (_: float) (_: float) = 1.0

    Kotlin では @Suppress("UNUSED_PARAMETER") を付ける必要がありましたが、 F# は _ で「使わない」と宣言できます。注釈ではなく構文で表せます。

    2 層目は AND¶

    /// 階段関数だけで組んだネットワーク。
///
/// 2 層目は `line1 + line2 - 1.5 >= 0`。1 層目の出力は 0 か 1 なので、
/// 和が 1.5 以上になるのは **両方とも 1 のときだけ**。つまり AND である。
let nnWithStep (a: float) (b: float) =
    step (step (6.0 * a + 10.0 * b - 15.0) + step (10.0 * a + 6.0 * b - 15.0) - 1.5)

    [<Fact>]
let ``2層目はANDになっている`` () =
    // 1 層目の出力は 0 か 1。その和が 1.5 以上になるのは両方 1 のときだけ
    Assert.Equal(1.0, nnWithStep 1.0 1.0, 15)
    Assert.Equal(0.0, nnWithStep 2.0 0.0, 15) // line2 だけが 1
    Assert.Equal(0.0, nnWithStep 0.0 2.0, 15) // line1 だけが 1

    バイアス -1.5 の 1 つの数が論理演算の種類を決めています。 -0.5 なら OR、-1.5 なら AND です。

    リテラルにも小数点が要る¶

    /// 1 層目の 1 つ目のニューロン。重み (6, 10)、バイアス -15
let line1 (a: float) (b: float) = step (6.0 * a + 10.0 * b - 15.0)

    原著は 6*a + 10*b - 15 です。F# で 6 * a と書くと通りません。

    error FS0001: 型 'float' は型 'int' と一致しません

    整数リテラル 6 は int に決まってしまい、float との掛け算にならないからです。 6.0 と書き換える手間が要りますが、#12 の Kotlin で踏んだ 整数除算が黙って 0 になる事故 は、この厳しさのおかげで起こりません。

    シグモイド版は 1 点だけ外す¶

    Python 版・Kotlin 版と同じ結果になりました。

    [<Fact>]
let ``シグモイド版は1点だけ外す`` () =
    // aack=1 beep=1 の点だけ 0 と答える。正解は 1
    Assert.Equal<int list>([ 0; 0; 0; 0; 0; 1; 1; 1 ], predictions nnWithSigmoid)
    Assert.Equal(0.875, accuracy nnWithSigmoid, 15)

        // 0.4905 で、しきい値 0.5 をわずかに下回る
    Assert.Equal(0.4905304218, nnWithSigmoid 1.0 1.0, 9)

    0.4905。しきい値 0.5 をわずかに下回ります。 原著は 2 つの図を並べて「同じ境界が滑らかになった」と見せますが、 シグモイド版は 8 点のうち 1 点を間違えます。 詳しくは Python 版 に書いています。

    格子は値として 1 回だけ作る¶

    /// 原著の `np.arange(-0.5, 3, 0.005)` にあたる格子の軸
let axis =
    let count = int (ceil ((GridMax - GridMin) / GridStep))
    Array.init count (fun i -> GridMin + float i * GridStep)

    let axis = ...（関数ではなく値）と書けるので、モジュールの初期化で 1 回だけ 計算されます。Kotlin 版は fun axis() にしたので呼ぶたびに 700 要素を作り直します。

    その代わり、値として書くと 評価の順序に縛られます。 GridMax などが先に定義されていないとコンパイルが通りません。 F# のファイル内の宣言順が厳密なのは、こういう初期化順の曖昧さを消すためです。

    NumPy の arange は誤差を累積する¶

    [<Fact>]
let ``格子は原著と同じ700刻み`` () =
    Assert.Equal(700, axis.Length)
    Assert.Equal(-0.5, axis.[0], 15)
    // こちらは `min + i * step` なのでちょうど 0.0 になる。
    // NumPy の arange は 4.44e-16 になる
    Assert.Equal(0.0, axis.[100], 15)

    -0.5 + 100 × 0.005 は、素直に計算すればちょうど 0.0 です。 NumPy の arange は 4.44e-16 を返します。誤差を累積する実装だからです。

    Python F#・Kotlin
    regionRatio nnWithStep 0.5544327 0.5543918

    49 万点のうち約 20 点だけ、境界ちょうどの点の判定が裏返ります。 どちらが正しいという話ではありません（その点をどちらに入れるかは決まっていない）。 テストは 4 桁で比較し、理由をコメントに残しました。

    8 点の判定はすべて一致します。 ずれるのは格子上の統計だけです。

    まとめ¶

    項目 原著と一致するか
    データの 8 点 完全一致
    5 つの関数の定義 完全一致
    シグモイドの値（10 桁） Python と完全一致
    階段版が 8 点すべて正解 一致
    シグモイド版の正解率 0.875 Python と一致
    格子上の領域の割合 5 桁目でずれる（arange の誤差）
