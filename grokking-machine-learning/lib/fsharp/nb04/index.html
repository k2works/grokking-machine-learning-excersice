    #04 パーセプトロンで直線を引く（F#）¶

    原著ノートブック: Chapter_05_Perceptron_Algorithm/Coding_perceptron_algorithm.ipynb

    2 次元の 8 点を直線で 2 クラスに分けます。 パーセプトロンのトリックを手で書いてから、同じ問題を ML.NET に解かせます。

    3 言語のなかで F# だけ、名前どおりのパーセプトロンがライブラリにあります。 ML.NET の AveragedPerceptron です。Smile には無く、線形 SVM で代替した Kotlin 版 とは対照的な回になりました。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-fsharp-lib/src/GrokkingMlLib/Nb04Perceptron.fs
    テスト apps/grokking-ml-fsharp-lib/tests/GrokkingMlLib.Tests/Nb04PerceptronTests.fs
    実行 dotnet test

    分離直線を型にする¶

    レコードにメンバーを持たせます。

    /// 分離直線。重みとバイアスの組
type Boundary =
    { Weights: float[]
      Bias: float }

    /// 重み付き和にバイアスを足したもの。直線からの符号つき距離に比例する
    member this.Score(features: int[]) =
        this.Bias + (Array.map2 (fun w (f: int) -> w * float f) this.Weights features |> Array.sum)

    /// スコアをステップ関数に通した予測ラベル
    member this.Predict(features: int[]) = step (this.Score features)

    /// パーセプトロン誤差。当たっていれば 0、外れていればスコアの絶対値
    member this.Error(features: int[], label: int) =
        if this.Predict features = label then 0.0 else abs (this.Score features)

    F# のレコードは配列でも構造的に等しい¶

    Kotlin 版 では data class に配列を入れると equals が参照比較になり、自分で書く羽目になりました。F# では要りません。

    F# のレコードが生成する等価性は、配列フィールドについても 要素ごとの比較 になります。

    [<Fact>]
let ``当たっているときは何も動かない`` () =
    // features.[4] = [1, 3] は重み [1, 2] バイアス -4 で予測 1、ラベルも 1
    // レコードなので構造的等価性でそのまま比べられる
    Assert.Equal(start, perceptronTrick 0.05 start features.[4] 1)

    同じ「構造的等価性を持つデータ型」でも、配列を入れたときの挙動が Kotlin と違います。 Kotlin の data class は Java の Object.equals に寄せた設計、 F# のレコードは値としての等価性を優先した設計、という違いがそのまま出ます。

    括弧が要る場面¶

    Score の実装で一度コンパイルエラーを踏みました。

    // これは通らない
this.Bias + Array.map2 (fun w (f: int) -> w * float f) this.Weights features |> Array.sum

    error FS0001: 型 ''a array' は型 'float' と一致しません

    |> は + より結合が弱いので、(this.Bias + Array.map2 ...) |> Array.sum と解釈されます。 float + float array を計算しようとして型エラーになりました。

    // 括弧で囲むと通る
this.Bias + (Array.map2 (fun w (f: int) -> w * float f) this.Weights features |> Array.sum)

    パイプライン演算子は読みやすさのための道具ですが、 算術演算と混ぜるときは優先順位を意識する 必要があります。

    原著の 2 つのトリックは挙動が違う¶

    Python 版 と同じ話です。 原著は「短く書いた版」でバイアスの更新を重みのループの内側に置いており、 特徴量の数だけ繰り返し適用されます。

    F# は不変なので for ループで足し込む書き方ができません。 掛け算にして意図を明示 しました。

    let perceptronTrick (learningRate: float) (boundary: Boundary) (features: int[]) (label: int) =
    let pred = boundary.Predict features
    let delta = float (label - pred)

    { Weights =
        Array.map2 (fun w (f: int) -> w + delta * float f * learningRate) boundary.Weights features
      // 原著はここをループの内側に置いているので、特徴量の数だけ足される
      Bias = boundary.Bias + delta * learningRate * float features.Length }

    * float features.Length の一言が、原著のバグを言葉にしています。 Python・Kotlin は「ループの内側に書いてあるから 2 回足される」という 書き方の副作用 でしたが、F# では「特徴量の数だけ掛ける」という 明示的な式 になりました。

    同じ挙動を再現していても、F# のコードのほうが原著の意図しない挙動が読み取りやすい という逆説的な結果です。

    原著のセル出力と一致します。

    [<Fact>]
let ``短く書いた版のトリックは原著と同じ数値になる`` () =
    // 原著の出力: ([0.9, 1.85], -4.1)
    let updated = perceptronTrick 0.05 start features.[6] 0

    Assert.Equal(0.9, updated.Weights.[0], 12)
    Assert.Equal(1.85, updated.Weights.[1], 12)
    Assert.Equal(-4.1, updated.Bias, 12)

    明示的な版との差もテストで固定しています。

    [<Fact>]
let ``短く書いた版はバイアスを特徴量の数だけ動かす`` () =
    let explicit = perceptronTrickExplicit 0.05 start features.[6] 0
    let short = perceptronTrick 0.05 start features.[6] 0

    // 重みの更新は一致する
    Assert.Equal<float[]>(explicit.Weights, short.Weights)
    // バイアスだけ 2 倍動く
    Assert.Equal(-4.05, explicit.Bias, 12)
    Assert.Equal(-4.1, short.Bias, 12)

    引数の順序は部分適用を意識する¶

    perceptronTrick は学習率を 第 1 引数 に置いています。

    let perceptronTrick (learningRate: float) (boundary: Boundary) (features: int[]) (label: int) =

    perceptronTrick 0.01 と書けば「学習率 0.01 で固定したトリック」が値として得られます。 Python・Kotlin ではデフォルト引数で同じことをしますが、 F# には既定値が無い代わりに部分適用があります。

    ML.NET の AveragedPerceptron¶

    smile.classification にパーセプトロンが無かった Kotlin と違い、 ML.NET には AveragedPerceptron があります。

    /// 同じ問題を ML.NET の `AveragedPerceptron` に解かせる。
///
/// scikit-learn の `Perceptron` にいちばん近いトレーナーである。ML.NET は
/// 二値分類のラベルを **bool** で扱うので、0 / 1 から変換する。
let fitWithMlNet (features: int[][]) (labels: int[]) =
    let ctx = MLContext(seed = 0)

    let rows =
        Array.map2
            (fun (f: int[]) (l: int) ->
                { Features = f |> Array.map single
                  Label = (l = 1) })
            features
            labels

    let data = ctx.Data.LoadFromEnumerable rows
    let trainer = ctx.BinaryClassification.Trainers.AveragedPerceptron(numberOfIterations = 100)
    let model = trainer.Fit data
    let engine = ctx.Model.CreatePredictionEngine<Sample, Prediction> model

    fun (row: int[]) ->
        let prediction =
            engine.Predict { Features = row |> Array.map single; Label = false }

        if prediction.PredictedLabel then 1 else 0

    ML.NET の作法¶

    項目 scikit-learn ML.NET
    入力の形 ndarray [<CLIMutable>] のレコード列
    特徴量の型 float64 single（float32）の配列
    ラベルの型 int（0 / 1） bool
    特徴量列の宣言 不要 [<VectorType(2)>] 属性
    予測 model.predict(X) PredictionEngine を作って 1 行ずつ

    float32 を要求されるのが F# では地味に効きます。 Array.map single の変換を忘れると型エラーです。 Python の float を暗黙に受け取る API に慣れていると引っかかります。

    ラベルが bool なのは ML.NET らしい設計です。 二値分類なのだから bool である、という筋は通っており、 Kotlin の Smile が int の $\pm 1$ を要求して 実行時に落ちた のと比べると、 型で守られている ぶん安全です。

    型を private にすると実行時に落ちる¶

    一度ここで失敗しました。

    System.TypeLoadException : GenericArguments[1], 'GrokkingMlLib.Nb04Perceptron+Prediction',
on 'Microsoft.ML.PredictionEngineBase`2[TSrc,TDst]' violates the constraint of type parameter 'TDst'.

    CreatePredictionEngine<TSrc, TDst> の TDst には 「公開されたクラスで、引数なしのコンストラクタを持つこと」という制約があります。 モジュール内でしか使わないつもりで type private Prediction = ... としていたのが原因でした。

    制約はコンパイル時に検査されず、実行時の TypeLoadException になります。 [<CLIMutable>] は付けていたので、あと 1 歩のところでした。

    結果は原著の予測と一致します。

    [<Fact>]
let ``ML_NET の AveragedPerceptron も全点を正しく分類する`` () =
    // 原著 scikit-learn の出力: Predictions: [0 0 0 0 1 1 1 1]
    let predict = fitWithMlNet features labels

    Assert.Equal<int[]>(labels, features |> Array.map predict)

    3 言語の比較¶

    原著の出力 ([0.55, 0.25], -1.1) は、Python 版 で述べたとおり、 原著が点の選択に使う random に種を与えていないため再現できません。 種を固定した手書きループの到達点を並べると次のようになります。

    実装 重み バイアス 全点を正しく分類
    原著（1 回きりの出力） [0.55, 0.25] -1.10 —
    Python（種 0・500 エポック） [0.63, 0.18] -1.04 できる
    Kotlin（種 0・500 エポック） [0.59, 0.23] -1.10 できる
    F#（種 0・500 エポック） [0.60, 0.23] -1.06 できる

    3 言語とも [0.6 前後, 0.2 前後] / -1.0 前後 に収まりました。 乱数列が違っても 同じあたりに落ち着く のは、 このデータで到達しうる分離直線の範囲が狭いためです。

    ライブラリ側は 3 言語とも 8 点すべてを正しく分類しますが、選ぶ直線は異なります。

    実装 ライブラリのアルゴリズム 係数
    Python Perceptron [4, 2] / -9（原著と一致）
    Kotlin 線形 SVM（代替） 比較対象にならない
    F# AveragedPerceptron 平均化された重みで、原著とは別

    AveragedPerceptron は名前のとおり 学習途中の重みを平均する 変種です。 scikit-learn の Perceptron とは別のアルゴリズムなので、係数は一致しません。 「パーセプトロンがある」といっても、同じものとは限らない例になりました。

    この章で F# が効いた場面・効かなかった場面¶

    場面 評価
    レコードの構造的等価性 効いた — 配列を持っても要素比較。Kotlin と違い自前実装が不要
    原著のバグの表現 効いた — * float features.Length で意図が明示される
    学習率の固定 効いた — 引数順を工夫した部分適用
    ML.NET のラベル型 効いた — bool なので取り違えが型で止まる
    パイプラインの優先順位 効かなかった — 算術と混ぜると括弧が要る
    float32 への変換 効かなかった — Array.map single を毎回書く
    型の可視性 効かなかった — private で実行時に TypeLoadException

    前章までライブラリの手当てがいちばん薄かった F# ですが、 この章は 3 言語でいちばんライブラリの支援が厚い 回でした。
