    #06 IMDB レビューの感情分析（F#）¶

    原著ノートブック: Chapter_06_Logistic_Regression/Sentiment_analysis_IMDB.ipynb

    映画レビュー 50000 件を、単語の出現回数だけからロジスティック回帰で肯定・否定に分類します。

    この章は F# だけ、ロジスティック回帰そのものを自前で書くことになりました。 そして結果として、最適化アルゴリズムの違いが結果をどう変えるか が いちばんはっきり見える回になりました。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-fsharp-lib/src/GrokkingMlLib/Nb06SentimentImdb.fs
    テスト apps/grokking-ml-fsharp-lib/tests/GrokkingMlLib.Tests/Nb06SentimentImdbTests.fs
    実行 dotnet test

    CountVectorizer を自前で書く¶

    .NET にも CountVectorizer に相当するものはありません。 ML.NET の FeaturizeText は n-gram やハッシュ化まで含む別物で、 stop_words='english' の 318 語も持っていません。

    Kotlin 版 と同じく、scikit-learn から書き出したストップワードを 共有データセットから読み、規則を 4 つ揃えて自前で書きます。

    /// 小文字化して 2 文字以上の単語を取り出し、ストップワードを除く
let tokenize (stopWords: Set<string>) (document: string) =
    tokenPattern.Matches(document.ToLowerInvariant())
    |> Seq.map (fun m -> m.Value)
    |> Seq.filter (fun token -> not (stopWords.Contains token))
    |> List.ofSeq

    Set<string> は F# の不変集合で、Contains が O(log n) です。 Kotlin の HashSet の O(1) には劣りますが、318 語なので差は出ません。 不変であることのほうが効きます — この関数は純粋なので、どこから呼んでも安全です。

    語彙の並べ替えで一度つまずいた¶

    「出現回数の降順、同数なら語の昇順」を書こうとして、最初にこう書きました。

    // 通らない書き方
counts |> Seq.sortByDescending (fun kv -> kv.Value, kv.Key)

    これだと 語も降順 になってしまいます。タプルで複合キーを作ると、 すべての要素に同じ方向が適用されるためです。Kotlin の compareByDescending { }.thenBy { } のように方向を混ぜられません。

    比較関数を書きました。

    // 出現回数の多い順。同数なら辞書順にして結果を決定的にする
let byCountThenWord (left: KeyValuePair<string, int>) (right: KeyValuePair<string, int>) =
    match compare right.Value left.Value with
    | 0 -> String.CompareOrdinal(left.Key, right.Key)
    | difference -> difference

let words =
    counts
    |> Seq.sortWith byCountThenWord
    |> Seq.truncate maxFeatures
    |> Seq.map (fun kv -> kv.Key)
    |> Seq.sortWith (fun a b -> String.CompareOrdinal(a, b))
    |> Array.ofSeq

    compare right.Value left.Value と引数を入れ替えているのが降順です。 match の | 0 -> で同数のときだけ語の比較に落ちる、という構造が そのまま「同数なら辞書順」の言い換え になっています。 1 行では書けませんでしたが、読みやすさでは負けていません。

    String.CompareOrdinal を使っているのは、 既定の compare がカルチャ依存の比較になるためです。 実行環境のロケールで語彙の順序が変わったら、添字が一致しなくなります。

    疎ベクトルを型で表す¶

    Kotlin 版 は密行列にしてヒープを使い切りました。 F# では最初から疎で書きます。

    /// 出現回数ベクトル。疎な表現で持つ。
///
/// **密な行列にしてはいけない。** IMDB は 50000 件 × 2000 語なので、
/// 倍精度の密行列にすると 800 MB になる。実際の非ゼロ要素は数パーセントである。
type SparseCounts = (int * float) list

    型エイリアスを 1 行置くだけで、 「これは (添字, 値) の並びである」 が型に出ます。 Smile の SparseArray のようなクラスを使わなくても、 F# の組み込みの型で表現できてしまいます。

    ML.NET を使わなかった理由¶

    ML.NET の二値分類トレーナーは、特徴量を 固定長の float32[] で要求します。 50000 × 2000 の配列を作れば単精度でも約 400 MB です。

    疎なまま解くほうが素直なので、勾配降下を自前で書きました。

    /// 疎な出現回数ベクトルに対するロジスティック回帰を、勾配降下で学習する。
///
/// ML.NET は特徴量を固定長の `float32[]` で要求するため、50000 × 2000 の
/// 密配列（約 400 MB）を作ることになる。ここは疎なまま解くほうが素直なので、
/// 自前の勾配降下で書いた。L2 正則化を掛けて scikit-learn の既定に寄せる。
let fitSparse ... =
    for _ in 1..epochs do
        ...
        // 疎ベクトルなので、非ゼロの要素だけを見れば済む
        for i in 0 .. features.Length - 1 do
            let score =
                features.[i] |> List.sumBy (fun (index, value) -> weights.[index] * value)

            let predicted = 1.0 / (1.0 + exp (-(score + intercept)))
            let error = float labels.[i] - predicted

            for (index, value) in features.[i] do
                gradient.[index] <- gradient.[index] + error * value

            interceptGradient <- interceptGradient + error

        for j in 0 .. vocabulary.Size - 1 do
            // L2 正則化。切片は罰則の対象にしない
            weights.[j] <- weights.[j] + learningRate * (gradient.[j] / n - lambda * weights.[j])

    List.sumBy で内積を取るところが、疎表現の効き目です。 2000 次元の内積が、実際には数百回の掛け算で終わります。

    語彙の添字は一致した¶

    自前実装が正しいかを確かめる決め手は、原著の出力に残る添字です。

    [<Fact>]
let ``IMDB の語彙は原著と同じ添字になる`` () =
    if imdbAvailable () then
        let reviews = loadReviews ()
        let vocabulary = fitVocabulary stopWords MaxFeatures reviews.Texts

        Assert.Equal(50000, reviews.Texts.Length)
        Assert.Equal(MaxFeatures, vocabulary.Size)
        // 自前のベクトル化が scikit-learn と同じ語彙を作れている証拠。
        // 原著の出力に現れる添字（1964 wonderfully / 1921 waste）と一致する
        Assert.Equal(1964, Array.findIndex ((=) "wonderfully") vocabulary.Words)
        Assert.Equal(1921, Array.findIndex ((=) "waste") vocabulary.Words)

    一致しました。 Python・Kotlin・F# の 3 言語が、 別々に書いたベクトル化で 同じ 2000 語・同じ添字 に到達しています。

    上位の感情語は一致しなかった¶

    ここが F# だけ違いました。

    順位 原著（lbfgs） F#（勾配降下 300 エポック）
    1 wonderfully excellent
    2 funniest perfect
    3 gem wonderful
    4 brilliantly great
    5 subtle amazing
    6 superb brilliant

    単語の系統がまるで違います。 原著は wonderfully funniest gem のような やや珍しい語、F# は excellent perfect great のような 頻出語 です。

    原因は最適化アルゴリズム¶

    これは語彙の問題ではありません（添字は一致しています）。 勾配降下が最適解まで届いていない のです。

    学習の初期は、出現回数の多い語ほど勾配が大きくなります。 great は全レビューの何割にも出るので、まずそこに重みが乗ります。 一方 wonderfully は珍しい語ですが、出れば肯定である確率がずっと高い — つまり 判別力が高い。最適解ではこちらの係数が大きくなります。

    エポックを増やすと、実際にその方向へ動きます。

    設定 上位 6 語
    学習率 0.5・300 エポック excellent, perfect, wonderful, great, amazing, brilliant
    学習率 5.0・300 エポック excellent, perfect, great, amazing, wonderful, brilliant
    学習率 5.0・2000 エポック excellent, amazing, perfect, brilliant, superb, wonderful

    2000 エポックで superb（原著の 6 位）が入ってきました。 方向は合っていますが、2000 エポックでも 111 秒かかって、まだ届きません。

    lbfgs は勾配だけでなく 曲率の近似 を使うので、 特徴量ごとにスケールが大きく違うこの問題でも一気に最適解へ向かいます。 LogisticRegression(max_iter=1000) の 1 行が肩代わりしているのは、この差です。

    テストは符号で書く¶

    上位語を固定するとテストが意味を失うので、 符号の向きが正しく学習できていること を確認する形にしました。

    [<Fact>]
let ``IMDB では感情語の符号が正しく分かれる`` () =
    if imdbAvailable () then
        // 自前の勾配降下は lbfgs ほど速く収束しない。300 エポックでは
        // 上位に出るのが原著の wonderfully / funniest ではなく excellent /
        // perfect のような頻出語になる。符号の向きは正しく学習できている
        let model = fit (loadReviews ()) MaxFeatures 300
        let weights = model.WordSentiments() |> Map.ofArray

        for word in [ "excellent"; "wonderful"; "superb"; "brilliant" ] do
            Assert.True(weights.[word] > 0.0, $"{word} は正のはず")

        for word in [ "waste"; "worst"; "awful"; "boring" ] do
            Assert.True(weights.[word] < 0.0, $"{word} は負のはず")

    何が再現できて、何が再現できないかを分けて書く のがこの章のテスト設計です。 語彙は完全一致するので添字で厳密に固定し、 係数は最適化アルゴリズムの差が出るので符号だけを見ます。

    3 言語の比較¶

    実装 ベクトル化 学習 語彙の添字 上位感情語
    Python CountVectorizer LogisticRegression（lbfgs） — 順序まで一致
    Kotlin 自前 SparseLogisticRegression 一致 集合が一致
    F# 自前 自前の勾配降下 一致 一致しない

    自前で書く範囲が広がるほど、原著から遠ざかっていく様子がそのまま出ました。 ただし 遠ざかった原因は特定できています — ベクトル化ではなく最適化です。

    これは悪い結果ではありません。 「ライブラリの fit() が何を肩代わりしているか」を知るという この連載の目的からすると、F# 版がいちばん多くを見せてくれた ことになります。

    この章で F# が効いた場面・効かなかった場面¶

    場面 評価
    疎ベクトルの表現 効いた — (int * float) list の型エイリアス 1 行で意図が出る
    比較関数 効いた — 「同数なら辞書順」がそのまま match の分岐になる
    トークン化 効いた — 純粋関数として書けて Set が不変
    複合キーの並べ替え 効かなかった — タプルでは昇順・降順を混ぜられない
    CountVectorizer 効かなかった — 相当するものが無く自前実装
    ML.NET の入力形式 効かなかった — 固定長 float32[] で疎データを扱えない
    最適化 効かなかった — 自前の勾配降下では lbfgs に届かない
