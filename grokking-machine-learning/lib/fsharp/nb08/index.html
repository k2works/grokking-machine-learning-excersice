    #08 ジニ不純度とエントロピーの計算（F#）¶

    原著ノートブック: Chapter_09_Decision_Trees/Gini_entropy_calculations.ipynb

    決定木の章に入ります。木を作る前に、どこで分割すべきかを決める物差し — ジニ不純度とエントロピー — を手で計算します。

    原著は NumPy しか使わない小さな回です。F# では List.countBy が初出順を保つ ことに助けられ、3 言語でいちばん短く書けました。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-fsharp-lib/src/GrokkingMlLib/Nb08GiniEntropy.fs
    テスト apps/grokking-ml-fsharp-lib/tests/GrokkingMlLib.Tests/Nb08GiniEntropyTests.fs
    実行 dotnet test

    List.countBy が原著の 6 行を 1 行にする¶

    原著の counts は辞書に数えてから取り出す 6 行です。F# は 1 行になります。

    /// 要素ごとの個数を、**初めて現れた順** に返す。
///
/// 原著は辞書に数えてから取り出しており、Python 3.7 以降の辞書は挿入順を保つ。
/// F# の `List.countBy` も **初出順** を保つので、そのまま対応する。
/// `Map` に入れると辞書順に並び替わってしまい、原著と結果がずれる。
let counts (items: string list) =
    items |> List.countBy id |> List.map snd

    List.countBy は初出順を保ちます。 ここが重要で、 items |> List.groupBy id |> Map.ofList のように Map を経由すると 辞書順（A, B, C）に並び替わります。原著の [3, 2, 1] が [3, 1, 2] になり、 浮動小数点の丸めまで揃えたい今回はそこで差が出ます。

    F# の Map は順序づけられた二分木なので、 「集合や写像に入れると勝手にソートされる」ことを意識しておく必要があります。 #07 の Set も同じ性質でした。

    [<Fact>]
let ``個数は初出順に並ぶ`` () =
    // 原著の出力: [3, 2, 1]。A が 3、C が 2、B が 1 の順
    Assert.Equal<int list>([ 3; 2; 1 ], counts elements)

    型変換が整数除算を防ぐ¶

    let gini (items: string list) =
    let classCounts = counts items
    let n = List.sum classCounts

    1.0
    - (classCounts
       |> List.sumBy (fun count -> float count * float count / (float n * float n)))

    float count の変換が 4 か所に要ります。書く量は増えますが、 忘れると型エラーで止まります。

    Kotlin 版 では count * count / (n * n) と書くと すべて Int のまま整数除算になり、黙って 0 を返して「常に不純度 1」という 壊れ方をします。F# ではその間違いが起きません。

    暗黙変換が無いことの利点が、はっきり出る場面でした。

    Math.NET のベクトルで内積を書く¶

    エントロピーは原著が np.log2 と np.dot を使う箇所です。

    let entropy (items: string list) =
    if List.isEmpty items then
        0.0
    else
        let classCounts = counts items
        let n = List.sum classCounts
        let proportions: Vector<float> =
            classCounts |> List.map (fun count -> 1.0 / float n * float count) |> DenseVector.ofList
        let logs = proportions |> Vector.map (fun p -> log p / log 2.0)
        -(logs * proportions)

    logs * proportions がそのまま内積になります。 Math.NET の Vector<float> は * を内積として定義しているので、 np.dot と 1 対 1 に対応します。

    Kotlin 版 の Multik は * が要素ごとの積なので .sum() を足す必要がありました。同じ「NumPy 相当」でも演算子の意味が違います。

    ライブラリ a * b の意味 内積の書き方
    NumPy 要素ごとの積 np.dot(a, b)
    Multik（Kotlin） 要素ごとの積 (a * b).sum()
    Math.NET（F#） 内積 a * b

    log2 が無いのは Math.NET も同じで、log p / log 2.0 と書きます。

    空のリストの扱いが 2 つで違う¶

    Python 版 と同じ発見です。 gini には空の特別扱いが無く、entropy にはあります。

    [<Fact>]
let ``空のリストの扱いは2つで違う`` () =
    // 原著はエントロピーだけ明示的に 0 を返す。ジニは 1 - 0 で 1 になる
    Assert.Equal(1.0, gini [], 15)
    Assert.Equal(0.0, entropy [], 15)

    F# の List.sumBy も、空のリストに対してラムダを 1 度も呼びません。 n = 0 でもゼロ除算にならず、1.0 - 0.0 = 1.0 が返ります。 3 言語とも同じ理由で、偶然うまくいっています。

    リスト内包表記で分割を並べる¶

    let splitImpurities (items: string list) =
    let total = items.Length

    [ for index in 0 .. total - 1 ->
        let left = List.truncate index items
        let right = List.skip index items

        { Index = index
          Left = left
          Right = right
          WeightedGini = weighted gini left right total
          WeightedEntropy = weighted entropy left right total } ]

    [ for ... -> ... ] のリスト内包表記が、原著の for ループと 同じ形のまま値を返す式 になります。 results.append(...) のような累積が要りません。

    List.truncate index と List.skip index が Python の elements[:i] / elements[i:] にあたります。 List.truncate は要素数が足りなくてもエラーにならないので、 index = 0 でも空のリストが返って安全です。

    重み付けは関数を引数に取る形にしました。

    let private weighted impurity (left: string list) (right: string list) (total: int) =
    1.0 / float total * (impurity left * float left.Length + impurity right * float right.Length)

    F# は関数を渡すのに :: のような記法が要らず、weighted gini left right total と 関数名をそのまま書けます。Kotlin の ::gini に相当する構文が不要な分、 「不純度を測る関数を差し替える」という意図が素直に読めます。

    結果は原著と完全一致する¶

    分割 0 のエントロピーが 1.4591479170272446 と、 entropy elements の 1.4591479170272448 から最下位ビットだけずれる点まで再現しました。

    [<Fact>]
let ``分割しない場合の重み付き不純度は全体の不純度と一致する`` () =
    // index 0 は左が空なので、右がそのまま全体になる。
    // ただしエントロピーは 1.4591479170272446 で、entropy elements の
    // 1.4591479170272448 と最下位ビットだけ違う。重み付けの掛け算と割り算で
    // 丸めが 1 度多く入るため
    let split = (splitImpurities elements).[0]

    Assert.Equal(gini elements, split.WeightedGini, 15)
    Assert.NotEqual(entropy elements, split.WeightedEntropy)
    Assert.True(abs (entropy elements - split.WeightedEntropy) < 1e-15)

    Assert.NotEqual と Assert.True(abs ... < 1e-15) を並べて、 「厳密には違うが、実質は同じ」 を 2 行で表しています。

    3 言語の比較¶

    場面 Python Kotlin F#
    初出順の数え上げ dict が挿入順を保つ groupingBy().eachCount() List.countBy
    整数除算の危険 無い（/ は常に実数） ある（toDouble() が要る） 無い（型エラーで止まる）
    内積 np.dot(a, b) (a * b).sum() a * b
    空のリスト 警告が出る 黙って NaN 黙って NaN

    3 言語とも原著の数値を完全に再現しました。 #07 と同じく、原著がライブラリを使っていない回は差が出ません。

    この章で F# が効いた場面・効かなかった場面¶

    場面 評価
    数え上げ 効いた — List.countBy が 1 行で初出順を保つ
    型変換 効いた — 整数除算の間違いが型エラーで止まる
    内積 効いた — Math.NET の * がそのまま内積
    分割の列挙 効いた — リスト内包表記が式のまま値を返す
    高階関数 効いた — 関数名をそのまま渡せる（:: が不要）
    Map / Set の順序 効かなかった — 経由すると辞書順に並び替わる
    log2 効かなかった — Math.NET にも無く log p / log 2.0
