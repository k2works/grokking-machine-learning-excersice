    ノートブック #21 勾配ブースティングと XGBoost（F# 版）¶

    原著ノートブック: Chapter_12_Ensemble_Methods/Gradient_boosting_and_XGBoost.ipynb

    8 人の年齢から「週に何日アプリを使うか」を当てる回帰の回です。

    #20 で AdaBoost を自前で書いたので、この回も同じ路線で 勾配ブースティングを自前で書きました。 その結果、段ごとの残差が 1e-16 の丸め誤差の出方まで scikit-learn と一致 しました。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-fsharp-lib/src/GrokkingMlLib/Nb21GradientBoosting.fs
    テスト apps/grokking-ml-fsharp-lib/tests/GrokkingMlLib.Tests/Nb21GradientBoostingTests.fs
    実行 dotnet test --filter "FullyQualifiedName~Nb21"

    分類の木を回帰の木に変える¶

    #20 の分類木から変えたのは 2 か所だけです。

    分類（#20） 回帰（#21）
    葉の値 多数決 平均
    分割の評価 ジニ不純度 二乗誤差 
    /// 重み付き二乗誤差。回帰木では分散の減少で分割を決める
let private sumSquaredError (targets: float[]) =
    if targets.Length = 0 then
        0.0
    else
        let mean = Array.average targets
        targets |> Array.sumBy (fun v -> (v - mean) ** 2.0)

    分割の候補の作り方（隣り合う値の中点）も、同点のときの選び方も #11 からそのまま持ち越せます。

                |> Array.sortBy (fun (error, threshold, _, _) -> error, threshold)

    同点なら小さいしきい値を選ぶ。 タプルで並べるだけで書けるのは F# の sortBy の使いやすいところです。

    勾配ブースティングは 20 行¶

    let fitGradientBoosting (rounds: int) =
    let centered = centeredLabels ()
    let predictions = Array.zeroCreate days.Length
    let stages = ResizeArray<Stage * Tree>()
    let mutable residuals = centered

    for _ in 1..rounds do
        let tree = fitTree ages residuals MaxDepth
        let stagePredictions = ages |> Array.map (predictTree tree)

        for i in 0 .. days.Length - 1 do
            predictions.[i] <- predictions.[i] + stagePredictions.[i] * LearningRate

        let newResiduals = Array.map2 (-) centered predictions
        ...
        residuals <- newResiduals

    本の説明「残差に木を当てて、学習率を掛けて足す」がそのままコードになります。

    Array.map2 (-) centered predictions の 1 行で残差が出るのは気持ちが良いところです。 演算子を関数として渡せるので fun a b -> a - b と書かずに済みます。

    段ごとの残差が丸め誤差まで一致する¶

    [<Fact>]
let ``2段目の後の残差は原著と一致する`` () =
    // 原著の出力: [ 0.6 -0.6 0.28 -0.44 0.56 -0.44 0.52 -0.48]
    let stage, _ = (fitGradientBoosting 4).[1]

    approx [| 0.6; -0.6; 0.28; -0.44; 0.56; -0.44; 0.52; -0.48 |] stage.NewResiduals 1e-12

    4 段ぶんの残差と予測が、すべて原著と一致しました。

    いちばん面白いのは 3 段目です。

    [<Fact>]
let ``3段目の予測はほとんど0になる`` () =
    // 原著の出力に -7.40148683e-17 が並ぶ。**符号は違うが桁は同じ**。
    // 「もう説明できるものが残っていない」を浮動小数点の誤差が示している
    let stage, _ = (fitGradientBoosting 4).[2]

    Assert.Equal(0.6, stage.Predictions.[0], 12)
    Assert.Equal(-0.6, stage.Predictions.[1], 12)
    Assert.All(stage.Predictions.[2..], fun value -> Assert.True(abs value < 1e-15))

    原著は -7.40148683e-17、こちらは +7.401486831e-17。 絶対値も指数も同じで、符号だけが違います。

    同じ大きさの誤差が出るということは、 同じ順序で同じ演算をしている ということです。 (v - mean) の平均を取る順番が 1 か所違えば、桁が変わります。

    数学的にはどちらも 0 なので、abs value < 1e-15 で判定しました。 「一致する」を「等しい」ではなく「同じ精度で 0 とみなせる」と定義 しています。

    2 段目にも同じことが起きていて、原著が 0. と印刷している位置に こちらは -2.220446049e-16 が出ます。これも 0 です。

    型注釈があるから引数を間違えない¶

    Kotlin 版は Smile の GradientTreeBoost.fit に 9 個の引数を並べる必要があり、 10000, 1, 0.8, 1.0 が何を意味するかはコメント頼みでした。

    自前実装なら関数名と引数名で書けます。

    let fitTree (x: float[]) (y: float[]) (maxDepth: int) =
    build x y [| 0 .. x.Length - 1 |] 0 maxDepth

    「ライブラリを使う」ことが目的ではなく、原著を再現することが目的 です。 そのとき、道具が足りなければ書くのが早い場面もあります。 このシリーズでは #20 と #21 がそれでした。

    手計算が XGBoost の gain と一致する¶

    [<Fact>]
let ``分割のスコアはXGBoostのgainと一致する`` () =
    // 原著の木のダンプ: 0:[f0<35] ... gain=14.291667
    // 手で計算した最良スコアが、XGBoost が出す gain とぴたり合う
    Assert.Equal(14.291667, (findBestSplit (xgboostResiduals ()) 3.0).Score, 6)

    原著が別々のセルに印刷している 2 つの数字が同じものだと確かめました。 この一致こそが「XGBoost が内部で何をしているか」の答え です。

    List.maxBy は最初の最大を返す¶

    let findBestSplit (residuals: float[]) (lambda: float) =
    let scores = splitScores residuals lambda

    if List.isEmpty scores then
        { Left = [||]; Right = residuals; Score = 0.0 }
    else
        let bestIndex = scores |> List.mapi (fun i score -> i, score) |> List.maxBy snd |> fst

    原著は if new_score > best_score と 狭義の不等号 で比べるので、 同点なら先に見つけたほうが残ります。

    F# の List.maxBy も 最初の最大値 を返します。挙動が一致するので、 左の木 [3, 1, 3]（5.45 が 2 通り）で同じ答えになりました。

    もし maxBy が最後の最大を返す仕様だったら、 [3, 1] / [3] のほうが選ばれて原著と食い違います。 同点の扱いは、こういう小さな関数の仕様で決まります。 #11 で scikit-learn の同点処理を 4 つ洗い出したときと同じ話です。

    原著の find_best_split にはバグがある¶

    [<Fact>]
let ``原著が返す7という値は最後の切れ目のスコア`` () =
    // 右の木 [-3,-2,-3,1,0] の最後の切れ目は [-3,-2,-3,1] / [0] で、
    // (-7)^2/(4+3) + 0^2/(1+3) = 7.0。これが原著の返り値 7.0 の正体
    let right = (findBestSplit (xgboostResiduals ()) 3.0).Right
    let scores = splitScores right 3.0

    Assert.Equal(7.0, List.last scores, 15)
    Assert.True(List.last scores < List.max scores)

    原著は best_score ではなく new_score を返しています。 詳しくは Python 版 に書きました。

    面白いのは、F# でこのバグを書くのが難しい ことです。 原著は for ループの外で new_score を参照していますが、 F# の for ループ内で束縛した let はループの外から見えません。

        for index in 1 .. residuals.Length - 1 do
        let newScore = ...   // ここで束縛した newScore は
    // ここでは参照できない（コンパイルエラー）

    意図的に書くなら let mutable を用意する必要があります。 「うっかり最後の値を返してしまう」が起きにくい構造 です。

    Python は関数スコープなので、ループを抜けた後も new_score が生き残ります。 このバグは 言語の仕様が許したから書けた とも言えます。

    まとめ¶

    項目 原著と一致するか
    段ごとの残差・予測（4 段ぶん） 完全一致（1e-16 の誤差の桁まで）
    勾配ブースティングの最終予測 完全一致
    類似度スコア・切れ目ごとのスコア 完全一致
    最良の分割（左右の木） 完全一致
    手計算のスコアと XGBoost の gain 一致（原著は触れていない）
    find_best_split の返すスコア 原著が間違っている
    XGBoost 本体 使わない（後半は四則演算だけ）
