    #02 ハイデラバードの住宅価格を予測する（F#）¶

    原著ノートブック: Chapter_03_Linear_Regression/House_price_predictions.ipynb

    実データ 2518 件から住宅価格を予測します。面積 1 列だけを使う単回帰と、 全 40 列を前処理してから使う重回帰の 2 本立てです。

    この章は 3 言語のうち F# だけが違う数値を出しました。 しかも、原著と同じ種類の異常な切片が出ます。原因まで追うと、この章でいちばんの読みどころになります。

    サンプル実装¶

    項目 内容
    実装 apps/grokking-ml-fsharp-lib/src/GrokkingMlLib/Nb02HousePrices.fs
    テスト apps/grokking-ml-fsharp-lib/tests/GrokkingMlLib.Tests/Nb02HousePricesTests.fs
    実行 dotnet test

    データセットの読み込み¶

    pandas の役割は Deedle が担います。

    /// ハイデラバードの住宅データを読み込む。2518 行 × 40 列
let loadData () = Datasets.loadFrame "Hyderabad.csv"

let private column (frame: Frame<int, string>) (name: string) =
    frame.GetColumn<float>(name) |> Series.values |> Array.ofSeq

let private stringColumn (frame: Frame<int, string>) (name: string) =
    frame.GetColumn<string>(name) |> Series.values |> Array.ofSeq

    GetColumn<float> のように 取り出す型を明示 します。Deedle は列の型を 実行時まで持たないので、ここで指定した型に変換されます。 型を間違えると実行時例外になり、コンパイル時には止まりません。 Kotlin DataFrame の convertTo<Double>() と同じ性質です。

    面積だけの単回帰¶

    let fitAreaOnly (frame: Frame<int, string>) =
    let struct (intercept, slope) =
        MathNet.Numerics.Fit.Line(column frame "Area", column frame "Price")

    { Intercept = intercept
      Coefficients = DenseVector.ofArray [| slope |] }

    ノートブック #01 と同じく Fit.Line は構造体タプルを返し、順序は (切片, 傾き) です。 数値は原著と一致します。

    [<Fact>]
member _.``単回帰の係数は原著と同じ数値になる``() =
    // 原著 scikit-learn の出力
    //   y-intercept: -6222669.083283698
    //   slope (coefficient of Area): 9753.940608184039
    let model = fitAreaOnly fixture.Frame

    Assert.Equal(-6222669.083283698, model.Intercept, 6)
    Assert.Equal(9753.940608184039, model.Coefficients.[0], 9)

    前処理¶

    特徴量は行列で持つ¶

    Python は DataFrame、Kotlin は Map<String, DoubleArray> でしたが、 F# では Matrix<float> と列名リストの組 にしました。

    /// 前処理を通したあとのデータ一式
type Preprocessed =
    { /// 列名。順序が予測時の行の組み立てと一致している必要がある
      ColumnNames: string list
      /// 特徴量行列。行が物件、列が特徴量
      Features: Matrix<float>
      Labels: Vector<float>
      Standardizer: Standardizer }

    member this.RowCount = this.Features.RowCount

    このあと SVD で解くので、どのみち行列が要ります。 Map から行列を組み立て直すくらいなら、最初から行列で持つほうが素直です。

    列を組み立てる¶

    前処理の 3 手順を、列のリストを連結する形で書きます。

        let columnNames =
        [ "Area"; "No. of Bedrooms" ]
        @ passthroughNames
        @ (locationNames |> List.map (sprintf "Location_%s"))

    let columns =
        [ area |> Array.map (fun v -> (v - standardizer.AreaMean) / standardizer.AreaStd)
          bedrooms
          |> Array.map (fun v -> (v - standardizer.BedroomsMean) / standardizer.BedroomsStd) ]
        @ (passthroughNames |> List.map (fun name -> take (column frame name)))
        @ (locationNames
           |> List.map (fun name -> location |> Array.map (fun v -> if v = name then 1.0 else 0.0)))

    列名のリストと値のリストが同じ形で並んでいる のが、この書き方の効きどころです。 Kotlin の LinkedHashMap は「順序を壊さないように気をつける」必要がありましたが、 ここでは 2 つのリストを同じ順序で組み立てているのが目で見て分かります。

    代償として、名前と値の対応が 型では保証されません。片方だけ並べ替えると壊れます。 (string * float[]) list にすれば型で縛れますが、行列を作るときにほどく手間が増えるため、 テストで列数の一致を確認する形にしました。

    one-hot 符号化は Kotlin と同じく自前です。

    let locationNames = location |> Array.distinct |> Array.sort |> List.ofArray

    Array.sort が要るのは pd.get_dummies がカテゴリを昇順に並べるからです。 これを忘れると Python 版と列順が変わり、係数の読み比べができなくなります。

    標準偏差¶

    pandas の std() に合わせて不偏分散を使います。

    /// 不偏分散（ddof = 1）の標準偏差。pandas の `std()` の既定に合わせる
let private sampleStd (values: float[]) =
    let mean = Array.average values
    sqrt (values |> Array.sumBy (fun v -> (v - mean) ** 2.0) |> fun s -> s / float (values.Length - 1))

    float (values.Length - 1) の変換が必須です。F# は整数と浮動小数点を暗黙に混ぜないので、 ddof の扱いを間違えるより先に 型エラーで手が止まります。この厳しさは、 ここでは助けになりました。

    ランク落ちした行列を SVD で解く¶

    /// 前処理済みの全特徴量で重回帰を学習する。
///
/// one-hot 符号化した地域の列は合計すると常に 1 になり、切片と線形従属になる。
/// 正規方程式では解けないので、擬似逆行列を求める SVD を使う。Math.NET の
/// `MultipleRegression.Svd` は最小ノルム解を返す。
let fitAllFeatures (prepared: Preprocessed) =
    // 切片を推定させるため、値が 1 の列を先頭に足した設計行列を作る
    let rows = prepared.RowCount
    let design =
        DenseMatrix.init rows (prepared.Features.ColumnCount + 1) (fun row col ->
            if col = 0 then 1.0 else prepared.Features.[row, col - 1])

    let solution =
        MathNet.Numerics.LinearRegression.MultipleRegression.Svd(design, prepared.Labels)

    { Intercept = solution.[0]
      Coefficients = solution.SubVector(1, solution.Count - 1) }

    scikit-learn も Smile も切片を自動で扱いますが、Math.NET の MultipleRegression.Svd は 切片を扱いません。値が 1 の列を自分で足します。 DenseMatrix.init で行列を作りながら 1 列ずらすのが、いちばん短い書き方でした。

    F# だけ違う数値が出た¶

    3 言語を並べます。

    実装 切片 Area の係数 RMSE 新物件の予測
    原著（旧 scikit-learn） 7.2895e+17 7,023,646.118 3,981,401.493 6,006,016.00
    Python（scikit-learn 1.9） 8,947,283.554 7,023,504.921 3,981,396.292 6,004,735.31
    Kotlin（Smile SVD） 8,910,003.206 7,023,504.921 3,981,396.292 6,004,735.31
    F#（Math.NET SVD） -2.4222e+18 7,023,759.697 3,981,504.454 5,984,256.00

    Python と Kotlin は RMSE も予測も 14 桁一致しますが、F# だけ 5 桁目で分かれます。 そして切片が -2.42e18。原著の 7.29e17 と同じ種類の異常値です。

    なぜこうなるのか¶

    どの実装も同じランク落ちした行列を解いており、解が一意に決まりません。 違いは「無数にある解のうちどれを返すか」です。

    SVD で擬似逆行列を作るとき、どれだけ小さい特異値をゼロとみなすか の 打ち切り閾値を決める必要があります。この設計行列（2434 × 278）の特異値を実際に見ると、 そこで何が起きているかがはっきりします。

    項目 実測値
    最大の特異値 118.843
    小さいほうから 2 番目 0.868
    最小の特異値 1.441e-15
    LAPACK の打ち切り閾値（max(m, n) × ε × σ_max） 6.423e-11
    条件数 8.247e+16

    理論上ちょうど 0 になるはずの特異値が、丸め誤差で 1.441e-15 として残っています。 そのすぐ上が 0.868 なので、ゼロと非ゼロの境目はきれいに分かれています。

    scikit-learn（内部の LAPACK gelsd）と Smile は、閾値 6.423e-11 を下回るこの特異値を 切り落とします。だから最小ノルムに近い素直な解が返ります。

    Math.NET の MultipleRegression.Svd はこの打ち切りを行いません。 1.441e-15 の逆数、つまり 約 7 × 10¹⁴ 倍 の増幅が係数に乗ります。 結果が -2.4e18 という切片です。

    原著の 7.29e17 も、当時の scikit-learn が同じ形で不安定な解を返していた ことを示しています。 つまり F# 版は、原著の出力を意図せず「忠実に」再現してしまいました。

    RMSE が 3,981,504 と、Python・Kotlin の 3,981,396 より わずかに悪い のも同じ理由です。 巨大な係数が互いに打ち消し合う解なので、丸め誤差が予測値に残ります。

    テストの書き方¶

    係数を突き合わせても意味がないので、当てはまりの良さで検証します。 Python・Kotlin より緩い許容誤差が必要でした。

    [<Fact>]
member _.``全特徴量モデルの RMSE は原著とほぼ同じ``() =
    // 原著の出力: Root Mean Squared Error (RMSE) of the model: 3981401.4927888927
    // 係数は一意でないが、当てはまりの良さは解の取り方によらずほぼ同じになる
    let error = rmse fixture.Prepared.Labels (predictAll fixture.Model fixture.Prepared)

    Assert.Equal(3981401.4927888927, error, 3981401.4927888927 * 1e-4)

    新物件の予測は 0.36% ずれるので、こちらはさらに緩くしています。

    [<Fact>]
member _.``新しい物件の予測は原著とほぼ同じ``() =
    // 原著の出力
    //   Predicted price for a house with size 1000 and 3 bedrooms: 6,006,016.00
    let predicted = predictNewHouse fixture.Model fixture.Prepared 1000.0 3 "Gachibowli"

    Assert.Equal(6006016.00, predicted, 6006016.00 * 1e-2)

    許容誤差を緩めた理由を残す

    「テストが通らないから許容誤差を広げた」で終わらせると、次に本当の劣化が起きても 気づけません。ここでは なぜ 3 言語で数値が分かれるのか を特定したうえで広げています。 根本的に直すなら pd.get_dummies(drop_first=True) に相当する処理で 地域列を 1 つ落とし、行列を正則にすればよいのですが、原著がそうしていないので直しません。

    テストの重い初期化はフィクスチャで¶

    データの読み込みと 2434 × 278 の SVD は、テストごとに走らせると無駄です。 xUnit の IClassFixture で 1 度だけ実行します。

    /// データの読み込みと SVD は重いので、クラスフィクスチャで 1 度だけ行う
type Fixture() =
    let frame = loadData ()
    let prepared = preprocess frame
    let model = fitAllFeatures prepared

    member _.Frame = frame
    member _.Prepared = prepared
    member _.Model = model

type Nb02HousePricesTests(fixture: Fixture) =
    interface Xunit.IClassFixture<Fixture>

    xUnit のフィクスチャはクラス構文が要るので、#01 のようなモジュールレベルの let ... [<Fact>] スタイルから クラスの member スタイル に切り替えました。 pytest の @pytest.fixture(scope="module") に比べると書式の変更が大きいところです。

    この章で F# が効いた場面・効かなかった場面¶

    場面 評価
    列名と値を同じ形で並べる 効いた — 対応関係が目で追える
    標準偏差の ddof 効いた — 暗黙変換が無く型で手が止まる
    特徴量を行列で持つ 効いた — SVD にそのまま渡せる
    Deedle の型指定 引き分け — 実行時変換なのでコンパイル時には守られない
    切片の扱い 効かなかった — Math.NET は自動で扱わず 1 の列を自分で足す
    SVD の数値安定性 効かなかった — 打ち切り閾値が無く係数が発散した
    テストのフィクスチャ 効かなかった — クラス構文が必要で書式が変わる

    同じ問題を 3 言語で解くと、ライブラリが黙ってやってくれている数値的な配慮が 見えてきます。この章ではそれが SVD の打ち切り閾値でした。
