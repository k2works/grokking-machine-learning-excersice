# 第 13 章 エンドツーエンドの実例 - 3 言語比較

原著第 13 章のエンドツーエンド実例を、Python・Kotlin・F# で実装した結果を比較します。各言語の詳細は [Python 版](../python/ch13.md)・[Kotlin 版](../kotlin/ch13.md)・[F# 版](../fsharp/ch13.md) を参照してください。

## 最終章が問うもの

本章に新しいアルゴリズムはありません。**10 章分の部品を組み合わせるだけ** です。だからこそ、これまでの設計判断がすべて跳ね返ってきます。

| 過去の判断 | 本章での結果 |
| :--- | :--- |
| 各章で `accuracy` という名前を使った | **名前が衝突した** |
| 第 4 章の分割を 1 次元の型で書いた | **再利用できなかった**（Kotlin・F#） |
| 第 9 章で `Impurity` を関数型にした | 第 12 章経由でそのまま流用できた |
| 第 11 章でラベルを +1/-1 にした | **変換コストが発生した** |
| モデルを第 1 引数に置き続けた | 部分適用で評価関数が作れた（F#） |

**統合の章は、設計の答え合わせです。**

## 名前の衝突をどう解いたか

`accuracy` は第 5・6・9・11・12 章に、`predict` は第 5・6・9・11 章に登場します。同じ概念に同じ名前を付けてきた自然な結果です。

```python
from grokking_ml.ch07_metrics import accuracy as matrix_accuracy
```

```kotlin
import ch07.accuracy as matrixAccuracy
```

```fsharp
// open せず完全修飾名で書く
GrokkingMl.Ch07Metrics.accuracy matrix
```

| 言語 | 機構 | 本章での選択 |
| :--- | :--- | :--- |
| Python | モジュール + `as` | 必要な名前だけ選んで別名を付ける |
| Kotlin | パッケージ + `import ... as` | インポート別名 |
| F# | モジュール（`open` で平坦化） | **`open` せず完全修飾名** |

**F# だけが「開かない」選択をしました。** `open` すると名前が平坦に入るため、4 つの章を同時に開くと後勝ちで壊れます。完全修飾名は冗長ですが、**どの章の関数かがコード上に残る** という副次的な利点がありました。統合の章としてはむしろ読みやすくなっています。

第 12 章で F# だけ `forestPredict` という接頭辞を付けたのも同じ問題への対処でした。**モジュールシステムの性質が、命名規則にまで影響します。**

## 型の一般性が再利用性を決めた

第 4 章の `train_test_split` を本章で再利用できたのは **Python だけ** でした。

```python
# 第 4 章の型ヒント（1 次元を想定）
def train_test_split(features: Sequence[float], labels: Sequence[int], ...)

# 第 13 章での呼び出し（多次元）
train_x, train_y, test_x, test_y = train_test_split(dataset.points, dataset.labels, ...)
```

**実装はインデックスの並べ替えしかしていないので、多次元の点でもそのまま動きます。** 型ヒントは合っていませんが、実行時には問題ありません。

Kotlin と F# では型が拒否しました。

```kotlin
fun trainTestSplit(features: List<Double>, labels: List<Double>, ...): Split
// 第 13 章の特徴量は List<List<Double>> なので渡せない
```

そのため両言語では本章で `splitDataset` を書き直しました。**同じ論理を 2 回書くことになった** わけです。

| 言語 | 再利用 | 理由 |
| :--- | :--- | :--- |
| Python | **できた** | 動的型付け（型ヒントは実行時に無効） |
| Kotlin | できなかった | `List<Double>` に固定されていた |
| F# | できなかった | 型注釈で `float list` に固定されていた |

これは **Python の勝利ではなく、設計の教訓** です。Kotlin ならジェネリクス（`fun <T> split(items: List<T>, ...)`）、F# なら型注釈を書かずに型推論へ委ねれば、どちらもジェネリックになっていました。

**「後で再利用するとき、型がどこまで一般的だったか」が問われます。** 静的型付け言語では、一般性を設計時に決める必要があります。Python はその判断を先送りできますが、代わりに **型ヒントが嘘をついたまま動く** 状態を許してしまいます。

## 欠損値を型で表す

「値がない」ことをどう表すかで、3 言語の書き味が分かれました。

```python
    raw = [None if row[name] == "" else parse_number(row[name]) for row in rows]
```

```kotlin
    val raw = rows.map { row -> row[name]?.takeIf { it.isNotEmpty() }?.let { parseNumber(it) } }
```

```fsharp
    let raw =
        rows
        |> List.map (fun row ->
            match valueOf name row with
            | "" -> None
            | text -> Some(parseNumber 0.0 text))
```

| 言語 | 型 | 欠損の連鎖 |
| :--- | :--- | :--- |
| Python | `float \| None` | 三項演算子 |
| Kotlin | `Double?` | **null 安全演算子の連鎖**（`?.takeIf`・`?.let`） |
| F# | `float option` | `match` で明示 |

**Kotlin の 1 行がもっとも情報量が多くなりました。** 「キーがない」「空文字」「数値でない」という 3 段階の欠損が、`?.` の連鎖として現れます。

F# は `match` で「空文字なら `None`」を明示します。冗長ですが、**判断がコードの表面に出ます。**

補完側も対応しています。

```python
    known = [value for value in column if value is not None]
```

```kotlin
    val filler = median(column.filterNotNull())
```

```fsharp
    let filler = column |> List.choose id |> median
```

F# の `List.choose id` は「`option` のリストから中身だけを取り出す」定型です。第 8 章の `Map.tryFind |> Option.defaultValue`、第 9 章の `List.choose` に続き、**`option` を扱う語彙が章をまたいで一貫しています。**

## 前処理で決まる 3 つのこと

3 言語とも同じ前処理を実装しました。それぞれ「やらないとどうなるか」が明確です。

| 処理 | やらないとどうなるか |
| :--- | :--- |
| 欠損補完（**中央値**） | 学習が落ちる。平均だと 1 件の外れ値が全欠損を汚染する |
| 正規化 | 値の大きい特徴量（収入）だけが効く |
| One-Hot | カテゴリに存在しない大小関係が生まれる |

とくに正規化は、**第 3 章の二乗トリック以来ずっと続いてきた性質** の帰結です。重みの更新量は特徴量に比例するため、年齢（18〜70）と収入（200〜900）を混ぜると収入が支配します。

3 言語とも「幅が 0 の列で 0 除算しない」ことをテストで固定しました。

```python
def test_normalize_handles_a_constant_column():
    # 幅が 0 の列で 0 除算しない
    assert normalize([5.0, 5.0, 5.0]) == [0.0, 0.0, 0.0]
```

**実データには必ず「全部同じ値の列」が紛れ込みます。**

## モデルの型を揃えずに比較する

3 つのモデル（第 6・9・12 章）は、共通のインターフェースを持ちません。後付けで基底クラスやインターフェースを導入することもできましたが、**3 言語とも「関数を受け取る」設計を選びました。**

```python
def evaluate(
    name: str,
    predict: Callable[[Point], int],
    probability: Callable[[Point], float],
    ...
```

```kotlin
fun evaluate(
    name: String,
    predict: (Point) -> Int,
    probability: (Point) -> Double,
    ...
```

```fsharp
let evaluate
    (name: string)
    (predictFn: Point -> int)
    (probabilityFn: Point -> float)
    ...
```

**既存のコードを 1 行も変えずに統合できました。** インターフェースを後から導入すると、第 6・9・12 章のすべてを書き換えることになります。

呼び出し側の書き味は言語で分かれます。

```python
    return evaluate("logistic", model.predict, model.predict_probability, points, labels)
```

```kotlin
    evaluate("logistic", { model.predict(it) }, { model.predictProbability(it) }, points, labels)
```

```fsharp
    evaluate
        "logistic"
        (GrokkingMl.Ch06LogisticRegression.predict logistic)
        (GrokkingMl.Ch06LogisticRegression.predictProbability logistic)
```

**F# は部分適用だけで済みます。** `predict logistic` が `Point -> int` になるので、ラムダが要りません。第 5 章から一貫して「モデルを第 1 引数に置く」設計にしてきたことが、最終章で効きました。

Python はバウンドメソッド（`model.predict`）をそのまま渡せます。Kotlin は既定引数を持つメソッドのため、ラムダで包む必要がありました。

## ラベル表現の統合コスト

第 11 章で SVM のためにラベルを +1/-1 に変え、第 12 章の AdaBoost もそれを引き継ぎました。本章で統合するとき、**AdaBoost だけ変換が必要になりました。**

```python
        lambda point: 1 if model.predict(point) == 1 else 0,
```

| 章 | ラベル | 本章での扱い |
| :--- | :--- | :--- |
| 6・9 章 | 0 / 1 | そのまま |
| 12 章 | **+1 / -1** | **0/1 へ変換** |

学習時にも逆向きの変換が要ります。

```python
    boosted = train_adaboost(
        train_x, [1 if label == 1 else -1 for label in train_y], rounds=5, max_depth=1
    )
```

**「その章では自然だった表現」が、統合の段階で費用になりました。** 第 11 章の時点では +1/-1 がヒンジ損失を簡潔にし、正しい判断でした。それでも系全体で見ると、境界に変換層が必要になります。

実務のシステムでも同じことが起きます。**部分最適な表現の選択は、統合コストとして後から現れます。**

## AUC が使える理由

決定木には確率がありません。AdaBoost のスコアは 0〜1 に収まりません。それでも 3 言語とも AUC を計算しています。

```python
        auc=auc(labels, [probability(point) for point in points]),
```

**AUC は順位さえ合っていればよい指標だからです。** 第 7 章で「AUC は閾値に依存しない」ことを実測で確かめました。

```python
def test_auc_ignores_the_threshold():
    scaled = [0.99, 0.98, 0.02, 0.01]
    compressed = [0.55, 0.54, 0.46, 0.45]
    assert auc(labels, scaled) == pytest.approx(auc(labels, compressed))
```

この性質のおかげで、**確率を出さないモデルも同じ土俵に乗せられます。** 決定木の 0/1 は順位情報がほとんどないので AUC が低めに出ますが、それも比較の材料になります。

## 実験結果

3 言語とも同じ規則（「40 歳未満かつ収入 400 超なら購入」）のデータ 40 件で試しました。

### Python

| モデル | 正解率 | 適合率 | 再現率 | F1 | AUC |
| :--- | ---: | ---: | ---: | ---: | ---: |
| ロジスティック回帰 | 0.667 | 0.333 | 0.333 | 0.333 | 0.741 |
| **決定木** | 0.750 | 0.500 | 1.000 | **0.667** | 0.833 |
| AdaBoost | 0.750 | 0.500 | 0.333 | 0.400 | 0.778 |

### Kotlin

| モデル | 正解率 | 適合率 | 再現率 | F1 | AUC |
| :--- | ---: | ---: | ---: | ---: | ---: |
| ロジスティック回帰 | 0.750 | 1.000 | 0.250 | 0.400 | **1.000** |
| 決定木 | 0.833 | 1.000 | 0.500 | 0.667 | 0.750 |
| **AdaBoost** | 0.917 | 1.000 | 0.750 | **0.857** | 1.000 |

### F# 版

| モデル | 正解率 | 適合率 | 再現率 | F1 | AUC |
| :--- | ---: | ---: | ---: | ---: | ---: |
| **ロジスティック回帰** | 0.833 | 0.800 | 0.800 | **0.800** | 0.857 |
| 決定木 | 0.833 | 1.000 | 0.600 | 0.750 | 0.800 |
| AdaBoost | 0.833 | 1.000 | 0.600 | 0.750 | 0.800 |

**勝者が 3 言語で違います。** 決定木（Python）、AdaBoost（Kotlin）、ロジスティック回帰（F#）。

これは実装の差ではありません。**擬似データの生成と訓練／テスト分割に使う乱数が言語ごとに違う** ためです。40 件のうちどの 12 件がテストに回るかで、数字は大きく動きます。

**この「揺れ」こそが本章のもっとも実務的な学びです。** テストデータが 12 件しかなければ、1 件の当たり外れが正解率を 0.083 動かします。「モデル A のほうが 3% 良い」という報告は、この規模では意味を持ちません。

第 4 章で訓練／テスト分割を導入したときは「過学習を見つけるため」でしたが、本章では **「その評価自体がどれだけ信頼できるか」** という問いが立ち上がります。実務では交差検証で複数の分割を試し、平均と分散を見ます。

## 指標が語ることも言語ごとに違った

Kotlin 版では、**AUC 1.000 と F1 0.400 が同居しました**（ロジスティック回帰）。

- AUC 1.000 = 順位付けは完璧（買う人ほど高いスコア）
- F1 0.400 = 閾値 0.5 での判定は不十分（再現率 0.250）

**モデルが悪いのではなく、閾値の選び方が悪い** のです。第 6 章で `threshold` を引数にしておいたこと、第 7 章で「閾値は運用上の選択」と学んだことが、ここで具体的な行動指針になります。

F# 版では 3 モデルの正解率がすべて 0.833 で並び、F1 で差が付きました。**正解率だけを見ていたら「3 モデルとも同じ」で終わっていました。**

第 7 章の主題（正解率だけでは足りない）が、最終章で 2 通りの形で再現しました。

## この章のまとめ

| 観点 | Python | Kotlin | F# |
| :--- | :--- | :--- | :--- |
| 強み | 型に縛られず前章の部品を流用できた | null 安全演算子で多段階の欠損処理が 1 行 | 部分適用で評価関数が作れる、戻り値の型を揃えて合成 |
| 注意点 | 型ヒントが嘘をついたまま動く | 型の一般性を設計時に決める必要がある | `open` できず完全修飾名になる |

13 章を通して、3 言語はそれぞれ違う場面で光りました。

| 章 | もっとも噛み合った言語と理由 |
| :--- | :--- |
| 3〜6 章 | 拮抗（状態の持ち方、種類を表す型、標準ライブラリの語彙） |
| 7 章 | **F#**（フィールド名必須、整数除算が型エラー） |
| 8 章 | 拮抗（Python の `Counter` は最短、F# は「無い」を型で表せる） |
| 9 章 | **F#**（判別共用体が木そのもの） |
| 10 章 | **F#**（`::` が逆伝播の向きに合致） |
| 11 章 | **F#**（カリー化された関数型にそのまま代入） |
| 12 章 | 拮抗（`zip` の制約は Kotlin の弱点、多重定義は強み） |
| 13 章 | **Python**（型に縛られず流用できた） |

**アルゴリズムの構造と言語機能が噛み合うと、コードは短くなるだけでなく定義そのものになります。** そして統合の段階では、静的型の厳密さがコストとして現れました。

どの言語が優れているかではなく、**何を守りたいときにどの言語が助けてくれるか** が本シリーズで見えたことです。
