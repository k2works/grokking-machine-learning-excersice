# #09 アプリ推薦の決定木（F#）

原著ノートブック: `Chapter_09_Decision_Trees/App_recommendations.ipynb`

6 人のユーザーの「端末」と「年齢」から、おすすめアプリを決定木で当てます。

**この章は、ライブラリを使わないという判断をしました。**
ML.NET の決定木は木の構造を外に出さないので、原著の見どころ（木の形）が消えてしまいます。
CART を自前で書いたところ、**原著とまったく同じ木** が得られました。

## ML.NET を使わなかった理由

ML.NET の決定木は `FastTree` です。名前のとおり **勾配ブースティング木** の実装で、
単体の決定木として使うには木を 1 本に制限する必要があります。

それでも足りません。**分割条件を読み出す API がありません。**
`FastTree` のモデルは予測のためのものであり、
`tree.plot_tree` や Smile の `dot()` に相当するものが用意されていないのです。

原著のこのノートブックは、`tree.plot_tree` を 2 回呼んで
**2 つの木を見比べる** ことが主眼です。木が見えないなら再現になりません。

```fsharp
/// **ML.NET の決定木は木の構造を外に出さない。** `FastTree` は勾配ブースティングの
/// 実装で、単体の決定木として使うには木を 1 本に制限する必要があり、それでも
/// 分割条件を読み出す API が無い。原著の見どころが「木の形」なので、
/// ここでは **CART を自前で実装** して形を取り出せるようにした。
```

[#03](nb03.md) の Lasso、[#06](nb06.md) のロジスティック回帰に続いて 3 度目の自前実装です。
F# はライブラリの手当てがいちばん薄い言語ですが、そのぶん **中身がよく見えます**。

## 判別共用体が決定木そのもの

```fsharp
/// 決定木。判別共用体で葉と節を表す
type Tree =
    /// 葉。予測するクラス
    | Leaf of prediction: string
    /// 節。特徴量としきい値、そして左右の部分木
    | Node of feature: string * threshold: float * left: Tree * right: Tree
```

**4 行で決定木の定義が終わります。** 「木は葉か、節（と 2 つの部分木）である」という
再帰的な定義が、そのまま型になります。

Python では `tree_.feature` / `tree_.threshold` / `tree_.children_left` という
**並行した配列**を添字で辿る形でした。Smile では DOT 文字列を正規表現で解析しました。
F# では **構造がそのまま値** です。

テストでパターンマッチが使えます。

```fsharp
[<Fact>]
let ``判別共用体が木の形をそのまま表す`` () =
    // Node と Leaf のパターンマッチで構造を直接確かめられる
    match fit numericDataset with
    | Node("Age", 20.0, Leaf "Atom Count", Node("Platform_iPhone", 0.5, right, left)) ->
        Assert.Equal(Leaf "Beehive Finder", right)
        Assert.Equal(Leaf "Check Mate Mate", left)
    | other -> failwith $"想定と違う木になった: {other}"
```

**木の形を 1 つのパターンで書き下せます。**
「根が Age の 20.0 分割、その左は Atom Count の葉、右は Platform_iPhone の節」が
そのまま読めます。

Python では `tree_.feature[0] == 0 and tree_.threshold[0] == 20.0 and ...` と
添字で条件を積むしかありません。

## しきい値の候補は中点

```fsharp
/// 分割の候補となるしきい値。隣り合う値の中点を使う。
///
/// scikit-learn も同じ規則で、`Age` が 15 と 25 のときに 20.0 を選ぶ。
let candidateThresholds (values: float[]) =
    values
    |> Array.distinct
    |> Array.sort
    |> Array.pairwise
    |> Array.map (fun (a, b) -> (a + b) / 2.0)
```

**`Array.pairwise` が「隣り合う組」を一発で作ります。**
`[12; 14; 15; 25; 32; 35]` から `[(12,14); (14,15); (15,25); ...]` を得て、
中点を取れば候補が揃います。

Python なら `zip(values, values[1:])`、Kotlin なら `zipWithNext()` に相当します。
名前は違いますが、3 言語とも 1 語で書ける操作です。

```fsharp
[<Fact>]
let ``候補のしきい値は隣り合う値の中点`` () =
    // 15 と 25 の間なら 20。scikit-learn も同じ規則
    Assert.Equal<float[]>([| 13.0; 14.5; 20.0; 28.5; 33.5 |], candidateThresholds (Array.map float ages))
```

候補は 5 つ。そのうち `20.0` が選ばれます。

## 同点は列の順に最初のものを選ぶ

[Python 版](../python/nb09.md) で見たとおり、`Platform_iPhone` と `Platform_Android` は
互いに裏返しなので、分割の良さが完全に同点になります。

scikit-learn は無作為に選びますが、自前実装では **決定的な規則** を選びました。

```fsharp
/// CART を再帰的に構築する。
///
/// 同点の分割候補が複数あるとき、**列の順に最初のものを選ぶ**。
/// scikit-learn は無作為に選ぶので、そこだけ規則が違う。決定的なぶん
/// 実行するたびに同じ木になる。
```

実装は `List.sortBy` に任せています。

```fsharp
|> List.sortBy (fun (impurity, _, _, _, _, _) -> impurity)
|> List.tryHead
```

**F# の `List.sortBy` は安定ソート** なので、同じ不純度なら元の順序（列の順）が保たれます。
`List.minBy` でも同じ結果になりますが、`sortBy` + `tryHead` のほうが
「同点なら先に来たほう」という意図が読み取りやすいと判断しました。

## 原著とまったく同じ木になった

この規則の結果、数値版は **原著と完全に一致** しました。

```fsharp
[<Fact>]
let ``数値版は原著とまったく同じ木になる`` () =
    // 原著の出力
    //   X[0] <= 20.0 （X[0] は Age）
    //   X[1] <= 0.5  （X[1] は Platform_iPhone）
    let tree = fit numericDataset

    Assert.Equal<(string * float) list>(
        [ "Age", 20.0; "Platform_iPhone", 0.5 ],
        splits tree
    )
```

原著が `X[1]`（= `Platform_iPhone`）を選んだのは、
その回の乱数がたまたまそうなっただけです。
こちらは **列の順に最初** という規則で、同じ結果に落ち着きました。

偶然の一致ですが、**規則が明示されているぶん、こちらのほうが再現できます**。

```fsharp
[<Fact>]
let ``学習は決定的で毎回同じ木になる`` () =
    // scikit-learn は同点の候補から無作為に選ぶため木の形が変わるが、
    // 列の順に最初のものを選ぶ規則にしたので毎回同じになる
    Assert.Equal(fit numericDataset, fit numericDataset)
```

**`Assert.Equal(tree, tree)` が書けるのも判別共用体のおかげ** です。
F# の判別共用体は構造的等価性を持つので、木全体を 1 行で比較できます。

## 3 言語の比較

| 実装 | 決定木の出どころ | 木の形 | 再現性 |
| :--- | :--- | :--- | :--- |
| Python | `DecisionTreeClassifier` | `tree_` の並行配列 | **実行のたびに変わる** |
| Kotlin | Smile `DecisionTree` | DOT 文字列を正規表現で解析 | 決定的 |
| **F#** | **自前の CART** | **判別共用体** | 決定的 |

木の形を扱う道具としては、**判別共用体がいちばん素直** でした。
配列の添字でも DOT 文字列でもなく、値そのものが木の形をしています。

一方で、ライブラリの恩恵は受けていません。
実データで枝刈りや欠損値処理が必要になれば、自前実装ではすぐ限界が来ます。
**教材の範囲だから成立している** ことは押さえておくべきです。

## この章で F# が効いた場面・効かなかった場面

| 場面 | 評価 |
| :--- | :--- |
| 木の表現 | **効いた** — 判別共用体 4 行で決定木の定義が終わる |
| 木の検証 | **効いた** — 形をパターンマッチ 1 つで書き下せる |
| 木の比較 | **効いた** — 構造的等価性で `Assert.Equal(tree, tree)` |
| しきい値の候補 | **効いた** — `Array.pairwise` が隣接組を一発で作る |
| 同点の扱い | **効いた** — 安定ソートで「列の順に最初」が保証される |
| ML.NET の決定木 | **効かなかった** — 木の構造を読み出せず、使えない |
| 実用性 | **効かなかった** — 枝刈りも欠損値処理も無い教材向け実装 |
