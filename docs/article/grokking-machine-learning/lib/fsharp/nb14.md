# #14 ニューラルネットワークで住宅価格を予測（F#）

原著ノートブック: `Chapter_10_Neural_Networks/House_price_predictions_neural_network.ipynb`

ニューラルネットワークを **回帰** に使う回です。
ハイデラバードの住宅データ 2518 件を 3 層のネットワークで予測します。

Accord.Neuro の出力は **シグモイドしか選べません**。
0〜1 しか返せないので、1000 万の桁の価格をそのまま学習させることはできません。
価格を写像してから学習し、予測を戻す形にします。

## 二段構えの変換

出力が 0〜1 に限られるので、変換を 2 段重ねました。

```fsharp
/// 平均と標準偏差。学習時と予測時で同じ値を使う必要がある
type Scaler =
    { Mean: float; Std: float }

    member this.Scale(value: float) = if this.Std = 0.0 then 0.0 else (value - this.Mean) / this.Std
    member this.Unscale(value: float) = value * this.Std + this.Mean
```

```fsharp
/// 標準化した価格を 0〜1 に写す。シグモイド出力が返せる範囲に合わせるため
let private toUnitRange (values: float[]) =
    let low = Array.min values
    let high = Array.max values
    values |> Array.map (fun v -> (v - low) / (high - low)), low, high
```

**1 段目で標準化、2 段目で 0〜1 に写す。** 予測時は逆順にたどります。

```fsharp
/// 全物件の価格を予測する。標準化と 0〜1 の写像を戻して円単位にする
let predict (network: ActivationNetwork, low: float, high: float) (scaled: Scaled) =
    scaled.X
    |> Array.map (fun row ->
        let unit = network.Compute(row).[0]
        scaled.PriceScaler.Unscale(unit * (high - low) + low))
```

`fit` が **タプル `(network, low, high)` を返す** のがこの設計の要です。
ネットワークだけ返すと、予測時に `low` と `high` を別途持ち回ることになります。

```fsharp
let fit (scaled: Scaled) (epochs: int) (seed: int) = ...
    network, low, high
```

F# はタプルを気軽に返せるので、
「モデルと、それを使うのに必要な情報」をひとまとめにできます。
Kotlin なら `data class` を 1 つ作るところです。

`Scaler` の `Scale` / `Unscale` が **対になっている** ことは、
テストで直接確かめました。

```fsharp
[<Fact>]
let ``標準化を戻すと元の価格になる`` () =
    // 予測を円単位に戻すために必要な操作
    for index in [ 0; 100; 2517 ] do
        Assert.Equal(data.Prices.[index], scaled.PriceScaler.Unscale scaled.Prices.[index], 6)
```

**変換が往復で戻ることを確かめないと、予測の桁が狂っていても気づけません。**

## Deedle の欠損で一度落ちた

データを読み込む段階でつまずきました。

```text
System.IndexOutOfRangeException : Index was outside the bounds of the array.
```

38 列を読んで行ごとの配列に組み直すところです。
**列によって長さが違いました。**

```fsharp
// Deedle の `Series.values` は欠損を飛ばすので、列ごとに長さが変わりうる。
// このデータには欠損があるため、0 で埋めてから配列にする
let columns =
    featureNames
    |> List.map (fun name ->
        frame.GetColumn<float>(name) |> Series.fillMissingWith 0.0 |> Series.values |> Array.ofSeq)
```

**`Series.values` は欠損を黙って飛ばします。** 2518 行のはずが、
欠損のある列だけ 2500 行になる、といったことが起きます。

[#02](nb02.md) では特定の数値列だけを読んでいたので気づきませんでした。
**全列を読んで初めて表面化した** 問題です。

pandas は欠損を `NaN` として残すので、行数がずれることはありません。
「欠損をどう表すか」の設計思想の違いが、こういう形で出ます。

## 標準化すれば原著より大きく良くなる

| エポック | RMSE |
| ---: | ---: |
| 10（原著と同じ） | **492 万** |
| 100 | 389 万 |
| 300 | **319 万** |

原著の `evaluate` は **554 万** です。

```fsharp
[<Fact>]
let ``原著の10エポックでも基準を大きく下回る`` () =
    // 原著と同じ 10 エポック。RMSE 約 492 万で、原著の 554 万より良い
    Assert.True(rmse (fit scaled OriginalEpochs 0) data scaled < baselineRmse data)
```

**原著と同じ 10 エポックで、すでに原著より良い結果** が出ています。

理由は前処理です。原著は標準化していません。
こちらは標準化に加えて 0〜1 への写像まで掛けているので、
**学習が非常に安定します**。

Adam のような賢い最適化が無いぶん前処理で補ったら、
かえって良くなったという形です。

## 3 言語の比較

| 項目 | Python（Keras） | Kotlin（Smile） | F#（Accord） |
| :--- | :--- | :--- | :--- |
| 出力層 | `Dense(1)`（恒等） | `Layer.mse(1, LINEAR)` | シグモイドのみ |
| 前処理 | **なし** | 標準化 | 標準化 + 0〜1 写像 |
| 標準化しないと | 動く | **10²⁹ に発散** | そもそも表現できない |
| 10 エポック後 | — | 797 万 | **492 万** |
| 十分な学習後 | 554 万 | 490 万 | **319 万** |

**3 言語とも、前処理の必要度が違います。**
Keras は何もしなくても動き、Smile は標準化が要り、Accord は写像まで要る。

そして **前処理をきちんとやったほうが結果が良い**。
原著の 554 万という数字は、前処理を省いた代償でもあります。

[#13](nb13.md) では「Dropout が無いと過学習する」と書きました。
今回は逆に「前処理をすると良くなる」です。
**ライブラリが肩代わりしている部分を自分でやると、
良くなることも悪くなることもある** と分かります。

## この章で F# が効いた場面・効かなかった場面

| 場面 | 評価 |
| :--- | :--- |
| モデルと変換係数 | **効いた** — タプルで返せて型を増やさずに済む |
| 変換の往復 | **効いた** — `Scale` / `Unscale` を対で持ちテストで確認 |
| 前処理の効果 | **効いた** — 結果として原著を上回った |
| 出力層 | **効かなかった** — シグモイドしか選べず 2 段の写像が要る |
| Deedle の欠損 | **効かなかった** — `Series.values` が欠損を飛ばして行数がずれる |
