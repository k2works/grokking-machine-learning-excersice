## 欠損を `option` で表す

pandas は欠損を `NaN` で表しますが、F# には `option` があります。

```fsharp
type Passenger =
    { Survived: int
      Pclass: int
      Sex: string
      Age: float option
      SibSp: int
      Parch: int
      Fare: float
      Embarked: string option }
```

Kotlin の `Double?` と役割は同じですが、**`option` は普通の型** です。
`Array.choose` に渡せば欠損が自動的に落ちます。

```fsharp
let medianAge (data: Passenger[]) =
    let ages = data |> Array.choose (fun p -> p.Age) |> Array.sort
```

`Array.choose` は `option` を返す関数を取り、`Some` だけを集めます。
`mapNotNull` にあたるものを言語が最初から持っているので、
「欠損を落として集計する」が 1 行です。

埋めるほうも `defaultArg` があります。

```fsharp
    raw
    |> Array.map (fun p ->
        { p with
            Age = Some(defaultArg p.Age median)
            Embarked = Some(defaultArg p.Embarked "U") })
```

`{ p with ... }` でレコードの一部だけを差し替えられるのは、
Kotlin の `copy` と同じです。

## Deedle の欠損は `OptionalValue`

Deedle は独自の `OptionalValue` を使うので、変換が要ります。

```fsharp
let private optionalFloat (series: Series<int, float>) index =
    match series.TryGet index with
    | OptionalValue.Present value -> Some value
    | _ -> None
```

**パターンマッチで書けるので、変換の意図がそのまま読めます。**
Kotlin 版は `as? String` で受けようとして、
型推論の食い違いから「全件欠損」という誤った結果を静かに得ていました。

こちらは `Series<int, string>` と型を明示して取るので、
食い違えばコンパイルか実行時に必ず止まります。

```fsharp
let private optionalString (series: Series<int, string>) index =
    match series.TryGet index with
    | OptionalValue.Present value when not (System.String.IsNullOrWhiteSpace value) -> Some value
    | _ -> None
```

`when` ガードで「空白だけの値も欠損とみなす」を足しました。
CSV の欠損は空文字列で来ることがあるためです。

## 分割の件数を合わせるには `ceil` が要る

```fsharp
    // 原著は 6:4 に切り、その 4 をさらに半分ずつにする。
    // scikit-learn は `test_size` の側を **切り上げる**（ceil）ので、
    // 891 -> 534 / 357、357 -> 178 / 179 になる
    let restSize = int (ceil (float prepared.Size * 0.4))
    let trainSize = prepared.Size - restSize
    let testSize = int (ceil (float restSize * 0.5))
    let validationSize = restSize - testSize
```

`float prepared.Size * 0.4` と **明示的に変換** しないと通りません。
[#16](nb16.md) で見たとおり、F# は暗黙の数値変換をしません。

うるさく感じますが、ここでは助かりました。
`prepared.Size * 0.4` を許す言語なら、`Size` が `int` のまま
整数演算になる可能性を心配する必要があります（Kotlin なら実際にそうなります）。

## 中身は一致しない

```fsharp
/// 原著と同じ件数（534 / 178 / 179）にするが、**同じ行が同じ組に入る
/// わけではない**。scikit-learn の並べ替えは .NET では再現できない。
```

[#17](nb17.md) で確かめたとおり、乱数列は言語をまたげません。
そのうえ .NET の `System.Random` は **.NET Core 3.0 で実装が変わっている** ので、
同じ .NET でも版によって違います。

だからモデルの成績は一致しません。
**一致するのは前処理と件数まで** と最初に決めて、そこに集中しました。

```fsharp
[<Fact>]
let ``同じ種なら分割は再現する`` () =
    // Accord と違い、System.Random は種を渡せば決定的
    let first = split prepared 100
    let second = split prepared 100

    Assert.Equal<int[]>(first.Validation.Y, second.Validation.Y)
```

原著と一致しなくても、**自分の実装が決定的であること** は確かめられます。
[#19](nb19.md)・[#20](nb20.md) で Accord と Smile の非決定性に痛い目に遭ったので、
今回は最初からこのテストを書きました。

## `var_smoothing` の意味

Accord の `NaiveBayes` は離散値しか扱えないので、
ガウシアン素朴ベイズを自前で書きました。

```fsharp
/// scikit-learn の `GaussianNB` に対応する。
/// **`var_smoothing`（全特徴量の最大分散 × 1e-9）を足すのが要点**である。
/// one-hot の列は分散がごく小さいので、固定値を足すだけでは正解率が崩れる。
```

[Kotlin 版](../kotlin/nb22.md) で先に踏んだ罠です。
one-hot の列は分散がほぼ 0 になり、固定値の下駄では足りません。

```fsharp
    let smoothing =
        1e-9 * ([ 0 .. featureNames.Length - 1 ] |> List.map varianceOfColumn |> List.max)
```

**`1e-9` という数字ではなく、「全特徴量の最大分散に比例させる」ことが本質** です。
scikit-learn のドキュメントには
「Portion of the largest variance of all features that is added to variances」
と書いてあり、まさにそのとおりでした。

**既定値を写すのではなく、定義を読む。** このシリーズで繰り返し必要になった態度です。

## 3 つに絞った

```fsharp
/// 原著が試す 7 つのうち **3 つ** を学習する。名前 -> 予測関数を返す。
///
/// 木系の 4 つ（決定木・ランダムフォレスト・勾配ブースティング・AdaBoost）を
/// 落としたのは、[#20](Nb20EnsembleSpam.fs)・[#21](Nb21GradientBoosting.fs) の
/// 自前実装が **2 特徴量ぶんの決め打ち** で、20 列には広げていないためである。
/// ここで確かめたいのは前処理と分割の再現なので、そちらに絞った。
```

[#20](nb20.md)・[#21](nb21.md) で書いた木は、
その回のデータに合わせて特徴量の数を決め打ちしていました。
20 列に一般化するのは可能ですが、**この回で確かめたいことではありません**。

落とした理由を書き残すのは、[#11](nb11.md) で
「原著の 3 つの制限のうち Smile には 1 つ無い」と書いたときと同じ考え方です。
**やらなかったことも、理由込みで記録します。**

## シリーズを終えて

22 本を 3 言語で書き切りました。F# 側を振り返ると、
**型が厳しいことが繰り返し助けになりました**。

- [#12](nb12.md) の整数除算：Kotlin は黙って 0 を返し、F# は型エラーで止まった
- [#16](nb16.md) の `6 * a`：リテラルにも小数点が要る
- #22 の Deedle：型を明示して取るので、食い違えば必ず止まる

一方、**書き下ろす場面が最も多かったのも F# でした**。
ライブラリのカバー範囲が Python や JVM より狭いためです。
しかし [#20](nb20.md) の AdaBoost、[#21](nb21.md) の勾配ブースティングでは、
**自前で書いたほうが原著とよく一致しました**。
ライブラリの既定値や近似解法が挟まらないぶん、本の説明どおりに動くからです。

「ライブラリを使う」シリーズで、いちばん再現できたのが自前実装だったというのは、
皮肉ですが正直な結果です。
