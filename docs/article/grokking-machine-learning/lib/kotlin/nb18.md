# #18 類似度行列で RBF カーネルを分解する（Kotlin）

原著ノートブック: `Chapter_11_Support_Vector_Machines/Calculating_similarities.ipynb`

RBF カーネルの正体を **手で計算して見せる** 回です。
7 点のデータに対して全対の類似度を計算し、7 列の特徴量を足してから
**線形** SVM を当てます。

計算部分は **原著の出力と 16 桁まで一致** しました。
一方、SVM の係数だけは比べられません。Smile が公開していないためです。

## 類似度は素直に書ける

```kotlin
    fun similarity(a: DoubleArray, b: DoubleArray): Double {
        val dx = a[0] - b[0]
        val dy = a[1] - b[1]
        return exp(-dx * dx - dy * dy)
    }
```

原著は `(x[0]-y[0])**2` と冪乗で書きますが、Kotlin に `**` はありません。
`dx * dx` にしています。**掛け算のほうが速く、精度も同じ** なので実害はありません。

```kotlin
    @Test
    fun `類似度は距離の2乗で決まる`() {
        val origin = doubleArrayOf(0.0, 0.0)
        // exp(-||x-y||^2)。距離 1 なら exp(-1)
        assertEquals(exp(-1.0), similarity(origin, doubleArrayOf(1.0, 0.0)), 1e-15)
        // 距離 √2 なら exp(-2)
        assertEquals(exp(-2.0), similarity(origin, doubleArrayOf(1.0, 1.0)), 1e-15)
        // 原著のセルに残っている出力 1.522997974471263e-08 は (0,0) と (3,3) の類似度
        assertEquals(1.522997974471263e-08, similarity(origin, doubleArrayOf(3.0, 3.0)), 1e-23)
    }
```

原著の `similarity` を定義したセルに、なぜか `1.522997974471263e-08` という
出力が残っています。`exp(-18)` を逆算すると `(0, 0)` と `(3, 3)` の類似度でした。
**消し忘れた実験の跡** です。Kotlin でも同じ値が出ます。

## 手書きの予測式も 16 桁一致する

```kotlin
    fun svmRbfPrediction(newPoint: DoubleArray): Double =
        POINTS.indices.sumOf { similarity(newPoint, POINTS[it]) * PREDICTION_SIGNS[it] }
```

```kotlin
    @Test
    fun `手書きの予測式は原著と桁まで一致する`() {
        // 原著の出力をそのまま並べたもの
        val expected = listOf(
            -0.7293294335267746,
            -0.9749464141121803,
            -0.9749464141121804,
            0.9884223081103513,
            0.9884223081103514,
            0.8650001793912898,
            0.8650001793912898,
        )

        assertEquals(expected, trainingPredictions())
    }
```

**`assertEquals` に許容誤差を渡していません。完全一致です。**

原著は `np.dot` を使い、こちらは `sumOf` で先頭から順に足しています。
BLAS の内積は順序を変える場合があるので不一致もありえましたが、
7 要素では順序どおりに足されたようです。

## Smile の SVM は係数を公開しない

原著は `svm.coef_` で 9 個の係数を印刷します。これは再現できませんでした。

```kotlin
    @Test
    fun `SVMは7点すべてを正しく分類する`() {
        // Smile の線形 SVM は **重みベクトルを公開しない**。
        // `SVM.fit` が返すのは無名の Classifier で、predict しかできない。
        // 原著の svm.coef_（9 個の係数）とは突き合わせられないので、
        // 代わりに分類結果で確かめる
        val model = fit()
        val predicted = features().map { if (model.predict(it) == 1) 1 else 0 }

        assertEquals(Y.toList(), predicted)
    }
```

`SVM.fit` が返すのは `smile.classification.SVM$1`、つまり **無名クラス** です。
公開メソッドを列挙すると `predict` 系と `classes` / `numClasses` だけで、
重みを取り出す口がありません。

scikit-learn の `coef_` / `intercept_` のように
**学習した中身をすべて属性で見せる** のは、実は当たり前ではありません。
Smile は「モデルは予測するもの」という設計で、内部を見せない方針です。

**検証できないなら、検証できる別のことを測る。** ここでは
「7 点すべてを正しく分類する」に置き換えました。

## ラベルは ±1 でなければならない

```kotlin
     * Smile の `SVM.fit` は **ラベルを ±1 で要求する**（[#04][Nb04Perceptron] と同じ）。
     * 0 のままだと `Invalid label: 0` で落ちるので、-1 に読み替えて渡す。
```

[#04](nb04.md) で踏んだのと同じ罠です。
scikit-learn は 0 / 1 をそのまま受け取りますが、Smile は ±1 を要求します。

幸い **例外で止まってくれる** ので、気付かないまま間違えることはありません。
[#15](nb15.md) の `MLP.update` のように黙って学習しないよりずっと良い挙動です。

## 特徴量を組み立てる

```kotlin
    fun features(): Array<DoubleArray> {
        val matrix = similarityMatrix()
        return Array(SIZE) { row ->
            DoubleArray(FEATURE_COUNT) { column ->
                when (column) {
                    0 -> X1[row]
                    1 -> X2[row]
                    else -> matrix[column - 2][row]
                }
            }
        }
    }
```

pandas なら `data['Sim0'] = column` と列を足すだけですが、
Kotlin には列を追加する DataFrame 操作を挟まず、**必要な形の 2 次元配列を直接作る**
ほうが読みやすくなりました。Smile が求めるのも `Array<DoubleArray>` です。

`when (column)` で 0 と 1 だけ特別扱いし、残りを類似度に回します。
9 列の中身がこの 5 行で全部見えるのは、素の配列で組む利点です。
