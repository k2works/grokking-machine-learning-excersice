## 境界の型を拡張する

[#04](nb04.md) の `Boundary` とほぼ同じですが、`predict` が `Int` から `Double` に、
`error` が `logLoss` に変わります。

```kotlin
/** 分離直線。重みとバイアスの組 */
data class Boundary(val weights: DoubleArray, val bias: Double) {
    /** 重み付き和にバイアスを足したもの */
    fun score(features: IntArray): Double =
        bias + weights.indices.sumOf { weights[it] * features[it] }

    /** 予測確率。0 / 1 ではなく 0〜1 の連続値を返す */
    fun prediction(features: IntArray): Double = sigmoid(score(features))

    /** 対数損失。当たっていても 0 にはならず、確信の度合いで連続的に変わる */
    fun logLoss(features: IntArray, label: Int): Double {
        val pred = prediction(features)
        return -label * ln(pred) - (1 - label) * ln(1 - pred)
    }

    override fun equals(other: Any?): Boolean =
        other is Boundary && weights.contentEquals(other.weights) && bias == other.bias

    override fun hashCode(): Int = 31 * weights.contentHashCode() + bias.hashCode()
}
```

`-label * ln(pred)` の `label` は `Int` ですが、`ln(pred)` が `Double` なので
結果は `Double` になります。**Kotlin は数値型を暗黙に広げる** ので、
`toDouble()` を書かずに済みます。F# ではここが型エラーになります。

`equals` を自前で書く必要があるのは [#04](nb04.md) と同じです。
`data class` に配列を入れた時点で、生成される `equals` は参照比較になります。

## 原著の「別の書き方」は対数損失と一致しない

[Python 版](../python/nb05.md) で導出したとおり、
原著の `soft_relu((pred - label) * score)` は対数損失と一致しません。
`pred` が 0〜1 の確率なので、`(pred - label)` が ±1 にならないためです。

正しい形は `(1 - 2 * label)` を掛けます。Kotlin では 2 つを並べて実装しました。

```kotlin
/**
 * 原著が「対数損失の別の書き方」として示す式。
 *
 * **実際には対数損失と一致しない。** `pred` は 0〜1 の確率なので、
 * `(pred - label)` は -1 か +1 ではなく中間の値になる。
 * スコアが 0 のときだけ両者が一致する。詳しくは記事を参照。
 */
fun alternateLogLossOriginal(boundary: Boundary, features: IntArray, label: Int): Double =
    softRelu((boundary.prediction(features) - label) * boundary.score(features))

/**
 * 対数損失と厳密に等しい「別の書き方」。
 *
 * ラベルが 0 なら +1、1 なら -1 を掛ける。つまり `(1 - 2 * label)`。
 */
fun alternateLogLoss(boundary: Boundary, features: IntArray, label: Int): Double =
    softRelu((1 - 2 * label) * boundary.score(features))
```

**`(1 - 2 * label)` は `Int` のままです。** `label` が 0 なら 1、1 なら -1 という
整数演算で済み、`score` を掛ける段階で `Double` に広がります。
意図が「符号を反転させる」ことなので、整数のまま書けるのは読みやすさに効きます。

一致しないこと・一致することの両方をテストで固定します。

```kotlin
@Test
fun `正しい別の書き方は対数損失と厳密に一致する`() {
    // ラベルが 0 なら +1、1 なら -1 を掛ける。つまり (1 - 2 * label)
    for (i in FEATURES.indices) {
        for (label in listOf(0, 1)) {
            assertEquals(
                start.logLoss(FEATURES[i], label),
                alternateLogLoss(start, FEATURES[i], label),
                1e-12,
            )
        }
    }
}
```

## Smile の LogisticRegression

`smile.classification.LogisticRegression` はありますが、
**`fit` という名前のメソッドがありません**。

```text
public static LogisticRegression$Binomial binomial(double[][], int[], double, double, int);
public static LogisticRegression$Multinomial multinomial(double[][], int[], double, double, int);
```

二値分類と多値分類でメソッドが分かれており、
それぞれ `binomial` / `multinomial` という名前です。
`LogisticRegression.fit(...)` と書いてコンパイルエラーになり、
`javap` で中身を見て気づきました。

```kotlin
/**
 * 同じ問題を Smile の [LogisticRegression] に解かせる。
 *
 * scikit-learn は既定で L2 正則化を掛けるが、Smile の `lambda` の既定は 0 である。
 * 原著と比較できるよう、scikit-learn の既定 `C = 1.0` に対応する
 * `lambda = 1.0 / データ数` を明示的に渡す。
 */
fun fitWithSmile(
    features: Array<IntArray> = FEATURES,
    labels: IntArray = LABELS,
    lambda: Double = 1.0 / FEATURES.size,
): LogisticRegression {
    val x = Array(features.size) { row ->
        DoubleArray(features[row].size) { features[row][it].toDouble() }
    }
    // Smile は二値と多値でメソッドが分かれている。二値は binomial
    return LogisticRegression.binomial(x, labels, lambda, 1e-6, 500)
}
```

### 正則化の既定値が違う

scikit-learn の `LogisticRegression` は **既定で L2 正則化を掛けます**（`C=1.0`）。
Smile の `lambda` は既定が 0 で、正則化なしです。

同じ「ロジスティック回帰」という名前でも、**既定で解いている問題が違います**。
scikit-learn に慣れていると、Smile では重みが伸び放題になって驚くことになります。

ここでは `lambda = 1.0 / データ数` を明示して、scikit-learn の `C=1.0` に
おおよそ対応させました。「おおよそ」と書いたのは、
両者の正則化項のスケールの取り方が完全には一致しないためです。
係数を突き合わせても意味がないので、テストは予測で行います。

```kotlin
@Test
fun `Smile のロジスティック回帰も全点を正しく分類する`() {
    // 原著 scikit-learn の出力: Logistic Regression Predictions: [0 0 0 0 1 1 1 1]
    assertEquals(LABELS.toList(), predictWithSmile(fitWithSmile()))
}
```

Smile の `binomial` はラベルを **0 / 1 で受け取ります**。
[#04](nb04.md) の SVM が ±1 を要求して実行時に落ちたのとは違い、こちらはそのまま渡せます。
**同じライブラリのなかで規約が揃っていない** のは、使う側からすると厄介です。

| Smile のクラス | ラベルの表現 |
| :--- | :--- |
| `SVM` | -1 / +1（0 を渡すと実行時例外） |
| `LogisticRegression.binomial` | 0 / 1 |

## 収束はパーセプトロンより遅い

種を固定した手書きループの到達点です。

| エポック | 重み | バイアス | 予測 |
| ---: | :--- | ---: | :--- |
| 500 | [0.750, 0.415] | -0.932 | 2 点誤り |
| 5,000 | [1.723, 1.149] | -3.966 | 1 点誤り |
| **20,000** | [2.832, 2.059] | -7.568 | **全点正解** |
| 50,000 | [3.692, 3.045] | -10.890 | 全点正解 |

Python は 5,000 エポックで揃いましたが、Kotlin は 20,000 かかりました。
**乱数列が違うので、どの点が何回選ばれるかが変わる** ためです。
どちらも「パーセプトロンの 500 エポックより明らかに遅い」という性質は同じです。

50,000 エポックの重みが 20,000 の約 1.3 倍になっています。
比 $w_0 : w_1$ はほぼ 1 : 0.8 のまま変わらず、大きさだけが増え続けます。
対数損失が 0 にならないので、**分離できたあとも「もっと確信を持て」と押し続ける**
という性質がそのまま出ています。

```kotlin
@Test
fun `学習後は全点を正しく分類できる`() {
    // 対数損失は当たっていても 0 にならないので、パーセプトロンより
    // 収束に時間がかかる。この乱数列では 20000 エポックで揃う
    val result = logisticRegressionAlgorithm(epochs = 20000)

    assertEquals(
        LABELS.toList(),
        FEATURES.map { if (result.boundary.prediction(it) >= 0.5) 1 else 0 },
    )
}
```

「20000 エポックで揃う」という数字はこの乱数列に固有です。
テストのコメントにその旨を書いて、将来の読み手が
「なぜ 20000 なのか」で迷わないようにしました。

## この章で Kotlin が効いた場面・効かなかった場面

| 場面 | 評価 |
| :--- | :--- |
| 数値型の暗黙変換 | **効いた** — `Int` と `Double` が混ざっても `toDouble()` が要らない |
| `(1 - 2 * label)` | **効いた** — 整数のまま符号反転を書ける |
| 境界の型 | **効いた** — #04 の `Boundary` をほぼそのまま拡張できた |
| `data class` + 配列 | **効かなかった** — #04 と同じく `equals` を自前で書く |
| Smile のメソッド名 | **効かなかった** — `fit` が無く `binomial` / `multinomial` |
| 正則化の既定値 | **効かなかった** — scikit-learn と違い既定で正則化なし |
| ラベルの表現 | **効かなかった** — `SVM` は ±1、`LogisticRegression` は 0 / 1 |

Smile は「アルゴリズムは揃っているが、API の規約が揃っていない」という印象です。
scikit-learn の `fit` / `predict` がすべてのモデルで同じ形をしていることの
ありがたさが、比べると分かります。
