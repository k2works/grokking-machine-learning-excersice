# #16 ネットワークの境界を描く（Kotlin）

原著ノートブック: `Chapter_10_Neural_Networks/Plotting_Boundaries.ipynb`

**学習をしない回** です。重みを手で決めたネットワークを 2 つ作り、
その境界を描いて「1 層目は直線、2 層目は曲がる」ことを見せます。

原著の出力は図が 5 枚だけで、数字が 1 つも出ません。
[Python 版](../python/nb16.md) と同じく **境界を数値に直して** 検証しました。
ライブラリは一切使いません。**Kotlin の関数型がそのまま原著の高階関数に対応する** 回です。

## 関数を渡す

原著は `plot_function(line_1)` と関数をそのまま渡します。
Kotlin では関数参照 `::line1` と関数型 `(Double, Double) -> Double` で書けます。

```kotlin
    /** 原著の `h(x, y) = f(x, y) >= 0.5`。境界はこの判定で決まる */
    fun classify(f: (Double, Double) -> Double, a: Double, b: Double): Int =
        if (f(a, b) >= DECISION_THRESHOLD) 1 else 0

    /** 8 点それぞれの予測 */
    fun predictions(f: (Double, Double) -> Double): List<Int> =
        ALIEN_DATASET.map { classify(f, it.aack.toDouble(), it.beep.toDouble()) }
```

```kotlin
        assertEquals(listOf(0, 0, 0, 1, 1, 1, 1, 1), predictions(::line1))
        assertEquals(listOf(0, 1, 0, 0, 1, 1, 1, 1), predictions(::line2))
```

ただし **戻り値の型を揃える必要があります**。
原著の `line_1` は `int` を返し、`nn_with_sigmoid` は `float` を返します。
Python は気にしませんが、Kotlin では同じ関数型に入れられません。

```kotlin
    /** 1 層目の 1 つ目のニューロン。重み (6, 10)、バイアス -15 */
    fun line1(a: Double, b: Double): Double = step(6 * a + 10 * b - 15).toDouble()
```

`step` は `Int` を返すので `.toDouble()` を付けます。
**型を揃える手間と引き換えに、渡し間違いはコンパイル時に止まります。**

## 使わない引数を明示する

```kotlin
    /** 常に 1 を返すニューロン。入力を一切見ない */
    @Suppress("UNUSED_PARAMETER")
    fun bias(a: Double, b: Double): Double = 1.0
```

`bias` は入力を見ませんが、他の関数と同じ型でなければ渡せないので
引数を持ちます。Kotlin は未使用引数を警告するので、
**意図的であることを `@Suppress` で示します**。

F# ならワイルドカード `_` で書けて、抑制の注釈は要りません。
Kotlin にトップレベル関数の引数名を `_` にする書き方はありません。

## 2 層目は AND

```kotlin
    @Test
    fun `2層目はANDになっている`() {
        // 1 層目の出力は 0 か 1。その和が 1.5 以上になるのは両方 1 のときだけ
        assertEquals(1.0, nnWithStep(1.0, 1.0))
        assertEquals(0.0, nnWithStep(2.0, 0.0)) // line2 だけが 1
        assertEquals(0.0, nnWithStep(0.0, 2.0)) // line1 だけが 1
    }
```

バイアス `-1.5` の 1 つの数が論理演算の種類を決めています。
`-0.5` なら OR、`-1.5` なら AND です。

## シグモイド版は 1 点だけ外す

Python 版と同じ結果になりました。

```kotlin
    @Test
    fun `シグモイド版は1点だけ外す`() {
        // aack=1 beep=1 の点だけ 0 と答える。正解は 1
        assertEquals(listOf(0, 0, 0, 0, 0, 1, 1, 1), predictions(::nnWithSigmoid))
        assertEquals(0.875, accuracy(::nnWithSigmoid))
    }
```

```kotlin
        assertEquals(0.4905304218, nnWithSigmoid(1.0, 1.0), 1e-9)
```

**0.4905。しきい値 0.5 をわずかに下回ります。**
図では境界線の真上に見える点が、実際には外側にありました。
詳しくは [Python 版](../python/nb16.md) に書いています。

Kotlin の `exp` は `java.lang.Math.exp` を呼ぶだけなので、
**10 桁目まで Python と一致します**。ここは移植で疑う必要がありませんでした。

## NumPy の `arange` は誤差を累積する

一方、**格子の作り方は一致しませんでした**。

```kotlin
    /** 原著の `np.arange(-0.5, 3, 0.005)` と同じ刻み */
    fun axis(): DoubleArray {
        val count = Math.ceil((GRID_MAX - GRID_MIN) / GRID_STEP).toInt()
        return DoubleArray(count) { GRID_MIN + it * GRID_STEP }
    }
```

要素数 700 は一致します。しかし **値が微妙に違います**。

```kotlin
        // こちらは `min + i * step` なのでちょうど 0.0 になる。
        // NumPy の arange は 4.44e-16 になる
        assertEquals(0.0, axis()[100], 0.0)
```

`-0.5 + 100 × 0.005` は、素直に計算すればちょうど 0.0 です。
NumPy の `arange` は **4.44e-16** を返します。誤差を累積する実装だからです。

結果、格子の割合が 5 桁目でずれます。

| | Python | Kotlin |
| :--- | ---: | ---: |
| `regionRatio(nnWithStep)` | 0.5544327 | **0.5543918** |

49 万点のうち **約 20 点だけ** 判定が違います。
`6a + 10b - 15 = 0` のような格子点がちょうど境界に乗るとき、
4.44e-16 の差が `>= 0` の判定を裏返します。

**どちらが正しいという話ではありません。**
「境界ちょうどの点をどちらに入れるか」は、この問題では決まっていないからです。
テストは 4 桁で比較し、ずれる理由をコメントに残しました。

```kotlin
        // Python 版は 0.5544327、Kotlin 版は 0.5543918。**格子の作り方が違う**。
        // NumPy の `arange` は誤差を累積するので、`-0.5 + 100 * 0.005` が
        // 0.0 ではなく 4.44e-16 になる。境界ちょうどの点の判定がそこで分かれ、
        // 49 万点のうち約 20 点だけ食い違う
        assertEquals(0.5544, regionRatio(::nnWithStep), 1e-4)
```

**8 点の判定はすべて一致します。** ずれるのは格子上の統計だけです。

## まとめ

| 項目 | 原著と一致するか |
| :--- | :--- |
| データの 8 点 | 完全一致 |
| 5 つの関数の定義 | 完全一致 |
| シグモイドの値（10 桁） | Python と完全一致 |
| 階段版が 8 点すべて正解 | 一致 |
| シグモイド版の正解率 0.875 | Python と一致 |
