# #15 手書き数字を認識する（Kotlin）

原著ノートブック: `Chapter_10_Neural_Networks/Image_recognition.ipynb`

MNIST の手書き数字 7 万枚を、[#13](nb13.md) と同じ形のネットワークで分類します。
原著はテストセットで **正解率 0.942** を出します。

この回で分かったことは 2 つです。

1. **Kotlin には MNIST のローダが無い** ので、`.npy` を自前で読む必要がある
2. **Smile の `MLP.update` にデータをまるごと渡すと、何も学習しない**（エラーは出ない）

## `.npy` を自前で読む

原著の `keras.datasets.mnist.load_data()` は、`mnist.npz` を取ってきて展開するだけです。
`.npz` は `.npy` を集めた ZIP なので、ZIP を開いて `.npy` を解析すれば同じデータが得られます。

```kotlin
    /**
     * NumPy の `.npy` 形式を読む。
     *
     * 形式は単純である。
     * - 6 バイトの magic `\x93NUMPY`
     * - メジャー・マイナー版が 1 バイトずつ
     * - ヘッダ長（版 1 なら 2 バイトのリトルエンディアン）
     * - Python の辞書リテラル（`{'descr': '|u1', 'fortran_order': False, 'shape': (60000, 28, 28), }`）
     * - 生のデータ
     *
     * MNIST は符号なし 8 ビット（`|u1`）なので、そのまま読める。
     */
```

ヘッダが **Python の辞書リテラルそのまま** というのが独特です。
本来は Python の構文解析が要りますが、必要な情報は `descr` と `shape` だけなので、
正規表現で取り出して、想定外の形式は弾きます。

```kotlin
        require("'descr': '|u1'" in header) { "符号なし 8 ビット以外は扱いません: $header" }

        val shape = SHAPE_PATTERN.find(header)!!.groupValues[1]
            .split(",")
            .map { it.trim() }
            .filter { it.isNotEmpty() }
            .map { it.toInt() }
            .toIntArray()
```

`shape` の中身は `(60000, 28, 28),` のように **末尾にカンマが付く**（1 次元だと
`(60000,)` になる）ので、`filter { it.isNotEmpty() }` が必要です。
[#06](nb06.md) で `split(" ")` に引っかかったのと同じ種類の落とし穴です。

読めていることは、原著が名指しする画像のラベルで確かめます。

```kotlin
    @Test
    fun `原著が例に挙げるラベルが一致する`() {
        val data = mnist()
        assertEquals(2, data.yTrain[5])
        assertEquals(4, data.yTest[4])
        // 原著が「モデルが間違える例」として挙げる 18 番目の正解
        assertEquals(3, data.yTest[18])
    }
```

**3 つとも原著の出力と一致しました。** バイト列を正しく解釈できている証拠です。

## Java の `byte` は符号付き

```kotlin
        /** 符号なしとして解釈した値 */
        fun unsigned(index: Int): Int = data[index].toInt() and 0xFF
```

JVM の `byte` は −128〜127 です。画素値 200 はそのまま読むと **−56** になります。
`and 0xFF` を忘れると、明るい画素だけが負の値になり、
**エラーも例外も出ないまま学習が壊れます**。

```kotlin
    @Test
    fun `画素値は0から255の整数`() {
        val data = mnist()
        assertEquals(255.0, data.xTrain[0].max())
        assertEquals(0.0, data.xTrain[0].min())
    }
```

このテストが、`and 0xFF` の抜けを検知する唯一の防波堤です。

## いちばんの落とし穴 — `update` にまとめて渡すと学習しない

最初はこう書きました。

```kotlin
repeat(epochs) { network.update(x, y) }
```

学習は走ります。例外も警告も出ません。しかし正解率は **0.093**。
10 クラスなので、当てずっぽうの 0.1 と変わりません。

原因は `MLP.update(x, y)` の意味でした。
**渡した配列全体を 1 つのミニバッチとして扱います。**
1 万件を渡すと、1 エポックで重みが **1 回しか動きません**。
3 エポックなら 3 回です。学習しないのは当然でした。

原著の `batch_size=10` に合わせて、10 件ずつ切って渡すように直します。

```kotlin
    /** 原著の `batch_size` と同じ。**この値がそのまま学習の成否を決める**（[fit] 参照） */
    const val BATCH_SIZE = 10

    /** 学習率。Smile の既定（0.01）では 3 エポックでは足りないので上げてある */
    const val LEARNING_RATE = 0.1
```

```kotlin
        network.setLearningRate(smile.math.TimeFunction.constant(LEARNING_RATE))
        repeat(epochs) {
            var start = 0
            while (start + BATCH_SIZE <= sampleSize) {
                network.update(
                    Array(BATCH_SIZE) { x[start + it] },
                    IntArray(BATCH_SIZE) { y[start + it] },
                )
                start += BATCH_SIZE
            }
        }
```

実測した結果です（1 万件・3 エポック・テスト 2000 枚）。

| 渡し方 | 学習率 | 正解率 |
| :--- | ---: | ---: |
| 1 万件をまとめて | 既定 | **0.093**（当てずっぽう） |
| 10 件ずつ | 0.01 | 0.885 |
| 10 件ずつ | 0.1 | **0.930** |

**同じデータ・同じ回数・同じネットワークで、渡し方だけで 0.09 と 0.93 に分かれます。**

Keras の `model.fit(x, y, batch_size=10)` は「全体を渡してバッチ幅を指定する」形なので、
Smile の `update` も同じだろうと考えると、この差にはまります。
`fit`（一括学習）と `update`（1 バッチぶんの更新）という **名前の違いが唯一の手掛かり** でした。

```kotlin
     * 2. **[BATCH_SIZE] 件ずつに切って `update` を呼ぶ。**
     *    Smile の `MLP.update(x, y)` は渡した配列全体を 1 つのミニバッチとして扱う。
     *    訓練データをまるごと渡すと 1 エポックで重みが 1 回しか動かず、
     *    **正解率は当てずっぽうと同じ 0.09〜0.10 のまま** で、エラーも警告も出ない。
     *    10 件ずつに切ると、同じ 10000 件・3 エポックで 0.93 に届く。
```

## 画素値は 0〜1 に直す

```kotlin
     * 1. **画素値を 0〜1 に直してから渡す。** 原著は 0〜255 のまま渡しているが、
     *    [#14][Nb14HousePriceNetwork] と同じ理由で Smile では発散する。
```

[#14](nb14.md) の住宅価格と同じ話です。
原著（Keras + Adam）は前処理なしで動きますが、Smile の素の勾配降下法では
**入力の桁がそのまま学習率に効いてしまいます**。

原著自身、この章では画素値を割っていません。
「Adam が桁の違いを吸収していた」ことが、移植して初めて見えました。

## Dropout は無い

Smile の `MLP` に Dropout はありません。原著は 0.2 を 2 か所に入れていますが、
ここでは省略しています。1 万件・3 エポックという小さい学習では過学習が問題にならないので、
実害はありませんでした。

## パラメータ数だけは計算で合わせられる

```kotlin
    /** 学習した重みの総数。原著の `model.summary()` が出す 109,386 と突き合わせる */
    fun parameterCount(): Int =
        (INPUT_DIM * HIDDEN_UNITS[0] + HIDDEN_UNITS[0]) +
            (HIDDEN_UNITS[0] * HIDDEN_UNITS[1] + HIDDEN_UNITS[1]) +
            (HIDDEN_UNITS[1] * CLASSES + CLASSES)
```

```kotlin
    @Test
    fun `重みの総数は原著と同じ109386`() {
        // 原著の model.summary() が出す Total params
        assertEquals(109_386, parameterCount())
    }
```

Smile は `summary()` にあたるものを持たないので、定義から計算します。
[#13](nb13.md)・[#14](nb14.md) と同じく、**学習結果は再現できなくてもここは固定できます**。
