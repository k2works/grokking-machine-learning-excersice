# #06 IMDB レビューの感情分析（Kotlin）

原著ノートブック: `Chapter_06_Logistic_Regression/Sentiment_analysis_IMDB.ipynb`

映画レビュー 50000 件を、単語の出現回数だけからロジスティック回帰で肯定・否定に分類します。

**Kotlin には `CountVectorizer` に相当するものがありません。**
語彙の作り方から自前で書くことになります。それでも規則を丁寧に揃えたところ、
**scikit-learn と同じ添字の語彙** が作れました。

## ストップワードを 3 言語で共有する

最初に決めたのがここです。`stop_words='english'` が除く 318 語は
**scikit-learn がソースコードに埋め込んでいるリスト** で、他の言語には同じものがありません。

リストが違えば語彙が変わり、3 言語の結果を比べられなくなります。
そこで scikit-learn から書き出して共有データセットに置きました。

```bash
python -c "from sklearn.feature_extraction.text import ENGLISH_STOP_WORDS; print('\n'.join(sorted(ENGLISH_STOP_WORDS)))"
```

```kotlin
/** scikit-learn 内蔵の英語ストップワード 318 語。共有データセットから読む */
fun englishStopWords(): Set<String> =
    Files.readAllLines(Datasets.path("sklearn_english_stop_words.txt"))
        .filter { it.isNotBlank() }
        .toSet()
```

**ライブラリの「既定値」がデータになっている** ことに気づかされる場面でした。
アルゴリズムを移植するときに見落としやすいところです。

## CountVectorizer を自前で書く

揃えるべき規則は 4 つです。

```kotlin
/**
 * scikit-learn の `CountVectorizer` と同じ規則でテキストをベクトル化する。
 *
 * 揃えているのは次の 4 点である。
 * 1. 小文字化する
 * 2. トークンは正規表現 `\b\w\w+\b`（2 文字以上の単語）で切り出す
 * 3. ストップワードを除く（scikit-learn の 318 語を共有データセットから読む）
 * 4. 残った語をコーパス全体の出現回数で並べ、上位 `maxFeatures` 語を採る
 *
 * 語彙は最後に **辞書順** に並べ替える。scikit-learn も同じで、
 * `get_feature_names_out()` の順序が特徴量の添字になる。
 */
class CountVectorizer(
    private val maxFeatures: Int = MAX_FEATURES,
    private val stopWords: Set<String> = englishStopWords(),
)
```

トークンの切り出しは 4 行です。

```kotlin
/** 小文字化して 2 文字以上の単語を取り出し、ストップワードを除く */
fun tokenize(document: String): List<String> =
    TOKEN_PATTERN.findAll(document.lowercase())
        .map { it.value }
        .filter { it !in stopWords }
        .toList()
```

`Regex.findAll` が `Sequence` を返すので、`map` / `filter` が遅延評価で繋がります。
50000 件のレビューを回すので、中間リストを作らない形になるのは効きます。

語彙の選び方はここです。

```kotlin
// 出現回数の多い順。同数なら辞書順にして結果を決定的にする。
// scikit-learn の同数時の扱いは実装依存なので、そこだけは規則が違いうる
vocabulary = counts.entries
    .sortedWith(compareByDescending<Map.Entry<String, Int>> { it.value }.thenBy { it.key })
    .take(maxFeatures)
    .map { it.key }
    .sorted()
```

`compareByDescending { ... }.thenBy { ... }` で
「出現回数の降順、同数なら語の昇順」が 1 行で書けます。
Kotlin の比較子コンビネータがきれいに効く場面です。

同数のときの扱いは scikit-learn では実装依存なので、
**そこだけは規則が違いうる** ことをコメントに残しました。

## 密行列にしたらヒープが尽きた

最初は `Array<DoubleArray>` で書きました。テストがこう落ちます。

```text
Test process encountered an unexpected problem.
> Could not complete execution for Gradle Test Executor 27.
   > Java heap space
```

50000 件 × 2000 語 = 1 億要素。倍精度なので **800 MB** です。
Gradle のテスト用 JVM の既定ヒープでは足りません。

scikit-learn の `CountVectorizer` が返すのは scipy の **疎行列** です。
「レビュー 1 件に出てくる語は多くても数百語」なので、
2000 次元のうち非ゼロはごく一部しかありません。

Smile にも疎行列版があります。

```kotlin
/**
 * 学習済みの語彙で出現回数の行列を作る。
 *
 * **疎行列で持つのが必須である。** IMDB は 50000 件 × 2000 語なので、
 * 密な `Array<DoubleArray>` にすると倍精度で 800 MB になり、
 * 既定のヒープでは `OutOfMemoryError` になる。実際の非ゼロ要素は
 * 全体の数パーセントしかない。scipy の疎行列を返す scikit-learn の
 * `CountVectorizer` と同じ考え方である。
 */
fun transform(documents: List<String>): List<SparseArray> =
    documents.map { document ->
        val counts = HashMap<Int, Double>()
        for (token in tokenize(document)) {
            indexOf[token]?.let { counts[it] = (counts[it] ?: 0.0) + 1.0 }
        }
        val array = SparseArray(counts.size)
        for ((index, value) in counts.entries.sortedBy { it.key }) {
            array.set(index, value)
        }
        array
    }
```

学習も疎行列版に替えます。

```kotlin
val model = SparseLogisticRegression.binomial(
    SparseDataset.of(features, vectorizer.vocabulary.size),
    reviews.sentiments,
    1.0 / reviews.texts.size,
    1e-5,
    1000,
)
```

`LogisticRegression.binomial` と `SparseLogisticRegression.binomial` は
**別のクラスの別のメソッド** です。scikit-learn は同じ `LogisticRegression` が
密でも疎でも受け取るので、ここは Smile のほうが手間が増えます。

一方で、**疎であることが型に出ている** のは分かりやすくもあります。
密で書いて落ちてから気づくより、最初から `SparseArray` を組み立てるほうが意図的です。

## 語彙の添字が scikit-learn と一致した

自前実装がうまくいったかを確かめるいちばん確実な方法は、
**原著の出力に残っている添字と突き合わせる** ことです。

原著の出力にはこうあります。

```text
1964  wonderfully  1.406897
1921  waste       -1.909643
```

```kotlin
@Test
fun `IMDB の語彙は原著と同じ添字になる`() {
    if (!imdbAvailable()) {
        println("IMDB_Dataset.csv が未取得のためスキップします")
        return
    }

    val trained = fit(loadReviews())

    assertEquals(MAX_FEATURES, trained.vocabulary.size)
    // 自前のベクトル化が scikit-learn と同じ語彙を作れている証拠。
    // 原著の出力に現れる添字（1964 wonderfully / 1921 waste）と一致する
    assertEquals(1964, trained.vocabulary.indexOf("wonderfully"))
    assertEquals(1921, trained.vocabulary.indexOf("waste"))
}
```

**一致しました。** 語彙は辞書順に並ぶので、添字が合うということは
2000 語の集合がほぼ同じということです。
トークンの正規表現・ストップワード・上位 2000 語の選び方、
どれか 1 つでも違っていれば添字はずれます。

## 上位の感情語も一致した

| 順位 | 原著 | Kotlin |
| ---: | :--- | :--- |
| 1 | wonderfully | wonderfully |
| 2 | funniest | funniest |
| 3 | gem | gem |
| 4 | brilliantly | brilliantly |
| 5 | subtle | subtle |
| 6 | superb | **delightful** |
| 7 | excellent | **superb** |
| 8 | finest | finest |
| 9 | delightful | **excellent** |
| 10 | underrated | underrated |

上位 5 語は順序まで一致し、6 位以降で 3 語が入れ替わります。
Python 版では否定側だけが入れ替わりましたが、Kotlin では肯定側でも起きました。
正則化の掛け方が scikit-learn と厳密には違う（[#05](nb05.md) 参照）ためです。

否定側は 10 語の集合が一致し、首位も `waste` で同じでした。

```kotlin
@Test
fun `IMDB の上位感情語は原著と同じ集合になる`() {
    // 係数の細かい順序は正則化の掛け方で入れ替わるが、集合は一致する
    assertEquals(
        listOf(
            "brilliantly", "delightful", "excellent", "finest", "funniest",
            "gem", "subtle", "superb", "underrated", "wonderfully",
        ),
        trained.mostPositiveWords(10).sorted(),
    )
    ...
    // 首位は原著と同じ
    assertEquals("wonderfully", trained.mostPositiveWords(1).first())
    assertEquals("waste", trained.mostNegativeWords(1).first())
}
```

`sorted()` を挟んで集合として比較しているのは、
**入れ替わる順序を固定してもテストの価値が上がらない** からです。
代わりに「首位は一致する」を別の表明として足しました。

## この章で Kotlin が効いた場面・効かなかった場面

| 場面 | 評価 |
| :--- | :--- |
| トークン化 | **効いた** — `Regex.findAll` の `Sequence` で遅延評価が繋がる |
| 語彙の選択 | **効いた** — `compareByDescending().thenBy()` が 1 行 |
| 疎行列 | **効いた** — 型に疎であることが出るので意図的に書ける |
| `CountVectorizer` | **効かなかった** — 相当するものが無く自前実装 |
| ストップワード | **効かなかった** — scikit-learn 固有のリストを外部から持ち込む必要 |
| 密と疎の API | **効かなかった** — `LogisticRegression` と `SparseLogisticRegression` が別クラス |

自前実装が多い章でしたが、**添字が一致したことで移植の正しさが証明できました**。
移植先に検証手段が無いときは、
「元の実装が出力に残した数値」を手がかりにするのが有効だと分かった回です。
