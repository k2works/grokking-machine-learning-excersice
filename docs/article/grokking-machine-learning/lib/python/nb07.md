# #07 ナイーブベイズでスパム判定（Python）

原著ノートブック: `Chapter_08_Naive_Bayes/Coding_naive_Bayes.ipynb`

メール 5728 通からスパム判定器を作ります。
**この回だけ、原著が scikit-learn を使いません。** pandas と辞書だけで書かれています。

そのおかげで、ライブラリの版差に悩まされずに済みました。
これまでの 6 本で唯一、**原著のすべての数値を再現できた** 回です。

ただし 1 つだけ落とし穴があります。原著の最後の行にある `np.compat.long` が、
**浮動小数点数を整数に切り捨てて** います。これを写さないと 8 桁目から食い違います。

## メールを単語集合にする

```python
def process_email(text: str) -> list[str]:
    """メール本文を、重複を除いた小文字の単語リストにする。

    原著は `list(set(text.lower().split()))`。**同じ単語が何度出ても 1 回** と
    数えるのがナイーブベイズのこの実装の前提である。
    """
    return list(set(text.lower().split()))
```

`set` を通しているのが重要です。「lottery が 3 回出るメール」も
「1 回出るメール」も同じ 1 通として数えます。
[#06](nb06.md) の `CountVectorizer` が出現 **回数** を数えたのとは違い、
こちらは出現 **通数** を数えています。

## ラプラス平滑化が数え方に埋め込まれている

```python
@dataclass
class WordCounts:
    """ある単語が、スパムとハムそれぞれ何通に現れたか。

    原著は 1 から数え始める。ラプラス平滑化にあたり、
    「一度も見ていない側」の確率が 0 になるのを防ぐ。
    """

    spam: int = 1
    ham: int = 1
```

**初期値が 0 ではなく 1** です。原著のこの行に対応します。

```python
if word not in model:
    model[word] = {'spam': 1, 'ham': 1}
```

これがラプラス平滑化です。ある単語がスパムにしか出なかった場合、
素直に数えると「ハムである確率 0」になり、その単語を含むメールは
他に何が書いてあっても必ずスパム判定になってしまいます。
1 から数え始めることで、そうならないようにしています。

原著の出力で確かめられます。

```python
@emails_required
def test_lotteryとsaleの出現数は原著と同じ(model) -> None:
    # 原著の出力
    #   model['lottery'] -> {'spam': 9, 'ham': 1}
    #   model['sale']    -> {'spam': 39, 'ham': 42}
    assert model.words["lottery"] == WordCounts(spam=9, ham=1)
    assert model.words["sale"] == WordCounts(spam=39, ham=42)
```

`lottery` の `ham` が 1 です。**実際には 1 通のハムにも出ていません。**
初期値の 1 がそのまま残っています。

### 原著の `if` が `elif` でない理由

原著の学習ループはこうなっています。

```python
if word not in model:
    model[word] = {'spam': 1, 'ham': 1}
if word in model:      # elif ではない
    ...
```

2 つ目が `elif` だと、初めて見る単語はカウントされません。
`if` を 2 つ並べることで「無ければ作って、必ず数える」という流れになります。
意図してこう書いたのか、たまたまなのかは分かりませんが、**結果は正しい** ので写しました。

`dict.setdefault` を使えば 1 行です。

```python
counts = words.setdefault(word, WordCounts())
if email["spam"]:
    counts.spam += 1
else:
    counts.ham += 1
```

## np.compat.long による切り捨て

原著の予測はこう終わります。

```python
prod_spams = np.compat.long(np.prod(spams)*num_spam)
prod_hams = np.compat.long(np.prod(hams)*num_ham)
return prod_spams/(prod_spams + prod_hams)
```

`np.compat.long` は Python 2 との互換のために置かれていたもので、
Python 3 では **`int` そのもの** です。つまりここで **小数点以下が切り捨てられます**。

意図した処理には見えません。おそらく「大きな数を扱うから long にしておこう」という
つもりだったのでしょう。しかし切り捨てないと、原著の出力と一致しません。

```python
@emails_required
def test_切り捨てを外すと原著と食い違う(model) -> None:
    # 原著の np.compat.long は Python の int と同じで小数点以下を切り捨てる。
    # 切り捨てないと 'lottery sale' が 0.9638144470140118 になり、
    # 原著の 0.9638144992048691 と 8 桁目から分かれる
    ...
    assert without_truncation == pytest.approx(0.9638144470140118, rel=1e-12)
    # 差は 8 桁目なので、既定の許容誤差（相対 1e-6）では見分けられない
    assert without_truncation != pytest.approx(0.9638144992048691, rel=1e-12)
    assert predict_naive_bayes(model, "lottery sale") == pytest.approx(
        0.9638144992048691, rel=1e-12
    )
```

**`pytest.approx` の既定（相対 1e-6）では、この差は見分けられません。**
`rel=1e-12` を明示して初めてテストが意味を持ちます。
「一致しないことを確かめるテスト」を書くときは、許容誤差の設定がそのまま主張の強さになります。

実装ではこう書きました。

```python
    product_spams = _product(spams) * corpus.spam
    product_hams = _product(hams) * corpus.ham
    # 原著の np.compat.long と同じ切り捨て
    truncated_spams = int(product_spams)
    truncated_hams = int(product_hams)
    return truncated_spams / (truncated_spams + truncated_hams)
```

`np.compat` は NumPy 2.0 で削除されているので、`int()` を直接使っています。
**原著のノートブックは、いまの NumPy ではそもそも動きません。**

### 切り捨てが結果に効く条件

7 つの入力のうち、切り捨ての有無で値が変わったのは 2 つだけでした。

| 入力 | 切り捨てあり（原著） | 切り捨てなし |
| :--- | ---: | ---: |
| `lottery sale` | 0.9638144992048691 | **0.9638144470140118** |
| `Grokking Machine Learning by Luis Serrano` | 0.4197107645488719 | **0.4197107645484568** |
| `Hi mom how are you` | 0.12554358867164464 | 同じ |
| `buy cheap lottery easy money now` | 0.999973472265966 | 同じ |

差が出るのは、**積が小さくて切り捨ての影響が相対的に大きいとき** です。
`buy cheap lottery easy money now` のように単語が多いと積が巨大になり、
小数点以下を落としても比率はほとんど動きません。

## 予測はすべて原著と一致する

```python
@emails_required
@pytest.mark.parametrize(
    ("email", "expected"),
    [
        ("lottery sale", 0.9638144992048691),
        ("Hi mom how are you", 0.12554358867164464),
        ("meet me at the lobby of the hotel at nine am", 6.964603508395961e-05),
        ("enter the lottery to win three million dollars", 0.9995234218677428),
        ("buy cheap lottery easy money now", 0.999973472265966),
        ("Grokking Machine Learning by Luis Serrano", 0.4197107645488719),
        ("asdfgh", 0.2388268156424581),
    ],
)
def test_メール全体の予測は原著と同じ(model, email: str, expected: float) -> None:
    # 原著のセル出力をそのまま期待値にしている
    assert predict_naive_bayes(model, email) == pytest.approx(expected)
```

`parametrize` で 7 件を 1 つのテストにまとめました。
どれか 1 つが落ちても、どの入力が原因かがテスト名に出ます。

### 面白い 2 つの結果

**`asdfgh` は事前確率をそのまま返します。**

```text
predict_naive_bayes('asdfgh') -> 0.2388268156424581
```

これは「スパムの割合 1368 / 5728」と同じ値です。
語彙にない単語は無視されるので、**何も情報が無いときの答え** に落ちます。
ナイーブベイズが確率モデルとして筋が通っていることの現れです。

**知らない単語を足しても結果は変わりません。**

```python
@emails_required
def test_知らない単語を足しても結果は変わらない(model) -> None:
    # 原著は同じ文に意味のない語を足しても同じ値になることを示している
    #   'Hi mom how are you' と
    #   'Hi MOM how aRe yoU afdjsaklfsdhgjasdhfjklsd' が同じ 0.12554358867164464
    assert predict_naive_bayes(model, "Hi mom how are you") == pytest.approx(
        predict_naive_bayes(model, "Hi MOM how aRe yoU afdjsaklfsdhgjasdhfjklsd")
    )
```

大文字小文字も無視されます。原著がわざわざこの 2 つを並べているのは、
前処理が効いていることを見せるためです。

## まとめ

| 項目 | 原著と一致するか |
| :--- | :--- |
| メール数・スパム数・事前確率 | **完全一致** |
| 単語ごとの出現数（`lottery` / `sale`） | **完全一致** |
| 単語 1 つの予測 | **完全一致** |
| メール全体の予測（7 件すべて） | **完全一致**（切り捨てを写した場合） |

**ライブラリを使わない章がいちばんよく再現できる** というのは、
この連載の趣旨からすると皮肉な結果です。
ライブラリの `fit()` を呼ばない分、版差の入り込む余地が無いのです。

Kotlin 版・F# 版も、同じ理由で完全に再現できました。
差が出たのは **多倍長整数の扱い** だけです。
