# 第 13 章 エンドツーエンドの実例（F# 版）

原著第 13 章「Putting it all in practice」を F# で実装します。**これまでの章で作った部品を組み合わせて、生データから評価までを 1 本のパイプラインに通します。**

新しいアルゴリズムは登場しません。本章の主題は **「実務のほとんどは前処理と評価である」** ということです。

サンプル実装は `apps/grokking-ml-fsharp/src/GrokkingMl/Ch13EndToEnd.fs` です。

## この章で作るもの

- 欠損値の補完・正規化・One-Hot エンコーディング
- 生データから特徴量ベクトルへの変換
- 3 つのモデル（第 6・9・12 章）の学習と比較
- 第 7 章の指標による評価

## 名前の衝突を修飾で避ける

本章は 4 つの章の部品を使いますが、**`open` していません。**

```fsharp
let matrix = GrokkingMl.Ch07Metrics.confusionMatrix labels (points |> List.map predictFn)

{ Name = name
  Accuracy = GrokkingMl.Ch07Metrics.accuracy matrix
  ...
```

理由は名前の衝突です。本シリーズでは `accuracy` が第 5・6・9・11・12 章に、`predict` が第 5・6・9・11 章に登場します。**同じ概念に同じ名前を付けてきた結果、統合の段階ですべてが衝突します。**

F# のモジュールは `open` すると名前が平坦に入るため、複数の章を同時に開くと後勝ちになります。Kotlin ではインポート別名（`import ch07.accuracy as matrixAccuracy`）で解決しましたが、F# では **完全修飾名で書く** のがもっとも明快でした。

冗長ですが、**どの章の関数を呼んでいるかがコード上に残ります。** 統合の章としてはむしろ読みやすくなりました。

第 12 章で `forestPredict` のような接頭辞を付けたのも同じ問題への対処です。**モジュールシステムの性質が、命名と統合の書き方の両方に影響しました。**

## 第 4 章の分割は使えなかった

Python 版では第 4 章の `trainTestSplit` をそのまま流用できましたが、**F# では型が合いません。**

```fsharp
// 第 4 章のシグネチャ
let trainTestSplit (testRatio: float) (seed: int) (features: float list) (labels: float list)
```

第 4 章の特徴量は 1 次元（`float list`）でした。本章の特徴量は多次元（`float list list`）です。**中身の処理はインデックスの並べ替えだけなので、論理的には同じものが使えるはずですが、型が拒否します。**

```fsharp
/// 訓練用とテスト用に分割する。第 4 章と同じ手順を多次元の点に対して行う。
let splitDataset (testRatio: float) (seed: int) (dataset: Dataset) =
    let rng = Random(seed)

    let indices =
        List.init (List.length dataset.Points) id
        |> List.sortBy (fun _ -> rng.Next())

    let testSize = int (float (List.length dataset.Points) * testRatio)
    let testIndices = List.truncate testSize indices
    let trainIndices = List.skip testSize indices

    { TrainPoints = trainIndices |> List.map (fun i -> dataset.Points[i])
      ... }
```

**ジェネリック関数（`let split<'T> (items: 'T list) ...`）にしておけば再利用できました。** F# は型推論が強いので、第 4 章で型注釈を書かなければ自動的にジェネリックになっていた可能性もあります。**明示的な型注釈が、再利用性を狭めることがある** という教訓です。

## 前処理

### 欠損値

```fsharp
/// 数値に見えない値は既定値に落とす。欠損への最初の砦。
let parseNumber (defaultValue: float) (text: string) =
    match Double.TryParse(text) with
    | true, value -> value
    | _ -> defaultValue

/// 欠損を中央値で埋める。平均より外れ値に強い。
let imputeMissing (column: float option list) =
    let filler = column |> List.choose id |> median
    column |> List.map (Option.defaultValue filler)
```

`Double.TryParse` は .NET の慣習で **タプル `(bool * float)` を返します**。F# はそれを `match` でパターン分解できるため、`out` パラメータの煩わしさがありません。`| true, value -> value` という 1 行が「成功したら値を取る」をそのまま表します。

`float option list` という型で「値がないかもしれない列」を表します。**`List.choose id` で `Some` の中身だけを取り出す** のが F# の定型です（`id` を渡すことで「`option` をそのまま選別に使う」意味になります）。

`Option.defaultValue filler` は第 8 章の `Map.tryFind |> Option.defaultValue 0` と同じ形です。**`Option` を扱う語彙が章をまたいで一貫しています。**

**平均ではなく中央値を使います。** 外れ値に引きずられないためです。

```fsharp
[<Fact>]
let ``imputeMissing は外れ値に強い`` () =
    // 平均なら 1000 に引きずられるが、中央値なら影響を受けない
    let filled = imputeMissing [ Some 1.0; Some 2.0; Some 3.0; Some 1000.0; None ]
    Assert.Equal(2.5, List.last filled, 6)
```

### 正規化

```fsharp
let normalize (column: float list) =
    let low = List.min column
    let high = List.max column

    if high = low then
        column |> List.map (fun _ -> 0.0)
    else
        column |> List.map (fun value -> (value - low) / (high - low))
```

年齢は 18〜70、収入は 200〜900。**このまま第 6 章のロジスティック回帰に渡すと、収入だけが効いてしまいます。** 重みの更新量は特徴量に比例する（第 3 章の二乗トリック以来ずっとそうです）ので、値の大きい特徴量が支配的になります。

### カテゴリ変数

```fsharp
let oneHot (column: string list) =
    let categories = column |> List.distinct |> List.sort

    let expanded =
        column
        |> List.map (fun value -> categories |> List.map (fun category -> if value = category then 1.0 else 0.0))

    (expanded, categories)
```

「東京・大阪・京都」を 0・1・2 と番号で表すと、**「京都は東京の 2 倍」という存在しない大小関係が生まれます。** 代わりに 3 本の 0/1 列へ展開します。

## 列の処理を関数で束ねる

```fsharp
let buildDataset (labelColumn: string) (rows: Row list) =
    ...
    let numericColumn name =
        let raw =
            rows
            |> List.map (fun row ->
                match valueOf name row with
                | "" -> None
                | text -> Some(parseNumber 0.0 text))

        ([ normalize (imputeMissing raw) ], [ name ])

    let categoricalColumn name =
        let expanded, categories = oneHot (rows |> List.map (valueOf name))
        ...
        (columns, categories |> List.map (fun category -> $"{name}={category}"))

    let parts =
        [ numericColumn "age"; numericColumn "income"; categoricalColumn "city" ]

    let columns = parts |> List.collect fst
    let names = parts |> List.collect snd
```

**`numericColumn` と `categoricalColumn` が同じ型（`string -> float list list * string list`）を返します。** だから 1 つのリストに並べて `List.collect` で平坦化できます。

数値列は 1 本、カテゴリ列は複数本の列を生みますが、**どちらも「列のリストと名前のリスト」を返す** と揃えたことで、後段の処理が統一されました。Python 版と Kotlin 版では可変リストへ追加していく形になった箇所です。

**戻り値の型を揃えることが、合成可能性を生みます。**

## 3 つのモデルを同じ土俵で比較する

```fsharp
let evaluate
    (name: string)
    (predictFn: Point -> int)
    (probabilityFn: Point -> float)
    (points: Point list)
    (labels: int list)
    =
    let matrix = GrokkingMl.Ch07Metrics.confusionMatrix labels (points |> List.map predictFn)
    ...
```

**モデルの型ではなく「予測関数」と「確率関数」を受け取ります。** F# では部分適用によって、モデルを固定した関数が自然に作れます。

```fsharp
    [ evaluate
          "logistic"
          (GrokkingMl.Ch06LogisticRegression.predict logistic)
          (GrokkingMl.Ch06LogisticRegression.predictProbability logistic)
          split.TestPoints
          split.TestLabels
      ...
```

**`predict logistic` と書くだけで `Point -> int` の関数になります。** ラムダ（`fun point -> ...`）を書く必要がありません。第 5 章から一貫して「モデルを第 1 引数に置く」設計にしてきたことが、最終章で効きました。

3 つのモデルは出力の形がばらばらです。

| モデル | 予測 | 「確率」に相当するもの |
| :--- | :--- | :--- |
| ロジスティック回帰（第 6 章） | 0 / 1 | 予測確率（0〜1） |
| 決定木（第 9 章） | 0 / 1 | **なし**（0/1 をそのまま使う） |
| AdaBoost（第 12 章） | **+1 / -1** | 重み付き投票のスコア（範囲は不定） |

AdaBoost だけラベルの表現が違うため、変換のラムダが必要でした。**第 11 章で +1/-1 を導入した判断が、ここで統合コストとして表れています。**

## 実行結果

「40 歳未満かつ収入 400 超なら購入」という規則に従う擬似データ 40 件（うち 9 件に 1 件は年齢が欠損）で試します。

| モデル | 正解率 | 適合率 | 再現率 | F1 | AUC |
| :--- | ---: | ---: | ---: | ---: | ---: |
| **ロジスティック回帰** | 0.833 | 0.800 | **0.800** | **0.800** | **0.857** |
| 決定木 | 0.833 | 1.000 | 0.600 | 0.750 | 0.800 |
| AdaBoost | 0.833 | 1.000 | 0.600 | 0.750 | 0.800 |

**3 モデルとも正解率は 0.833 で並びましたが、F1 では差が付きました。**

- ロジスティック回帰: 適合率 0.800・再現率 0.800（バランス型）
- 決定木と AdaBoost: 適合率 1.000・再現率 0.600（**慎重型**）

決定木と AdaBoost は「買う」と言った予測がすべて当たっています（適合率 1.0）が、買う人の 4 割を見逃しています。ロジスティック回帰は多少空振りしますが、より多く拾えています。

**正解率だけを見ていたら「3 モデルとも同じ」で終わっていました。** 第 7 章で学んだ指標の使い分けが、最終章で実際に効いています。

用途によって選ぶモデルは変わります。ダイレクトメールのコスト（空振りの損）が高いなら決定木、機会損失（見逃しの損）が高いならロジスティック回帰です。

これらの値は Python 版・Kotlin 版とは異なります。**擬似データの生成に使う乱数と、訓練／テスト分割の乱数が言語ごとに違う** ためです。3 言語のどれでも「モデルによって指標の傾向が変わる」という結論は共通しています。

## まとめ

- 本章に新しいアルゴリズムはありません。10 章分の部品を組み合わせただけです。
- `open` せず完全修飾名で書くことで、名前の衝突を避けつつ「どの章の関数か」を残せます。
- 第 4 章の分割関数は型注釈で 1 次元に固定されていたため再利用できませんでした。**型推論に任せていればジェネリックになっていたかもしれません。**
- `Double.TryParse` のタプルを `match` で分解でき、`out` パラメータの煩わしさがありません。
- 列を処理する関数の戻り値の型を揃えると、`List.collect` で合成できます。
- 「モデルを第 1 引数に置く」設計により、部分適用だけで評価用の関数が作れました。
