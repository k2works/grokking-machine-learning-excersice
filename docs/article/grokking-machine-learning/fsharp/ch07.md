# 第 7 章 分類モデルの評価指標（F# 版）

原著第 7 章「How do you measure classification models?」を F# で実装します。第 5・6 章では正解率だけでモデルを評価してきました。本章では **正解率がまったく役に立たない場面** を出発点に、混同行列・適合率・再現率・F1 スコア・AUC を実装します。

サンプル実装は `apps/grokking-ml-fsharp/src/GrokkingMl/Ch07Metrics.fs` です。

## この章で作るもの

- 混同行列（すべての指標の土台）
- 正解率・適合率・再現率
- F1 スコアと F ベータスコア
- ROC 曲線と AUC

## 正解率 99% の役立たずモデル

1000 人に 10 人が罹る病気を診断するモデルを考えます。**全員を「陰性」と判定する** モデルの正解率は 99% です。

```fsharp
[<Fact>]
let ``正解率が高くてもモデルが役立たずなことがある`` () =
    let matrix = confusionMatrix sickLabels alwaysHealthy
    // 990/1000 を当てているので正解率は 99%
    Assert.Equal(0.99, accuracy matrix, 6)
    // しかし病人を 1 人も見つけられていない
    Assert.Equal(0.0, recall matrix, 6)
```

このモデルは病人を 1 人も見つけられません。**正解率は、陽性と陰性の数が偏っているときに壊れます。** 本章の指標はすべて、この問題への対処として存在します。

## 混同行列

すべての指標は、4 つの数から導けます。

```fsharp
/// 混同行列。すべての指標の土台になる 4 つの数。
type ConfusionMatrix =
    { TruePositives: int
      FalsePositives: int
      FalseNegatives: int
      TrueNegatives: int }

    member this.Total =
        this.TruePositives
        + this.FalsePositives
        + this.FalseNegatives
        + this.TrueNegatives
```

| | 予測 = 1 | 予測 = 0 |
| :--- | :--- | :--- |
| **正解 = 1** | 真陽性（TP） | 偽陰性（FN）= 見逃し |
| **正解 = 0** | 偽陽性（FP）= 誤検知 | 真陰性（TN） |

**F# のレコードは構築時に必ずフィールド名を書きます。** 4 つとも `int` なので、Python や Kotlin では位置引数による取り違えが起こりえますが、F# では言語がそれを許しません。同じ型のフィールドが並ぶ型では、この強制が効いてきます。

```fsharp
/// 正解ラベルと予測から混同行列を作る。
let confusionMatrix (labels: int list) (predictions: int list) =
    let counts =
        List.zip labels predictions
        |> List.countBy id
        |> Map.ofList

    let count key = Map.tryFind key counts |> Option.defaultValue 0

    { TruePositives = count (1, 1)
      FalsePositives = count (0, 1)
      FalseNegatives = count (1, 0)
      TrueNegatives = count (0, 0) }
```

`List.countBy id` は「要素そのものをキーとして数える」という意味です。`id`（恒等関数）を渡すことで、`countBy` の一般形をそのまま使えます。

`Map.tryFind key counts |> Option.defaultValue 0` は F# らしい書き方です。**存在しないキーは `None` として型に現れ、`defaultValue` で既定値に落とします。** Kotlin の `?: 0` と同じ意図ですが、`Option` という明示的な型を経由する点が違います。

この `count` をローカル関数として切り出したことで、レコード構築の 4 行が揃った形になりました。

## 適合率と再現率

0 除算の扱いを 1 か所にまとめます。

```fsharp
/// 0 除算を避ける割り算。分母が 0 なら 0 を返す。
let private safeDivide (numerator: int) (denominator: int) =
    if denominator = 0 then
        0.0
    else
        float numerator / float denominator

/// 正解率。全体のうち正しく当てた割合。
let accuracy (matrix: ConfusionMatrix) =
    safeDivide (matrix.TruePositives + matrix.TrueNegatives) matrix.Total

/// 適合率。陽性と予測したもののうち、本当に陽性だった割合。
let precision (matrix: ConfusionMatrix) =
    safeDivide matrix.TruePositives (matrix.TruePositives + matrix.FalsePositives)

/// 再現率。本当に陽性のもののうち、拾えた割合。
let recall (matrix: ConfusionMatrix) =
    safeDivide matrix.TruePositives (matrix.TruePositives + matrix.FalseNegatives)
```

`safeDivide` を切り出したことで、3 つの指標が **それぞれ 1 行の式** になりました。分子と分母の定義だけが残り、指標の本質が見えます。

`float numerator / float denominator` と両方を明示的に変換しているのは、F# が `int / int` を整数除算として扱うためです。**ただし F# では `float numerator / denominator` と書くと型エラーになります。** 暗黙の昇格がないため、変換忘れがコンパイル時に止まります。Kotlin では `numerator / denominator` が静かに整数除算になり、0.75 が 0 になる事故が起きえます。第 4 章から続く「明示のコスト」がここで利益に変わりました。

| 指標 | 問い | 分母 |
| :--- | :--- | :--- |
| 適合率（precision） | 「陽性」と言ったとき、どれくらい信じてよいか | 陽性と **予測した** 数 |
| 再現率（recall） | 本当の陽性を、どれくらい拾えたか | 実際に **陽性である** 数 |

2 つはトレードオフの関係にあります。

```fsharp
[<Fact>]
let ``precision と recall はトレードオフ`` () =
    // 全員を陽性と予測すると再現率は 1.0 だが適合率は下がる
    let aggressive = confusionMatrix sickLabels (List.replicate 1000 1)
    Assert.Equal(1.0, recall aggressive, 6)
    Assert.Equal(0.01, precision aggressive, 6)
```

全員を「陽性」と判定すれば見逃しはゼロ（再現率 1.0）ですが、当たりは 10 件だけ（適合率 0.01）です。**冒頭の「全員陰性」モデルとちょうど裏返しの失敗** です。

## F1 スコア

適合率と再現率を 1 つの数にまとめますが、**算術平均ではなく調和平均** を使います。

```fsharp
/// F ベータスコア。beta が大きいほど再現率を重視する。
let fBetaScore (beta: float) (matrix: ConfusionMatrix) =
    let p = precision matrix
    let r = recall matrix

    if p = 0.0 && r = 0.0 then
        0.0
    else
        let betaSquared = beta * beta
        (1.0 + betaSquared) * p * r / (betaSquared * p + r)

/// F1 スコア。適合率と再現率の調和平均。
let f1Score (matrix: ConfusionMatrix) = fBetaScore 1.0 matrix
```

引数の順序に注目してください。**`beta` を先、行列を後** に置いています。第 4 章から一貫している「ハイパーパラメータ → データ」の並びです。この順序だから `fBetaScore 1.0` の部分適用で `f1Score` を作れます。

F# にはデフォルト引数がないため、Python や Kotlin のように `f_beta_score(matrix, beta=1.0)` の既定値としては書けません。代わりに **部分適用で特殊形に名前を付けます**。第 6 章の `predict` / `predictWith` と同じ解き方です。

なぜ調和平均かというと、**偏りを強く罰するため** です。

```fsharp
[<Fact>]
let ``f1Score は偏りを算術平均より強く罰する`` () =
    // 適合率 1.0、再現率 0.1 のモデル
    let unbalanced =
        { TruePositives = 1
          FalsePositives = 0
          FalseNegatives = 9
          TrueNegatives = 90 }

    let arithmeticMean = (precision unbalanced + recall unbalanced) / 2.0
    Assert.True(f1Score unbalanced < arithmeticMean)
```

適合率 1.0・再現率 0.1 のモデルは、算術平均なら 0.55 と「まあまあ」に見えますが、F1 スコアは 0.18 です。**片方が壊れているモデルを、平均で誤魔化させません。**

病気の見逃しを避けたいなら `fBetaScore 2.0`（再現率重視）、迷惑メール判定で誤検知を避けたいなら `fBetaScore 0.5`（適合率重視）を選びます。

## 閾値と ROC

第 6 章で `predictWith` を用意したことが、ここで効いてきます。確率を返すモデルなら、**再学習せずに適合率と再現率のバランスを変えられます。**

```fsharp
/// 確率と閾値から 0 / 1 の予測を作る。
let predictionsAtThreshold (threshold: float) (probabilities: float list) =
    probabilities |> List.map (fun p -> if p >= threshold then 1 else 0)
```

**閾値はモデルの性能ではなく、運用上の選択です。** ではモデル自体の良し悪しは何で測るのか。すべての閾値を試して、その全体を見ます。それが ROC 曲線です。

```fsharp
/// ROC 曲線の点列。閾値を動かしたときの (偽陽性率, 真陽性率) を返す。
let rocPoints (labels: int list) (probabilities: float list) =
    let thresholds =
        probabilities @ [ 0.0; 1.0 + 1e-9 ]
        |> List.distinct
        |> List.sortDescending

    thresholds
    |> List.map (fun threshold ->
        let matrix = confusionMatrix labels (predictionsAtThreshold threshold probabilities)

        let falsePositiveRate =
            safeDivide matrix.FalsePositives (matrix.FalsePositives + matrix.TrueNegatives)

        (falsePositiveRate, recall matrix))
    |> List.sort
```

試す閾値は **データに現れた確率そのもの** です。それ以外の値を試しても予測は変わりません。

`1.0 + 1e-9` という値が要るのは、`predictionsAtThreshold` が `>=` で比較するためです。確率がちょうど 1.0 の点があると、閾値 1.0 では陽性のままになります。**境界の扱いを決めたら、その帰結を最後まで面倒みる必要があります。**

最後の `List.sort` に注目してください。F# のタプルは **構造的比較を持つ** ため、`(float * float) list` をそのまま辞書式にソートできます。Kotlin では `Pair` が `Comparable` ではないので `compareBy` で比較器を組み立てる必要がありました。**タプルが値として振る舞うかどうかの差** です。

## AUC

ROC 曲線の下の面積です。台形則で積分します。

```fsharp
/// ROC 曲線下の面積。台形則で積分する。
let auc (labels: int list) (probabilities: float list) =
    rocPoints labels probabilities
    |> List.pairwise
    |> List.sumBy (fun ((x1, y1), (x2, y2)) -> (x2 - x1) * (y1 + y2) / 2.0)
```

`List.pairwise` が隣り合う 2 要素の組を作り、`List.sumBy` が台形の面積を足し上げます。**ラムダの引数でタプルを入れ子のままパターン分解できる** ため、`((x1, y1), (x2, y2))` と 4 つの座標に一度で名前が付きます。ループもインデックスも現れません。

AUC の意味は「面積」よりも **「陽性を陰性より高くランク付けできた組の割合」** と理解するほうが実用的です。

| 並び | AUC | 意味 |
| :--- | ---: | :--- |
| 陽性がすべて上位 | 1.0 | 完全な順位付け |
| 陽性が最上位と最下位 | 0.5 | ランダムと同じ |
| 陰性がすべて上位 | 0.0 | 完全に逆 |

```fsharp
[<Fact>]
let ``auc は正しく並んだ組の割合`` () =
    // 陽性 2 件と陰性 2 件の組 4 通りのうち、3 通りで陽性が上位
    Assert.Equal(0.75, auc [ 1; 0; 1; 0 ] [ 0.8; 0.6; 0.4; 0.2 ], 6)
```

AUC の最大の利点は **閾値に依存しないこと** です。

```fsharp
[<Fact>]
let ``auc は閾値に依存しない`` () =
    let labels = [ 1; 1; 0; 0 ]
    let scaled = [ 0.99; 0.98; 0.02; 0.01 ]
    let compressed = [ 0.55; 0.54; 0.46; 0.45 ]
    Assert.Equal(auc labels scaled, auc labels compressed, 6)
```

確率が 0.99 と 0.01 に分かれていても、0.55 と 0.45 に固まっていても、**順位が同じなら AUC は同じ** です。第 6 章で見た「重みの大きさ＝確信の強さ」は AUC には影響しません。

## 指標の使い分け

| 指標 | 見るべき場面 | 弱点 |
| :--- | :--- | :--- |
| 正解率 | クラスの数が釣り合っているとき | 偏りがあると壊れる |
| 適合率 | 誤検知のコストが高いとき | 見逃しを無視する |
| 再現率 | 見逃しのコストが高いとき | 誤検知を無視する |
| F1 | 両方を 1 つの数で見たいとき | 閾値に依存する |
| AUC | モデル自体の識別能力を見たいとき | 実運用の閾値を教えてくれない |

## まとめ

- 正解率はクラスが偏ると壊れます。全員陰性で 99% になります。
- レコードは構築時にフィールド名が必須なので、同じ型のフィールドが並んでも取り違えられません。
- `Map.tryFind |> Option.defaultValue` により、キーの不在が型に現れます。
- 数値変換が必須なので、整数除算の事故がコンパイル時に止まります。
- タプルが構造的比較を持つため `List.sort` がそのまま使え、`List.pairwise` で台形則が 1 行になります。
