# 第 8 章 ナイーブベイズ（Kotlin 版）

原著第 8 章「Using probability to its maximum」を Kotlin で実装します。第 5〜7 章の分類器は境界線を **学習** しました。本章の分類器は **数え上げるだけ** です。それでいて実用的な精度が出ます。

サンプル実装は `apps/grokking-ml-kotlin/src/main/kotlin/ch08/NaiveBayes.kt` です。

## この章で作るもの

- 文書を単語集合に分解するトークナイザ
- 単語ごとのクラス別出現回数を数える学習
- ラプラス平滑化つきの単語スパム確率
- 対数空間での文書スパム確率の合成

## 学習しない学習器

| | 第 5〜6 章 | 第 8 章 |
| :--- | :--- | :--- |
| 学習 | エポックを回して重みを更新 | **数えるだけ**（1 回のパス） |
| ハイパーパラメータ | 学習率、エポック数、シード | 平滑化の強さのみ |
| 乱数 | 使う | **使わない** |
| 結果の再現性 | シード依存 | **常に同一** |

そのため本章の実装は、**3 言語すべてで数値が完全に一致します**。

## ベイズの定理と「ナイーブ」な仮定

知りたいのは「この文書がスパムである確率」です。しかし単語列全体の出現確率を数えることはできません。「lottery winning sale」という並びは訓練データにほぼ現れないからです。

そこで **「単語は互いに独立に出現する」** と仮定します。これがナイーブ（素朴）と呼ばれる所以です。実際の文章で単語は独立ではありません。**明らかに間違った仮定ですが、それでも実用的に機能します。**

## トークナイズと学習

```kotlin
/** 文章を小文字の単語列に分解する。 */
fun tokenize(text: String): List<String> =
    text.lowercase().split(" ").filter { it.isNotEmpty() }

/** 文書とラベル（1 がスパム）から分類器を学習する。 */
fun train(documents: List<String>, labels: List<Int>): NaiveBayesClassifier {
    // 同じ単語が何度出ても 1 文書につき 1 回だけ数える（ベルヌーイ型）
    val byLabel = documents.zip(labels).groupBy({ it.second }, { tokenize(it.first).toSet() })
    fun countWords(label: Int): Map<String, Int> =
        byLabel[label].orEmpty().flatten().groupingBy { it }.eachCount()
    return NaiveBayesClassifier(
        spamWordCounts = countWords(1),
        hamWordCounts = countWords(0),
        spamDocuments = byLabel[1].orEmpty().size,
        hamDocuments = byLabel[0].orEmpty().size,
    )
}
```

`groupBy` は 2 引数版が使えます。**第 1 引数でキー（ラベル）を、第 2 引数で値の変換（トークン集合化）を同時に指定できる** ため、`Map<Int, List<Set<String>>>` が 1 行で得られます。

その後の `flatten().groupingBy { it }.eachCount()` は第 7 章と同じ数え上げです。**ループも可変変数も現れません。**

`countWords` を **ローカル関数** として定義しているのが要点です。`byLabel` をクロージャで捕捉できるので引数が 1 つで済み、スパム用とハム用で同じ処理を 2 度書かずにすみます。トップレベルに置くと `byLabel` を渡す必要が出て、この関数がどこで使われるのかも曖昧になります。

`orEmpty()` は `null` を空リストに変換します。そのラベルの文書が 1 件もないとき `byLabel[1]` は `null` になるためです。**`Map` の添字が `V?` を返すことを、Kotlin は毎回意識させます。**

### なぜ集合にするのか

「spam spam spam」で `spam` を 3 回数えるか 1 回数えるかは、モデルの種類の違いです。回数を数えるのが多項分布型、出現の有無だけを見るのがベルヌーイ型です。ここではベルヌーイ型を選びました。

```kotlin
@Test
fun `train は同じ単語を 1 文書につき 1 回だけ数える`() {
    val repeated = train(listOf("spam spam spam"), listOf(1))
    assertEquals(1, repeated.spamWordCounts["spam"])
}
```

## モデル

```kotlin
/** ナイーブベイズ分類器。単語ごとの出現回数からスパム確率を求める。 */
data class NaiveBayesClassifier(
    val spamWordCounts: Map<String, Int>,
    val hamWordCounts: Map<String, Int>,
    val spamDocuments: Int,
    val hamDocuments: Int,
) {
    val totalDocuments: Int get() = spamDocuments + hamDocuments

    val vocabulary: Set<String> get() = spamWordCounts.keys + hamWordCounts.keys
}
```

`Map<String, Int>` は読み取り専用インターフェースなので、モデルが不変であることが型で表現されます。Python の `Counter` は `dict` のサブクラス（可変）だったので、この点は Kotlin のほうが素直です。

`spamWordCounts.keys + hamWordCounts.keys` は `Set` の和集合です。`+` 演算子が `Set` に対して和集合として定義されているため、集合演算がそのまま書けます。

## ラプラス平滑化

ある単語がスパム文書に 3 回、通常文書に 0 回現れたとします。素朴に計算すると確率は `3 / 3 = 1.0` です。

これは危険です。**確率 1.0 は「絶対にスパム」を意味し、他のどんな単語が来ても覆せません**。そこで、すべてのカウントに 1 を足します。

```kotlin
/** その単語を含む文書がスパムである確率。ラプラス平滑化つき。 */
fun wordSpamProbability(
    model: NaiveBayesClassifier,
    word: String,
    smoothing: Double = 1.0,
): Double {
    val spam = (model.spamWordCounts[word] ?: 0) + smoothing
    val ham = (model.hamWordCounts[word] ?: 0) + smoothing
    return spam / (spam + ham)
}
```

`(model.spamWordCounts[word] ?: 0) + smoothing` の型に注目してください。`Int + Double` が `Double` に昇格するため、**第 7 章で問題になった整数除算がここでは起きません**。`spam` と `ham` の時点で既に `Double` だからです。平滑化を足すという処理が、たまたま型の問題も解消しています。

```kotlin
@Test
fun `wordSpamProbability はラプラス平滑化を使う`() {
    // lottery はスパム 3 件、ハム 0 件。平滑化なしなら 1.0 になってしまう
    assertEquals(3, model.spamWordCounts["lottery"])
    assertEquals(null, model.hamWordCounts["lottery"])
    // (3+1) / ((3+1) + (0+1)) = 0.8
    assertEquals(0.8, wordSpamProbability(model, "lottery"), 1e-9)
}
```

`assertEquals(null, model.hamWordCounts["lottery"])` という行が、**Kotlin の `Map` と Python の `Counter` の違い** を表しています。Python の `Counter` は存在しないキーに 0 を返しますが、Kotlin の `Map` は `null` を返します。だからこそ `?: 0` が必要でした。

未知語はスパム 0 件・通常 0 件なので、平滑化後はちょうど 0.5 になります。**「何も知らない単語は判定に寄与しない」** という望ましい性質が自然に出ます。

## 対数空間で合成する

各単語の確率を掛け合わせるのが素直な実装ですが、**そのまま書くと壊れます**。0.1 を 100 語分掛けると `1e-100` になり、アンダーフローします。

そこで対数を取り、掛け算を足し算に変えます。

```kotlin
/** 文書がスパムである確率。対数空間で計算する。 */
fun predictProbability(
    model: NaiveBayesClassifier,
    document: String,
    smoothing: Double = 1.0,
): Double {
    if (model.totalDocuments == 0) return 0.0
    val prior = priorSpamProbability(model)
    var logSpam = ln(safe(prior))
    var logHam = ln(safe(1.0 - prior))
    // 学習時に見ていない単語は何も語らないので無視する
    tokenize(document).toSet().filter { it in model.vocabulary }.forEach { word ->
        val spamGivenWord = wordSpamProbability(model, word, smoothing)
        logSpam += ln(safe(spamGivenWord))
        logHam += ln(safe(1.0 - spamGivenWord))
    }
    // log の差から確率へ戻す（シグモイドと同じ形）
    return 1.0 / (1.0 + exp(min(max(logHam - logSpam, -700.0), 700.0)))
}
```

最後の 1 行に注目してください。`1 / (1 + exp(差))` は **第 6 章のシグモイドとまったく同じ形** です。ロジスティック回帰では重み付き和をシグモイドに通しました。ここでは対数確率の差を通しています。**まったく違う道筋で同じ関数に辿り着きます。**

`filter { it in model.vocabulary }` で未知語を落としています。`in` 演算子が `Set.contains` として働くため、条件が自然言語のように読めます。

2 つの累積値（`logSpam` と `logHam`）を同時に更新するため、ここでは `var` を使いました。`fold` でタプルを畳み込むこともできますが、`Pair` の分解と再構築が入るぶん読みにくくなります。**第 3 章の学習ループと同じく、可変性を関数内部に閉じ込める判断です。**

`min(max(..., -700.0), 700.0)` のクランプは `exp` のオーバーフロー対策です。JVM では `exp(710)` は `Infinity` になり、`1/(1+Infinity)` は 0.0 になるので実は落ちません。それでも 3 言語で同じ式にするため入れています（Python では例外になります）。

## 実行結果

スパム 3 通、通常 5 通の小さなデータセットで学習します。

### 単語ごとのスパム確率

| 単語 | スパム文書 | 通常文書 | 平滑化後の確率 |
| :--- | ---: | ---: | ---: |
| lottery | 3 | 0 | 0.8000 |
| winning | 2 | 0 | 0.7500 |
| sale | 2 | 1 | 0.6000 |
| today | 0 | 2 | 0.2500 |
| meeting | 0 | 3 | 0.2000 |
| unseen（未知語） | 0 | 0 | 0.5000 |

### 文書ごとのスパム確率

| 文書 | 確率 |
| :--- | ---: |
| （空） | 0.3750 |
| project deadline | 0.0909 |
| sale today | 0.2308 |
| lottery | 0.7059 |
| lottery winning | 0.8780 |
| lottery winning sale | 0.9153 |

**これらの値は Python 版・F# 版と完全に一致します。** 乱数も学習ループもないためです。第 3〜6 章では言語ごとに数値が違いましたが、本章では 3 言語のどれで計算しても同じ答えになります。

スパム語が重なるほど確率が上がるのは掛け算の効果です。「lottery」単独では 0.71、「winning」が加わると 0.88 になります。

空の文書の 0.375 は事前確率（3/8）と一致します。単語による更新が 1 つも起きないためです。

## まとめ

- ナイーブベイズに学習ループはありません。数え上げの 1 パスで終わります。
- `groupBy` の 2 引数版とローカル関数により、クラス別の集計が可変変数なしで書けます。
- `Map` の添字は `V?` を返します。`?: 0` と `orEmpty()` が繰り返し必要になります。
- 平滑化で `Int + Double` になるため、第 7 章の整数除算問題がここでは起きません。
- 確率の積は対数の和に変換します。最後の `1 / (1 + exp(差))` は第 6 章のシグモイドと同じ形です。
