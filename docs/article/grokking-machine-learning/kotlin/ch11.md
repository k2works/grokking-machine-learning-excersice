# 第 11 章 サポートベクターマシンとカーネル法（Kotlin 版）

原著第 11 章「Finding boundaries with style」を Kotlin で実装します。第 5 章のパーセプトロンは「分けられればどこでもよい」でした。SVM は **できるだけ広い余白を空ける** 境界線を選びます。

サンプル実装は `apps/grokking-ml-kotlin/src/main/kotlin/ch11/Svm.kt` です。

## この章で作るもの

- ヒンジ損失とマージン
- 正則化つきの SVM 学習
- 線形・多項式・RBF カーネル
- カーネル版パーセプトロン

## パーセプトロンの何が不満なのか

第 5 章のパーセプトロンは、8 点すべてを正しく分類できた時点で更新を止めます。**その境界線がぎりぎりでも構いません。**

```kotlin
@Test
fun `SVM はパーセプトロンより広いマージンを残す`() {
    val (perceptron, _) = perceptronAlgorithm(points, perceptronLabels)
    val asSvm = SupportVectorMachine(perceptron.weights, perceptron.bias)
    val (svm, _) = trainSvm(points, labels, epochs = 20000, regularization = 0.01)

    // どちらも完全に分離できている
    assertEquals(1.0, accuracy(asSvm, points, labels), 1e-9)
    assertEquals(1.0, accuracy(svm, points, labels), 1e-9)
    // しかしパーセプトロンは分離できた時点で止まるため、余白がない
    assertEquals(0.0, asSvm.margin(points), 1e-9)
    assertTrue(svm.margin(points) > 0.5)
}
```

`SupportVectorMachine(perceptron.weights, perceptron.bias)` という 1 行に注目してください。**第 5 章のパーセプトロンを、そのまま SVM の型として解釈し直しています。** 両者の内部表現（重みとバイアス）が同一だからできることです。第 10 章では第 6 章の実装を呼びましたが、ここでは **型を移し替えて同じ指標で測っています**。

| モデル | 正解率 | マージン幅 |
| :--- | ---: | ---: |
| パーセプトロン（第 5 章） | 1.0 | **0.0** |
| SVM（正則化 0.01） | 1.0 | **0.564** |

**パーセプトロンのマージンは 0 でした。** 境界線の上にちょうど乗っている点があるのです。正解率という指標は、この危うさを一切見せません。

## マージンとヒンジ損失

```kotlin
/** ヒンジ損失。マージンの内側に入った分だけ罰する。 */
fun hingeLoss(model: SupportVectorMachine, point: Point, label: Int): Double =
    max(0.0, 1.0 - label * model.score(point))
```

`label * score` は「正しい側にどれだけ離れているか」です。ラベルを **+1 / -1** で表すのはこのためです（第 5・6 章の 0/1 では、この積が意味を持ちません）。

`label * model.score(point)` は `Int * Double` ですが、Kotlin の演算子オーバーロードが `Double` に昇格させます。第 6 章と同じく、型変換を書かずに済みました。

| 状況 | `label × score` | ヒンジ損失 |
| :--- | ---: | ---: |
| 正解かつ余裕がある | 2.0 | 0.0 |
| 正解だがぎりぎり | 0.5 | 0.5 |
| 境界線上 | 0.0 | 1.0 |
| 誤分類 | -1.0 | 2.0 |

**「正解しているのに損失が残る」** のが第 5 章との決定的な違いです。

```kotlin
/** マージン幅。境界線からもっとも近い点までの距離の 2 倍。 */
fun margin(points: List<Point>): Double {
    val norm = sqrt(weights.sumOf { it * it })
    if (norm == 0.0) return 0.0
    return 2.0 * points.minOf { abs(score(it)) } / norm
}
```

`minOf { }` が「もっとも近い点までの距離」をそのまま表します。ループも比較変数も要りません。

## 正則化とマージンのトレードオフ

```kotlin
fun svmError(
    model: SupportVectorMachine,
    points: List<Point>,
    labels: List<Int>,
    regularization: Double = 0.1,
): Double {
    val losses = points.zip(labels).sumOf { (point, label) -> hingeLoss(model, point, label) } / points.size
    return losses + regularization * model.weights.sumOf { it * it }
}
```

第 4 章の L2 正則化とまったく同じ形の罰則項です。ただし **目的が違います**。

| 章 | 正則化の目的 |
| :--- | :--- |
| 第 4 章 | 過学習を防ぐ（重みを縮めてモデルを単純化） |
| 第 11 章 | **マージンを広げる**（重みが小さいほど余白が広い） |

マージン幅は `2 / ||w||` に比例します。**同じ式が別の意味を持つ例です。**

```kotlin
@Test
fun `正則化が弱いほどマージンは広がる`() {
    val (loose, _) = trainSvm(points, labels, epochs = 20000, regularization = 0.01)
    val (tight, _) = trainSvm(points, labels, epochs = 20000, regularization = 0.1)
    assertTrue(loose.margin(points) > tight.margin(points))
}
```

**このテストは直感に反します。** 正則化が強すぎると重みが 0 方向へ潰れ、`||w||` が小さくなる以上に **境界線からの距離そのものが縮みます**。

| 正則化 | 重み | マージン |
| ---: | :--- | ---: |
| 0.01 | (1.726, 1.686) | **0.564** |
| 0.10 | (0.908, 0.837) | 0.206 |

## 更新則

```kotlin
fun svmStep(
    model: SupportVectorMachine,
    point: Point,
    label: Int,
    learningRate: Double = 0.01,
    regularization: Double = 0.1,
): SupportVectorMachine {
    val insideMargin = label * model.score(point) < 1.0
    val weights = model.weights.zip(point) { w, x ->
        val gradient = 2.0 * regularization * w - if (insideMargin) label * x else 0.0
        w - learningRate * gradient
    }
    val bias = model.bias + if (insideMargin) learningRate * label else 0.0
    return SupportVectorMachine(weights, bias)
}
```

2 つの力が働きます。

1. **常に働く力**: 重みを 0 方向へ縮める（`2 × 正則化 × w`）
2. **マージンの内側でだけ働く力**: 点を押し返す（`label × x`）

`if` が式なので、`- if (insideMargin) label * x else 0.0` と **条件付きの項をそのまま式の中に書けます**。Python では `if` 文で分岐してから加算しました。

マージンの外にいる点では 2 番目が消えるので、**重みが少し縮むだけ** です。

```kotlin
@Test
fun `svmStep は自信のある点をほとんど動かさない`() {
    val model = SupportVectorMachine(listOf(1.0, 1.0), -3.0)
    val moved = svmStep(model, listOf(3.0, 2.0), 1, learningRate = 0.01, regularization = 0.1)
    // マージンの外なので、重みを縮める力しか働かない
    assertEquals(model.bias, moved.bias, 1e-9)
    assertTrue(moved.weights[0] < model.weights[0])
}
```

**バイアスがまったく動かない** ことが「押し返す力が働いていない」ことの証拠になります。

## カーネル法

XOR は直線で分けられません（第 10 章）。SVM は **点を高次元へ写してから直線を引く** ことで解きます。ただし、写した先の座標を計算せず、**内積だけを求めます**。これがカーネルトリックです。

```kotlin
/** 2 点の類似度を測る関数。 */
typealias Kernel = (Point, Point) -> Double

/** 線形カーネル。ただの内積。 */
val linearKernel: Kernel = { a, b -> dot(a, b) }

/** 多項式カーネル。特徴量の積を暗黙のうちに作る。 */
fun polynomialKernel(degree: Int = 2, constant: Double = 1.0): Kernel =
    { a, b -> (dot(a, b) + constant).pow(degree) }

/** RBF（ガウシアン）カーネル。距離が近いほど 1 に近づく。 */
fun rbfKernel(gamma: Double = 1.0): Kernel =
    { a, b ->
        val squaredDistance = a.zip(b) { x, y -> (x - y) * (x - y) }.sum()
        exp(-gamma * squaredDistance)
    }
```

第 9 章の `Impurity` と同じ設計です。**設定が要らない `linearKernel` は `val`、設定が要る `polynomialKernel` / `rbfKernel` は「カーネルを返す関数」** にしました。

`fun polynomialKernel(...): Kernel = { a, b -> ... }` という形は、**関数を返す関数がラムダ 1 つで書ける** ことを示しています。デフォルト引数も併用できるため、`polynomialKernel()` だけで 2 次のカーネルが得られます。

### カーネルの意味

`polynomialKernel(2)` は `(x·y + 1)²` を計算します。展開すると `x₁²y₁² + 2x₁y₁x₂y₂ + ...` という項が現れます。**これは 6 次元空間での内積と同じです。**

つまり、6 次元へ写す計算を **一度もせずに**、その空間での内積が手に入ります。RBF カーネルはさらに極端で、**無限次元空間の内積** に相当します。

```kotlin
@Test
fun `rbfKernel は距離とともに減衰する`() {
    val kernel = rbfKernel(1.0)
    val near = kernel(listOf(0.0, 0.0), listOf(0.5, 0.0))
    val far = kernel(listOf(0.0, 0.0), listOf(3.0, 0.0))
    assertTrue(0.0 < far)
    assertTrue(far < near)
    assertTrue(near < 1.0)
}
```

Python 版では `0.0 < far < near < 1.0` という連鎖比較 1 行で書けましたが、**Kotlin には連鎖比較がない** ため 3 行に分けています。`in` を使った範囲チェックはありますが、変数同士の大小連鎖には使えません。

## カーネル分類器

```kotlin
/** カーネル分類器。訓練点そのものを重み付きで覚えておく。 */
data class KernelClassifier(
    val points: List<Point>,
    val labels: List<Int>,
    val weights: List<Double>,
    val bias: Double,
    val kernel: Kernel,
) {
    fun score(point: Point): Double =
        bias + weights.indices.sumOf { i -> weights[i] * labels[i] * kernel(points[i], point) }

    fun predict(point: Point): Int = if (score(point) >= 0) 1 else -1
}
```

**モデルが訓練データそのものを保持します。** これまでのモデルは重みベクトル（第 3〜6・10 章）や確率表（第 8 章）、木（第 9 章）でしたが、カーネル法は **訓練点を捨てられません**。

`data class` に関数（`kernel`）をフィールドとして持たせている点に注意が要ります。**関数は `equals` を持たない** ため、`KernelClassifier` 同士の等価比較は同じラムダインスタンスでない限り `false` になります。第 9 章では木の等価比較をテストに使いましたが、本章ではそれができません。

そのため本章のテストは、等価性ではなく **振る舞い**（正解率、重みの符号）を検証しています。**型に関数を持たせると、自動生成される `equals` の意味が変わる** という副作用です。

## 実行結果

XOR を 3 種類のカーネルで解きます。

| カーネル | 正解率 |
| :--- | ---: |
| 線形 | 0.75 |
| 多項式（2 次） | **1.00** |
| RBF | **1.00** |

**線形カーネルは 0.75 で頭打ちです。** 内積しか使わないので、実質的に第 5 章のパーセプトロンと変わりません（Python 版・F# 版では 0.50 でした。乱数列の違いでどの点を先に見るかが変わるためです）。

多項式カーネルと RBF カーネルは 1.0 に達しました。**アルゴリズムは一切変えず、カーネル関数を差し替えただけです。**

第 10 章のニューラルネットワークと同じ問題を、まったく違う方法で解いたことになります。

| 手法 | XOR の解き方 |
| :--- | :--- |
| ニューラルネット（第 10 章） | 隠れ層で特徴を **学習する** |
| カーネル法（第 11 章） | カーネルで特徴を **設計する** |

## まとめ

- 第 5 章のパーセプトロンと SVM は内部表現が同じなので、型を移し替えて同じ指標で測れます。
- ヒンジ損失は「正解しているのにまだ損失が残る」形です。`if` が式なので、条件付きの勾配項をそのまま式に書けます。
- SVM の正則化は第 4 章と同じ式ですが、目的が「過学習防止」から「マージン拡大」に変わります。
- カーネルは第 9 章の `Impurity` と同じ設計です。設定が要るものは「関数を返す関数」にします。
- `data class` に関数を持たせると `equals` が期待どおり働きません。テストは振る舞いで検証します。
- Kotlin には連鎖比較がないため、`0 < a < b < 1` は 3 つのアサーションに分かれます。
