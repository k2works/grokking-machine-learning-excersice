# Grokking Machine Learning シリーズ レビュー結果

- 実施日: 2026-08-13
- 対象: v0.1.0（PR #1）

## レビュー実施上の注記

マルチエージェント（`xp-programmer` / `xp-tester` / `xp-architect` / `xp-technical-writer` / `xp-user-representative`）を並列起動したが、**各エージェントの最終レポートが呼び出し元へ返らなかった**（アイドル通知のみ届き、本文が届かない状態）。
そのため `developing-review` スキルに定義されたフォールバック手順に従い、5 視点を逐次レビューに切り替えて実施した。

本レポートの指摘は **すべて実際にファイルを読み、コマンドを実行して確認した事実** に基づく。推測による指摘は含めていない。検証に使ったコマンドは各指摘に付記した。

## 総合評価

記事・実装・ノートブックの三者がコードを複製せず結び付いており、記載された数値がすべて実測値であるという教材としての誠実さは高い水準にある。3 言語で同じアルゴリズムを実装し、言語機能とアルゴリズム構造の噛み合いを比較する構成も一貫している。

一方で、**公開後に読者が最初に触れる導線に実害のある不具合が 1 件ある**（ノートブックから記事へのリンクがサイト上で 404）。また、章ごとの記事に載せたテスト実行結果が執筆時点のスナップショットのままで、読者が再現できない状態になっている。いずれもマージ前に対応する価値がある。


| C | `notebooks:sync` 時にリンクを書き換える | 両立するが、同期スクリプトに変換処理が増える |

**推奨は B**。教材の読者はオンラインで読む前提が強く、変換処理という新たな仕掛けを増やさずに済む。

## 視点別の所見

### xp-programmer（コード品質）

#### 良い点

- 3 言語で引数順の方針が一貫している。F# は「ハイパーパラメータ → データ」で部分適用が効く形、Python/Kotlin は「データ → 設定（デフォルト引数）」。**言語の呼び出し慣習に合わせて意図的に変えており、その理由が記事に書かれている**
- モデルはすべて不変で、更新は新しい値を返す純関数。学習ループの可変性だけを関数内部に閉じ込める方針が全章で守られている
- 章をまたいだ再利用が機能している。第 12 章は第 9 章の決定木を、第 13 章は第 6・7・9・12 章を、いずれも **1 行も書き換えずに** 部品として使えている

#### 改善提案

- 【中】上記 #3（JAR バージョン依存）
- 【低】上記 #7（ch03 のテスト粒度）

### xp-tester（テスト品質）

#### 良い点

- 乱数を含むアルゴリズムに対し「1 点分の更新は手計算値と厳密比較」「学習全体は関係性（収束範囲・誤差の減少・ギャップの拡大）で検証」という 2 段構えが全章で徹底されている
- 第 5 章でパーセプトロン誤差が初期状態 0 になる性質を、テストを緩めるのではなく **実際の挙動を検証する形に書き換えて** 記録している
- L1 正則化の閾値を「もっとも 0 から遠い F# の実測値（-0.0011）」に合わせて `5e-3` に決めており、数学的理想でなく実装の実測に基づいている

#### 改善提案

- 【中】上記 #4（3 言語のテスト網羅差の明示）
- 【低】上記 #7

#### 懸念事項

- ch04 の「高次モデルは過学習する」テストは Kotlin で汎化ギャップの差が 0.195 対 0.233 と margin が小さい。シードが固定されているため flaky にはならないが、データやエポック数を変えると容易に反転する。**変更に弱いテスト**である点は認識しておきたい

### xp-architect（設計整合性）

#### 良い点

- ノートブックの正本を `apps/` に置き、実装を相対パスで読み込む構造は、記事・実装・ノートブックの三者不整合を原理的に防いでいる
- ローカルと CI で同じコマンド（`gulp notebooks:check`、`./gradlew test`）を使えている
- `deploy:prd` が存在しない構成で gulpfile が読み込めなくなる問題を、存在確認で握り潰さず「存在するときだけ登録する」形で直している

#### 改善提案

- 【高】上記 #1（同期によってリンクが壊れる = 同期という仕掛けの副作用）
- 【中】上記 #3
- 【低】上記 #6

#### 懸念事項

- 環境が Nix devShell / Docker / uv / Gradle / dotnet の 5 系統ある。教材として「各言語の標準的な環境で動く」ことを示す意味はあるが、**すべてを維持し続けるコスト**は小さくない。とくに Nix の `kotlin` devShell は Gradle Wrapper 導入後は必須ではなくなっている（JDK があれば足りる）

### xp-technical-writer（ドキュメント品質）

#### 良い点

- 「この章で作るもの」「まとめ」「参照」の構成が全 33 章で揃っており、どの言語版から読み始めても迷わない
- 数値を載せた表に実行条件（学習率・エポック数・シード）が併記されている
- 3 言語版の重複は意図的だが、各版とも **その言語固有の観点**（Python の `frozen=True` の落とし穴、Kotlin の `zip` が 2 本まで、F# のカリー化）で差別化されており、冗長さより完結性の利点が上回っている

#### 改善提案

- 【高】上記 #1
- 【中】上記 #2
- 【低】上記 #5

#### 懸念事項

- 用語は「マージン」「汎化ギャップ」「切り株」「発言権」で統一されており揺れは見つからなかった。ただし「発言権」は AdaBoost の `alpha` に対する独自訳。初出（第 12 章）で原語（weight / alpha）を併記すると、他資料へ進む読者が繋げやすい

### xp-user-representative（利用者視点）

#### 良い点

- 記事の実行例をコピーしてそのまま実行でき、記載どおりの値が出た（第 3 章・第 12 章で確認）
- 「試してみる」節が全章にあり、パラメータを変えて再実行する体験に繋がっている
- 「バギングが効かない」「パーセプトロンのマージンが 0 になる」など、**うまくいかない結果を隠していない**。手法の得手不得手が分かる

**検証コマンド**:

```bash
cd apps/grokking-ml-python
uv run python -c "
from grokking_ml.ch03_linear_regression import linear_regression, model_rmse
features = [1, 2, 3, 5, 6, 7]; labels = [155, 197, 244, 356, 407, 448]
model, errors = linear_regression(features, labels)
print(model.slope, model.intercept, model_rmse(model, features, labels))"
# → 51.04430678220095 91.59448307644864 7.450146103691173（記事の 51.0443 / 91.5945 / 7.4501 と一致）
```

#### 改善提案

- 【高】上記 #1（サイトでノートブックを開いた読者が記事へ戻れない）
- 【中】上記 #2（第 3 章でテストを実行すると記事と違う数が出て戸惑う）

#### 懸念事項

- Kotlin ノートブックは事前に `./gradlew jar` が必要で、忘れると `@file:DependsOn` が解決できずに失敗する。セットアップ節には書かれているが、**失敗時のエラーメッセージから原因に辿り着けるか**は読者の経験次第。ノートブック冒頭の注記を太字にするなどの手当てがあるとよい
