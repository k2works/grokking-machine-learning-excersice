    Grokking Machine Learning シリーズ レビュー結果¶

    • 実施日: 2026-08-13
    • 対象: v0.1.0（PR #1）
    • 記事 52 本（docs/article/grokking-machine-learning/）
    • サンプル実装 3 言語（apps/grokking-ml-{python,kotlin,fsharp}/）
    • ノートブック 33 本（apps/grokking-ml-*/notebooks/）
    • 手法: 5 視点によるマルチパースペクティブレビュー

    レビュー実施上の注記¶

    マルチエージェント（xp-programmer / xp-tester / xp-architect / xp-technical-writer / xp-user-representative）を並列起動したが、4 つのエージェントは最終レポートが呼び出し元へ返らなかった（アイドル通知のみ届く状態）。 そのため developing-review スキルのフォールバック手順に従い、まず 5 視点を逐次レビューして本レポートを作成した。

    その後 xp-user-representative からレポートが届き、逐次レビューでは検出できなかった重大な問題（#0）を含んでいた。同エージェントの指摘は本レポートに統合し、すべて再検証したうえで 採否を記載した。誤りだった指摘も記録に残す。

    本レポートの指摘は すべて実際にファイルを読み、コマンドを実行して確認した事実 に基づく。推測による指摘は含めていない。検証に使ったコマンドは各指摘に付記した。

    総合評価¶

    記事・実装・ノートブックの三者がコードを複製せず結び付いており、記載された数値がすべて実測値であるという教材としての誠実さは高い水準にある。3 言語で同じアルゴリズムを実装し、言語機能とアルゴリズム構造の噛み合いを比較する構成も一貫している。

    一方で、新規に clone した読者が Kotlin 版をビルドできないという致命的な問題があった（#0、修正済み）。加えて公開後の導線に実害のある不具合が 1 件（#1、ノートブックから記事へのリンクがサイト上で 404）、章ごとのテスト実行結果が再現できない問題（#2）がある。

    指摘 #0 は逐次レビューでは検出できなかった。レビュー担当（私）が常に Nix devShell（JDK 21）でビルドしており、システム既定の JDK 25 で試していなかったためである。環境を固定して作業していると、その環境ごと見落とす。

    改善提案（重要度順）¶

    高（マージ前に対応すべき）¶

    # 提案 箇所 指摘元 状態 理由
    0 Kotlin プラグインを JDK 25 に対応した版へ上げる apps/grokking-ml-kotlin/build.gradle.kts:2、ops/nix/environments/kotlin/shell.nix:8 user-representative 修正済み Kotlin 2.0.21 に同梱の JavaVersion.parse が JDK 25 のバージョン文字列 25.0.2 を解釈できず、./gradlew clean test が Internal compiler error で失敗する。新規 clone した読者は第 3 章の入口で止まる。既存のビルド成果物があると ./gradlew test は UP-TO-DATE で成功して見えるため、手元では気づけない

    #0 の検証と修正:

    java -version                        # → openjdk 25.0.2（システム既定）
./gradlew clean test --no-daemon     # → BUILD FAILED: Internal compiler error
./gradlew clean compileKotlin --stacktrace | grep JavaVersion
# → java.lang.IllegalArgumentException: 25.0.2
#      at org.jetbrains.kotlin.com.intellij.util.lang.JavaVersion.parse

    build.gradle.kts の Kotlin プラグインを 2.0.21 → 2.2.20 に上げて解消した。検証結果は次のとおり。

    環境 結果
    システム JDK 25.0.2 clean test 成功、178 tests
    Nix devShell（JDK 21.0.8） clean test 成功
    Kotlin ノートブック ch03 再実行して出力が完全に一致（コンパイラ更新の影響なし）

    あわせて shell.nix の jdk（バージョン未固定）を jdk21 に変更した。記事が「JVM 21」を前提にしているのに実体が無印だったため、nixpkgs の更新で同じ障害を踏む余地があった。

    # 提案 箇所 指摘元 状態 理由
    1 ノートブックから記事へのリンクを、同期後の階層で解決できる形に直す 全 33 ノートブックの先頭マークダウンセル（例: apps/grokking-ml-python/notebooks/ch03.ipynb:12） technical-writer 修正済み リンクは ../../../docs/article/.../ch03.md。apps/ 配下では正しく解決するが、gulp notebooks:sync で docs/article/grokking-machine-learning/python/notebooks/ へ複製されると docs/article/docs/article/... を指し 公開サイト上で 404 になる。ビルド済み HTML でも href="../../../docs/article/grokking-machine-learning/python/ch03.md" のまま出力されていることを確認済み

    検証コマンド:

    grep -o 'href="[^"]*ch03[^"]*"' site/article/grokking-machine-learning/python/notebooks/ch03/index.html | grep '\.md'
# → href="../../../docs/article/grokking-machine-learning/python/ch03.md"

    修正案: 同期先（docs/.../{lang}/notebooks/）から見た記事は ../ch03.md で解決する。正本の apps/.../notebooks/ から見ると壊れるが、ノートブックの主たる閲覧経路はサイトと IDE の両方である。両立させるなら次のいずれか。

    案 内容 得失
    A リンクを ../ch03.md に統一する サイトで正しく解決。apps/ 配下では壊れる（IDE で開いた人はリンクを踏めない）
    B GitHub 上の絶対 URL にする どちらの経路でも解決する。オフラインでは辿れない
    C notebooks:sync 時にリンクを書き換える 両立するが、同期スクリプトに変換処理が増える

    採用したのは B（GitHub 上の絶対 URL）。当初は公開サイトの URL も候補だったが、GitHub Pages が未有効（gh-pages ブランチは存在するがサイトは 404）だったため、確実に解決する GitHub の blob URL にした。

    https://github.com/k2works/grokking-machine-learning-excersice/blob/main/docs/article/grokking-machine-learning/python/ch03.md

    変更したのはマークダウンセルのリンク 1 行のみで、コードセルには触れていない。出力と実行状態はそのまま保たれている（gulp notebooks:check で 33 本すべて実行済みを確認、3 言語で出力値の残存も確認）。

    サイトを再ビルドして、33 ページすべてで絶対 URL が出力され、壊れた相対リンクが 0 件になったことを確認した。

    あわせて #5（リンク文言）も同時に直した。「第 3 章 線形回帰（Jupyter Notebook（Python） の言語版）」→「第 3 章 線形回帰（Python 版）」。

    中（対応推奨）¶

    # 提案 箇所 指摘元 理由
    2 章ごとの記事に載せたテスト実行結果を、再現可能な形に改める 全 33 章記事の「テスト」節（例: docs/article/grokking-machine-learning/python/ch03.md の # 7 passed） technical-writer / user-representative 各章は執筆時点の 累積 テスト数を載せている（ch03: 7/8/8、ch05: 33/34/34、ch09: 105/106/106、ch13: 179/178/176）。読者が第 3 章の時点で uv run pytest を実行すると 179 と出て一致しない。「読んで同じ手順を再現する人」という読者像と矛盾する
    3 Kotlin ノートブックの JAR バージョン依存を解消する apps/grokking-ml-kotlin/notebooks/*.ipynb（@file:DependsOn("../build/libs/grokking-ml-kotlin-0.1.0.jar")）、apps/grokking-ml-kotlin/build.gradle.kts:6 architect ノートブック 11 本が JAR ファイル名に埋め込まれた 0.1.0 に依存している。build.gradle.kts の version を上げた瞬間に 11 本すべてが動かなくなる。tasks.jar { archiveFileName.set("grokking-ml-kotlin.jar") } でファイル名を固定すれば版から切り離せる
    4 3 言語間のテスト網羅の差を、意図か漏れか明示する ch10（Python/Kotlin 17・F# 15）、ch11（Python 20・Kotlin/F# 19）、ch12（Python 18・Kotlin/F# 17） tester ch10 の 2 件（前章のロジスティック回帰との比較・不変性の検証）は F# 記事で「モジュールの名前解決の都合」「言語が保証するためテスト不要」と理由を書いており意図的。しかし ch11 と ch12 の各 1 件は理由が書かれておらず、漏れと区別が付かない（ch11: test_kernel_classifier_is_a_pure_function_of_its_parts、ch12: test_adaboost_stops_when_no_useful_learner_remains）

    検証コマンド（#2）:

    grep -h "passed\|合格" docs/article/grokking-machine-learning/python/ch03.md | tail -1   # → # 7 passed
cd apps/grokking-ml-python && uv run pytest -q | tail -1                                  # → 179 passed

    修正案（#2）: 各章の実行例を「その章のテストだけを走らせるコマンド」に変える。読者が実行して一致する。

    # 変更前
uv run pytest
# 7 passed

# 変更後
uv run pytest tests/test_ch03_linear_regression.py
# 7 passed

    低（改善の余地あり）¶

    # 提案 箇所 指摘元 理由
    5 ノートブック冒頭のリンク文言を整える（修正済み） 全 33 ノートブックの先頭セル technical-writer 「第 3 章 線形回帰（Jupyter Notebook（Python） の言語版）」は括弧が二重で、リンク先が記事なのに「の言語版」という語が実態と合っていない。「第 3 章 線形回帰（Python 版の記事）」で足りる
    6 Markdown Lint の対象を段階的に広げる計画を残す .markdownlint-cli2.jsonc:17 architect 本シリーズ 52 ファイルのみを対象にした判断は妥当だが、既存文書 2200 件超の違反は放置されたまま。設定にコメントは残してあるので、あとは実行計画（どの単位で直すか）を決めれば負債の可視化として十分
    7 ch03 の Python テストだけ粒度が粗い apps/grokking-ml-python/tests/test_ch03_linear_regression.py:57（test_rmse） tester Kotlin/F# は「誤差ゼロのとき 0」「二乗平均平方根を返す」の 2 件に分けているが、Python は 1 件にまとめている。失敗時にどちらの性質が壊れたか分かりにくい。ch03 の 7 対 8 という差はこれが理由で、カバレッジ自体の欠落ではない

    レビューから派生した再発防止¶

    指摘 #0 を検出できなかった原因は実装ではなく 検証の網 にあった。

    検証経路 当時の状態 なぜ通ってしまったか
    ローカル（レビュー担当） Nix devShell 固定 常に JDK 21。システム既定の JDK 25 を試していない
    CI java-version: '21' 固定 JDK 21 しか検証していない（.github/workflows/grokking-ml.yml）
    CI のコマンド ./gradlew test キャッシュされた成果物があると UP-TO-DATE でコンパイルが走らない

    対応（実施済み）: CI の Kotlin ジョブに JDK 21 / 25 のマトリクスを追加し、コマンドを ./gradlew clean test に変更した。同じ問題が起きれば CI が落ちる。

    矛盾事項¶

    # 視点 A 視点 B 論点 推奨判断
    1 technical-writer:「ノートブックの記事リンクはサイトで解決すべき」 architect:「ノートブックの正本は apps/ 配下であり、そこで完結すべき」 リンクの解決先をどちらの経路に合わせるか 両立させる（上記の案 B、絶対 URL）。どちらか一方に寄せると他方が壊れる構造的な問題であり、片側を諦める理由がない
    2 tester:「3 言語のテストは揃えるべき」 programmer:「言語が保証する性質はテストしない」 F# で不変性のテストを書かない判断の是非 書かない判断を支持する。F# のレコードとリストは言語レベルで不変であり、テストしても常に成立して情報量がない。ただし #4 のとおり その判断を記事に明記すること が条件。ch10 は明記済み、ch11・ch12 は未記載

    視点別の所見¶

    xp-programmer（コード品質）¶

    良い点¶

    • 3 言語で引数順の方針が一貫している。F# は「ハイパーパラメータ → データ」で部分適用が効く形、Python/Kotlin は「データ → 設定（デフォルト引数）」。言語の呼び出し慣習に合わせて意図的に変えており、その理由が記事に書かれている
    • モデルはすべて不変で、更新は新しい値を返す純関数。学習ループの可変性だけを関数内部に閉じ込める方針が全章で守られている
    • 章をまたいだ再利用が機能している。第 12 章は第 9 章の決定木を、第 13 章は第 6・7・9・12 章を、いずれも 1 行も書き換えずに 部品として使えている

    改善提案¶

    • 【低】上記 #7（ch03 のテスト粒度）

    xp-tester（テスト品質）¶

    良い点¶

    • 乱数を含むアルゴリズムに対し「1 点分の更新は手計算値と厳密比較」「学習全体は関係性（収束範囲・誤差の減少・ギャップの拡大）で検証」という 2 段構えが全章で徹底されている
    • 第 5 章でパーセプトロン誤差が初期状態 0 になる性質を、テストを緩めるのではなく 実際の挙動を検証する形に書き換えて 記録している
    • L1 正則化の閾値を「もっとも 0 から遠い F# の実測値（-0.0011）」に合わせて 5e-3 に決めており、数学的理想でなく実装の実測に基づいている
